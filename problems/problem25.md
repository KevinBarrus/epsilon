# 问题 25：SWE-bench 评测的补丁被运行产物污染，且存在裁判记录不一致

## 一、问题背景：为什么 retry9 的 `0/5` 不能直接当作解题成功率

第二十四轮优化已让 Agent 在官方实例镜像中执行命令，并将容器写入身份与宿主工作区对齐。随后使用五个 Django Lite 样本进行 retry9：

```text
django__django-11019
django__django-11283
django__django-11905
django__django-13321
django__django-14155
```

结果目录：

```text
evaluation-results/swebench-retry9/
```

命令最终输出：

```text
swebench evaluation: 0/5 passed
```

这次不能只看到“0 通过”就得出“Agent 五题全都解错”。一次真实评测像一次考试：有些同学交卷后答案错误，有些人中途网络断开，有些人的答题卡被弄脏，还有些试卷的阅卷记录本身不一致。只有先把这几种情况分开，成功率才有意义。

## 二、先理解正常评测应该经过哪些关口

```text
模型请求
  ↓
Agent 读写代码、在官方实例容器中执行命令
  ↓
从工作区生成代码补丁
  ↓
独立官方 Harness 应用补丁并运行隐藏测试
  ↓
写入裁判报告
```

只有同时完成“生成补丁”和“官方 Harness 裁判”后，才可以称为一个有效的解题样本。

## 三、排查过程

### 1. 先按失败阶段拆分五条结果

读取 `results.jsonl` 中的 `error_category`、`error_stage`、`stop_reason`、模型请求次数和工具轮次，得到：

| 实例 | 停止位置 | 关键信息 | 初步分类 |
| --- | --- | --- | --- |
| 11019 | Agent Loop | 第 33 次模型请求超时 | 模型服务失败 |
| 11283 | 官方 Harness | 补丁生成并应用，隐藏失败用例未通过 | 真实代码失败 |
| 11905 | 官方 Harness | 日志称补丁已应用、测试已运行，报告却称未应用 | 裁判记录待核对 |
| 13321 | 官方 Harness 环境 | 补丁包含 `Django.egg-info/*`，应用时同名文件冲突 | 运行产物污染 |
| 14155 | 官方 Harness | 达到 40 工具轮次，未生成补丁 | 真实探索失败 |

因此，这五条不是同一个根因。`0/5` 是一次批处理的原始计数，不是可直接写入简历的可靠解决率。

### 2. 11283 证明容器与官方裁判的主链路已经通了

`report.json` 记录：

```text
patch_successfully_applied = true
infra_failure = false
resolved = false
```

其中一个目标失败测试仍然失败，而原本应保持通过的八个测试仍然通过。这说明：

```text
Agent 改代码
  ↓
补丁成功交给官方 Harness
  ↓
官方在真实环境执行测试
  ↓
补丁逻辑不正确
```

这是一条有效的负样本，不是容器、权限或评测框架提前中断。

### 3. 13321 定位到补丁污染

13321 的官方日志显示补丁尝试创建：

```text
Django.egg-info/PKG-INFO
Django.egg-info/SOURCES.txt
Django.egg-info/requires.txt
...
```

但官方裁判的干净项目中已存在这些同名文件，因此补丁应用失败。日志同时显示真正的代码文件 `django/contrib/sessions/backends/base.py` 已开始应用，说明污染文件来自 Agent 运行测试或安装过程产生的构建元数据，而不是任务要求修改的源码。

可以把它理解为：模型本来要交“改好的作业纸”，却把运行程序时自动生成的临时草稿也夹进了答案。阅卷程序看到草稿与试卷已有内容撞名，整份答案就无法正常批改。

本质是：当前补丁生成器把“基线中没有的所有工作区变化”都当成候选补丁，但没有区分用户源码修改与评测运行产生的临时构建产物。

### 4. 11905 的日志与报告互相矛盾

11905 的 `run_instance.log` 明确写入：

```text
Checking patch django/db/models/lookups.py...
Applied patch django/db/models/lookups.py cleanly.
Test runtime: 7.06 seconds
```

但同一任务的 `report.json` 最终记录：

```text
patch_successfully_applied = false
resolved = false
infra_failure = false
```

这好比监考录像显示考卷已经收走并批阅，成绩单却写着“没有收到答卷”。在没有读取 `test_output.txt` 与 Harness 报告生成逻辑前，不能武断地说是 Agent 补丁没有应用，也不能把它与正常的代码失败混为一谈。

### 5. 11019 与 14155 的边界

- 11019 是模型请求超时，没有进入官方 Harness。这是网络或模型服务可用性问题，应单独重跑，不能计入代码补丁能力
- 14155 达到工具轮次上限且没有生成补丁。它是有效的 Agent 未收敛样本，但没有代码补丁可供正确性裁判

## 四、问题定义

本轮需要处理两个不同层次的问题：

1. **补丁卫生问题**：评测运行产生的构建产物被混入代码补丁，使官方 Harness 无法应用补丁
2. **结果可信度问题**：11905 的 Harness 运行日志与最终报告字段不一致，现有结果归类无法说明它究竟是“补丁未应用”“测试未通过”还是“报告解析错误”

如果不修复第一项，类似 13321 的任务会继续因非源码文件失败；如果不核对第二项，评测报告就不能可靠地区分 Agent 失败和裁判记录异常。

## 五、影响与数据口径

- retry9 不能作为单一的 `0/5` 解题成功率写入简历
- 11283 是明确的真实补丁失败样本
- 14155 是明确的 Agent 未产生补丁样本
- 11019 是模型超时样本，应从代码正确率分母排除并重跑
- 13321 是补丁污染导致的评测无效样本，应修复后重跑
- 11905 暂列为“官方裁判未通过，原因待核对”，不据此推断补丁正确性

## 六、面试表达

可以这样说明本轮排查：

> 我没有把一次 `0/5` 直接解释为模型能力差，而是按模型请求、Agent 执行、补丁生成和独立裁判四层拆分结果。排查发现一个任务的补丁里混入了运行时生成的 `egg-info` 文件，导致裁判无法应用补丁；另一个任务的应用日志与最终报告字段矛盾。这个过程让我把评测重点从“打印一个通过率”转成“先保证每条样本的失败归因可信”。

## 七、边界

- 不修改 SWE-bench 数据集、参考补丁或隐藏测试
- 不用“忽略所有异常”伪造通过率
- 不在普通 Epsilon 运行路径中加入 SWE-bench 专属过滤逻辑
- 不把构建产物过滤扩大为删除基线中本来存在的项目文件
