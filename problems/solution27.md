# 第二十七轮优化方案：补齐执行轨迹闭环，并增加最小长任务状态

## 一、目标

- 保证模型失败、用户取消和并行工具执行后，Session 仍能恢复真实发生过的轨迹
- 让工具执行状态进入持久化与上下文压缩链路
- 防止同一 Session 被多个进程同时写入
- 补齐 MCP 的超时、输出和本地权限策略
- 在不重构现有 Session/Context 架构的前提下，为长任务增加可恢复的最小控制状态
- 明确工作区路径边界与真正沙箱之间的差别

## 二、总体原则

保留现有三层数据模型：

```text
完整 JSONL 历史 → Session/Memory → ContextManager 构造模型上下文
```

不把 Session 改造成庞大的统一状态对象，也不引入数据库、向量库或完整事件溯源框架。先复用已有 `Message`、`ToolResult`、JSONL 记录、输出限制和错误分类，修复所有调用路径共享的根因。

长期任务部分只吸收 LoopX 的最小思想：

```text
长期目标负责“要去哪里”
单次 Agent 运行负责“这次走哪一步”
检查点负责“已经走到哪里、凭什么这么判断”
```

不移植其 Registry、Quota、多人认领、调度器、看板和多 Agent 治理能力。

## 三、代码改动顺序

### 问题一方案：失败时携带并持久化本轮新增轨迹

1. 在 `agent_loop.py` 增加一个只服务于执行边界的失败类型，保存原始 `AgentError` 与 `new_messages`
2. 模型请求在已有工具轮次后失败时，由 `AgentLoop` 抛出该失败对象，不丢弃已经形成的 assistant/tool 消息
3. `ui.py` 先按原顺序持久化失败对象携带的消息，再追加最终错误消息
4. 若模型在任何有效事件产生前失败，不制造空工具轨迹，保持现有错误展示
5. 增加“工具成功后，下一次模型请求失败，恢复 Session 仍包含完整工具调用和结果”的测试

这里不把持久化逻辑下沉到 `AgentLoop`。AgentLoop 只报告发生过什么，Session 仍是唯一持久化入口。

### 问题二方案：取消并行批次时补全每个 ToolCall 的终态

1. 并行执行器在取消时收集已经完成的真实 `ToolResult`
2. 对尚未拿到结果的调用生成结构化取消结果，内容明确为“执行结果未知”，不能写成“确认未执行”
3. 所有结果保持模型原始 ToolCall 顺序，并保留对应 `call_id`
4. AgentLoop 将 assistant tool_calls 与全部 tool 终态一起放入 `AgentLoopCancelled.new_messages`
5. UI 继续复用 `_persist_new_messages()`，不增加 TUI 专用持久化分支
6. 增加两个测试：部分工具完成后取消、全部工具尚未完成时取消；恢复后每个 ToolCall 都有唯一 ToolResult

第一版仍只并行标记为 `parallel` 的安全只读工具，不扩大有副作用工具的并发范围。

### 问题三方案：贯通工具执行状态与文件事实

1. 将 `ToolResult.is_error` 映射到 tool Message 的 `status`，并保留 `error_category`
2. SessionStore 继续使用现有 Message JSONL 字段，不新增另一套工具结果协议
3. `_serialize_messages()` 在摘要输入中写明工具状态和错误类别
4. `_collect_file_operations()` 按 `tool_call_id` 配对调用与结果，只把成功执行的文件读取/写入计入事实列表
5. 对找不到对应结果、结果被取消或执行失败的调用，不写入 `<read-files>` / `<modified-files>`
6. 增加失败写入不进入 modified-files、成功写入正常进入、摘要保留错误状态的测试

### 问题四方案：为 Session 增加生命周期级单写者锁

1. 在创建或恢复 Session 时，对该 `session_id` 对应的锁文件获取非阻塞独占锁
2. 锁由 Session 持有，在 `close()` 时释放；不同 Session 使用不同锁文件，互不影响
3. 第二个进程尝试恢复正在使用的 Session 时立即返回清晰错误，不等待、不覆盖
4. 使用 Python 标准库和 Linux/WSL 的 `fcntl`，不引入第三方锁依赖
5. 增加同一 Session 第二次打开失败、关闭后可重新打开、不同 Session 可同时打开的测试

锁只解决同一会话的单写者问题，不把整个工作区加全局锁。

### 问题五方案：统一 MCP 的超时、输出与权限策略

1. 使用 `asyncio.wait_for()` 为一次 MCP JSON-RPC 请求增加固定超时，超时后转换为结构化工具错误
2. MCP 文本结果复用现有 `limit_tool_output()`，保持本地工具和远程工具相同的上下文入口上限
3. MCP 的 `readOnlyHint` 和 `idempotentHint` 只作为外部元数据，不直接获得自动放行资格
4. 第一版所有 MCP 工具默认进入写工具审批；只有 Epsilon 本地配置的受信任工具白名单才能降级为自动允许的只读工具
5. “本会话始终允许”只对非 command 且 `idempotent=True` 的工具开放；其他工具即使界面返回该选项，也退化为仅允许一次
6. 增加 MCP 无响应超时、超长输出截断、伪造只读标记仍需审批、不可幂等工具不获得会话授权的测试

不让模型自行判断 MCP 工具是否安全，也不为第一版实现复杂能力策略语言。

### 问题六方案：明确 Shell 安全边界，暂不伪造沙箱能力

1. 保持命令工具每次审批、超时、进程组清理和输出限制
2. 在工具描述与模块说明中明确：`cwd=workspace` 只提供默认执行位置，不限制 Shell 访问范围
3. 不增加危险命令黑名单；黑名单无法覆盖 shell 组合、脚本和解释器绕过
4. 无人值守或不可信任务复用评测中已有的可替换命令执行器与容器执行能力，后续单独设计生产沙箱

本轮不把所有本地交互强制放进容器，避免破坏用户开发环境、凭据、构建缓存和调试体验。

### 问题七方案：增加可选的最小 Goal 状态，而不是继续放大聊天摘要

第一版只为显式长任务启用，不影响普通对话。

1. 新增最小 `GoalState`，只包含：`goal_id`、`objective`、`status`、`next_step`、`updated_at`
2. 新增追加式 `GoalCheckpoint`，只记录：本次有界运行的结果、成功工具或测试的证据引用、阻塞原因和下一步
3. Goal 记录与聊天 Message 使用不同 JSONL record type，但继续存放在当前 Session 文件中，避免增加数据库和双写事务
4. 恢复时通过顺序回放得到最新 GoalState；原始聊天仍完整展示，ContextManager 只把最新 Goal 投影放入系统上下文
5. 普通 chat 不自动创建 Goal；只有显式长任务入口才创建，避免把“一处改字母”变成任务管理流程
6. 每次 Agent 执行仍是有边界的一轮；只有成功写入检查点后，该轮才算长期目标的已记录进展
7. 目标完成或阻塞不能只依赖自然语言自述：完成证据只能引用当前 Session 中真实存在的成功工具/检查结果；缺少证据时保存为 active 或 blocked，不保存为 completed
8. 增加创建 Goal、写入检查点、进程重启回放、压缩后仍注入最新状态、聊天记录与 Goal 投影互不覆盖的测试

第一版不实现自动定时续跑、计算额度调度、多人任务认领、多 Agent lease、复杂 gate 或独立控制面服务。只有真实长任务证明最小状态不够时，再从 LoopX 中选择下一项能力。

## 四、验收顺序

### 第一阶段：正确性闭环

- 模型失败和用户取消后，JSONL 中不存在孤立 ToolCall
- 已经完成的工具结果不会因下一次模型请求失败而消失
- 失败工具不会被上下文摘要写成“已修改文件”
- 完整相关单元测试通过

### 第二阶段：并发与远程工具边界

- 同一 Session 不能被两个进程同时写入
- MCP Server 无响应不会永久卡住 Agent
- MCP 超长输出不能绕过统一限制
- 外部只读声明不能绕过本地审批策略

### 第三阶段：长任务恢复

- 普通对话行为完全不变
- 显式 Goal 可跨进程恢复 objective、status 和 next_step
- 压缩聊天历史不会删除最新 Goal 投影
- 已完成状态能够追溯到真实执行证据
- 中断后继续执行从最新检查点开始，而不是重新扫描完整聊天猜测进度
