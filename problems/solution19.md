# 第十九轮优化方案：可验证评测与可恢复工具回合

## 目标与边界

- 让 SWE-bench 结果反映真实修复能力，排除提交历史和隐藏答案泄漏
- 让模型可以分段读取文件，并在参数不合法时得到明确工具反馈
- 达到工具轮次上限后保留全部已完成消息和工具结果，不再静默丢失进度
- 不把评测限制混入正常用户工作区，不引入完整容器编排、通用权限引擎或复杂任务规划器

## 统一设计

```text
基准仓库基线
  ↓ 源码快照
隔离评测工作区（无 .git、无隐藏测试）
  ├── Agent 工具仅操作此目录
  └── Session 与日志写入工作区外
  ↓
AgentLoop
  ├── 分段 read_file / 严格参数校验
  └── 达到轮次上限 → 返回带 stop_reason 的本轮结果
                                  ↓
                           UI 持久化全部新增消息
                                  ↓
                         官方 Harness 在独立环境验证
```

## 设计依据

- 执行环境与审批策略应是命令调用的显式输入，而不是散落在工具实现中的命令黑名单
- 文件读取需要支持行级范围和明确的继续读取提示，避免大文件重复进入上下文
- 工具失败、取消或回合结束都应转换为可记录的消息，使后续模型请求和 Session 恢复拥有一致历史

## 问题一方案：评测运行器创建无历史源码快照

### 实施步骤

1. 在 `evaluation/` 中新增评测工作区准备函数，输入基准仓库路径与基线提交，输出临时工作目录
2. 使用 Git 的源码导出能力生成基线文件快照；不复制 `.git`、其他 Git 元数据、参考补丁、隐藏测试或之前的 Agent 产物
3. 将 Epsilon 的 `working_directory` 指向该快照目录，将 Session 根目录和运行日志指向评测结果目录，而不是任务目录
4. Agent 结束后只从快照目录生成补丁；官方 Harness 继续在它自己的容器中验证补丁
5. 评测任务启动前断言工作区不存在 `.git`，发现则立即标记为评测环境错误，不运行 Agent

### 边界

- 这是评测运行器职责，不修改正常 `run_command` 的能力边界
- 不维护 `git log`、`git show` 等命令黑名单；隔离输入比关键词过滤更可靠
- 本轮不实现通用 Docker 沙箱，官方 Harness 已负责验证容器；评测侧只负责提供干净的 Agent 输入目录

## 问题二方案：把分段文件读取做成严格工具契约

### 实施步骤

1. 为 `read_file` 的 Schema 增加可选 `offset` 与 `limit`：`offset` 为从 1 开始的行号，`limit` 为最多返回的行数
2. 工具先校验类型、正整数范围和字段名，再读取对应范围；无效参数返回 `ToolResult` 错误文本交给模型，不执行读取
3. 当文件还有未读取内容时，在结果末尾追加统一提示：已显示的行范围、文件总行数和下一次建议的 `offset`
4. 复用现有工具输出预算；范围读取在进入输出截断前生效，避免仅靠截断获得不完整的文件开头
5. 将校验层的未知参数从“忽略”改为“明确拒绝”，并确保所有本地工具共享此行为

### 测试

- 可按 `offset` 与 `limit` 返回正确行区间，并带有继续读取提示
- 省略两个参数时保持现有小文件读取行为
- 未知字段、非整数和非正数都返回可供模型理解的工具错误
- 大文件多次范围读取不会重复第一段

## 问题三方案：把工具轮次耗尽建模为可恢复停止结果

### 实施步骤

1. 将 AgentLoop 的执行结果增加 `stop_reason`，至少区分 `completed`、`cancelled` 与 `tool_limit`
2. AgentLoop 在每一条 assistant 消息、tool call、tool result 产生时持续追加到本轮 `new_messages`
3. 达到 `max_tool_rounds` 时停止发起下一次模型请求，返回 `stop_reason="tool_limit"` 和截至该时刻的全部 `new_messages`，不再用普通异常替代结果
4. `ui.py` 对任何可返回结果先持久化 `new_messages`；当 `stop_reason` 为 `tool_limit` 时，再展示并持久化一条明确说明，告知用户本轮因工具轮次上限结束
5. 保持模型请求、工具注册和 TUI 布局不变；本轮不自动额外请求模型生成总结，避免在已耗尽预算后再次扩大执行范围

### 测试

- 工具轮次上限触发后，结果包含本轮全部 assistant/tool 消息且顺序正确
- UI 能持久化这些消息，恢复 Session 后工具调用链完整
- 不会发起超过配置上限的下一次模型请求
- 正常完成、取消、模型错误的既有行为不回归

## 执行顺序

1. 实现问题二的分段读取与严格校验，减少真实任务的无效工具轮次
2. 实现问题三的可恢复停止结果，保证真实运行即使触顶也能留下可诊断数据
3. 实现问题一的隔离工作区，并用一条预检任务验证 `.git` 不可见、Session 不污染待测仓库
4. 再运行预检任务与完整 SWE-bench 任务，报告“环境有效性”和“任务结果”两个独立结论

## 验收标准

- 评测 Agent 工作区不含 `.git`，且 Session、日志、补丁产物均在工作区外
- `read_file` 支持稳定的行级分页；未知参数不会再被静默忽略
- 工具轮次耗尽后，Session 恢复可完整解释已执行的工具操作
- 预检任务与相关单元测试通过；官方 Harness 的结果能够明确标注为有效、环境无效或任务失败
