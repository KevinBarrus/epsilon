# 问题 20：工具回合预算与同批工具调度限制真实任务能力

## 问题一：交互会话存在固定工具回合上限

`AgentLoop` 当前使用 `for range(max_tool_rounds)` 执行模型—工具循环，默认值为 10。用户让 Agent 阅读较大项目并整理简历时，模型可能尚未完成信息收集就收到工具上限提示，必须依赖用户发送下一条消息才能继续。

真实 SWE-bench 运行虽然显式设置为 40 回合，但结果文件没有保存 Agent 的 `stop_reason` 与实际循环轮数。因此，无法区分“补丁本身不正确”和“任务在回合上限处被提前停止”，不能把当前通过率直接归因于上限。

## 问题二：同一模型响应中的工具调用严格串行

`AgentLoop` 对同一 assistant 消息中的每个 `ToolCall` 都立即 `await ToolManager.execute()`。因此多个互不依赖的文件读取、目录列举或搜索必须依次完成。

这不会减少固定模型回合数内可发起的工具调用数量，但会拉长单个回合的墙钟时间，增加命令超时、网络中断和用户等待；在有总时长预算的真实评测中也会间接降低有效探索量。

当前不能直接对所有工具使用 `asyncio.gather()`：写文件、编辑文件、命令和待审批工具可能存在顺序依赖、文件竞争或多个审批弹窗并发的问题。

## 问题三：评测缺少判断优化是否有效的运行轨迹

现有 SWE-bench 结果保存了模型请求数与工具调用数，但未保存工具回合数、停止原因、单批工具的并发数量和批次耗时。完成优化后无法用真实数据说明是否减少了等待、是否仍受轮次上限影响。
