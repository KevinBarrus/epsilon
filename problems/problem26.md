# 问题 26：写后验证把“命令成功”误当作“代码已验证”

## 一、问题背景：为什么要做容器时代烟雾测试

在第二十五轮优化后，SWE-bench 的补丁已不会被 `egg-info` 等运行产物污染，Agent 的命令也已在官方实例镜像中执行。为了确认这一新链路不只会得到“可信的失败”，还能得到真实正样本，选取三个此前未在容器环境中运行的 Django Lite 实例进行烟雾测试：

```text
django__django-12125
django__django-15902
django__django-11001
```

结果目录：

```text
evaluation-results/swebench-smoke/
```

最终结果为：

```text
swebench evaluation: 1/3 passed
```

这不是最终成功率，而是一项“小范围通电测试”：先确认新容器线路能够让模型改代码、交补丁、由独立裁判判对。

## 二、烟雾测试告诉了我们什么

| 实例 | 官方 Harness | Agent 本地验证 | 结果说明 |
| --- | --- | --- | --- |
| 12125 | 空补丁，未通过 | 不需要 | 40 轮后仍未形成代码修改 |
| 15902 | 补丁应用，未通过 | failed | 目标用例通过，但引入 2 个旧用例回归 |
| 11001 | 通过 | failed | Agent 达到 40 轮，但源码补丁被独立 Harness 判定正确 |

11001 的两个目标失败用例均已通过，证明容器评测链路可以产出真实正样本。15902 则说明“主问题测试通过”不等于“补丁正确”：它修复了目标用例，却破坏了两个原本通过的用例。

因此，官方 Harness 仍是补丁正确性的唯一裁判；Agent 自己的命令结果只是一条帮助下一步决策的局部证据。

## 三、从 13321 重新定位写后验证策略

在修复运行产物过滤后重跑 `django__django-13321`：

```text
Agent 修改 django/contrib/sessions/backends/base.py
  ↓
连续三次 run_command 退出码为 1
  ↓
执行 pip list，退出码为 0
  ↓
Agent 自然结束，verification_reminder_injected=false
  ↓
官方 Harness：337 个目标用例通过，18 个关键 decode/security 用例仍失败
```

这不是“模型已经验证代码正确”，而是“模型运行了一条能成功结束的环境信息命令”。`pip list` 能告诉模型安装了哪些包，却不能检查它刚修改的会话解码逻辑。

## 四、源码如何导致这个问题

当前 `WriteVerificationPolicy` 的核心逻辑是：

```python
elif tool_call.name == "run_command" and self._needs_verification:
    self._post_write_command_results.append(result)
    self._needs_verification = result.is_error
```

意思是：文件写入后，只要任意 `run_command` 的 `is_error` 为 `false`，策略就认定“不再需要验证”。它不读取命令参数，也不判断命令是否在运行测试、静态检查、构建或其他代码检查。

可以把它想成老师要求学生“改完答案后做一次验算”，但系统只检查学生有没有成功打开计算器：

```text
运行 pytest 并通过          -> 真的做了检查
运行 python -m py_compile   -> 至少检查了语法
运行 pip list               -> 只是打开计算器看型号
运行 pwd                    -> 只是确认自己在哪个房间
```

当前实现把后三种都当作“验算完成”。这就是验证语义过弱的问题。

## 五、问题定义

问题不是“本地验证必须通过”，也不是“模型自然结束必须禁止”。11001 已证明，本地命令失败时，补丁仍可能被独立官方裁判判对；15902 也证明，本地目标测试通过时，补丁仍可能存在回归。

真正的问题是：

> 当前收尾策略没有区分“检查代码的命令”和“查询环境的命令”，导致无关成功命令能够取消写后验证提醒；同时评测中的 `agent_verification_status` 只反映任意命令退出结果，不能准确表示模型是否尝试了有意义的检查。

## 六、影响

- 13321 一类任务可能在关键测试失败后过早结束
- 评测报告把 `pip list`、`pwd` 与测试命令同样计为本地验证，降低诊断价值
- 若直接把本地验证状态当作质量指标，会与 11001 的官方正样本相矛盾
- 若强制本地测试必须通过，又会让模型在环境限制或不完整测试选择下无谓循环

## 七、边界

- 不把 Agent 本地验证替代为官方 Harness
- 不要求每个任务都必须执行某一个固定测试命令
- 不让模型无限重试验证；每轮仍最多补充一次收尾提醒
- 不为评测专门修改生产工具的执行环境
- 不通过模型自我声明“我已测试”作为成功证据

## 八、面试表达

> 真实 SWE-bench 烟雾测试中，我发现“写后验证”不能只看命令退出码。一个模型在修复后连续得到失败结果，但执行 `pip list` 成功后，框架就允许它结束；这只是环境查询，不是代码验证。另一方面，另一个样本的本地验证失败、官方裁判却通过，说明我不能简单强制本地测试成功。最终我把策略收紧为：只把具有测试、静态检查、构建或语法检查语义的命令当作验证证据；是否真正解决任务仍只由独立 Harness 判定。
