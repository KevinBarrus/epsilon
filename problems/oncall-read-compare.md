# 只读汇总任务的多 Agent 对比（oncall）

**单次运行的描述性对照，不作统计推断。** 同一任务、同一副本内容、同模型
`deepseek-flash`（`thinking=high`）、同熔断（40M token / 60 分钟每档）。

## 一、三档定义

| 档 | arm | 内容 |
|---|---|---|
| A | `single` | 单 Agent 串行读 |
| B | `fanout_fresh` | fresh Scout 扇出并行读（各读不相关分区，不共享上下文） |
| C | `map_then_fork` | 父先做项目测绘 → **fork** Scout 继承项目图后深读 |

B 与 C 是核心对照：同一任务、同样扇出，**唯一差别是子 Agent 是否继承父上下文**。

## 二、结果

| 档 | token | 墙钟 | 文档级覆盖率 | **源码级覆盖率** | **精确率** | 读调用 | 子 Agent 缓存命中 | 工具错误 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A `single` | 3,616,222 | 176s | 10/12 | **5/6** | 0.9455 | 67 | — | 4 |
| B `fanout_fresh` | **3,018,936** | 154s | 9/12 | **5/6** | **1.000** | 156（子 141） | 0.9167 | 7 |
| C `map_then_fork` | **9,638,365** | 378s | 9/12 | **5/6** | 0.9865 | 177（子 125） | **0.9537** | 17 |


> ⚠️ 指标效度提示：本节引用的"源码级覆盖率"基于**任意挑出的源码事实清单**，
> 命中主要反映运气与报告篇幅，**不得单独支撑结论**（见 design/evaluation.md 第十四节）。
> 本节中仅依赖该指标的判断视为**未证实**。

相对倍数（首轮）：**B = 0.83× A**；**C = 2.67× A = 3.19× B**。
⚠️ **A 与 B 已重跑验稳，方向相反**（见第五节）；C 未重跑，但其幅度远大于运行间噪声。
三档都缺同一项源码题（`source_evidence_table`），文档级差在 `memory` / `argon2` / `explainability`。

## 三、结论（按规定的口径）

1. **在 20k 行 / 57 文件、单 Agent 176 秒就能全读的语料上，扇出读没有覆盖率优势。**
   三档源码级覆盖率都是 **5/6**，差的还是同一项；扇出读**读了更多**（A 67 次 → B 156 次 → C 177 次）
   却没有覆盖到任何新东西。
2. **本次能验证的是 fork vs fresh（B vs C）**（这条对照不依赖覆盖率天花板）：
   - 覆盖率：**相同**（都是 5/6）；
   - token：**C 是 B 的 3.19×**（子 Agent 6.04M 对 2.25M）——fork 的代价是每个请求都要重发继承前缀；
   - 缓存：fork 子 Agent 的缓存命中率确实更高（**0.9537 对 0.9167**，+3.7pp）——机制生效，
     但**远不足以抵消重发量**；
   → **fork 在本任务上不划算**：买到了更高的缓存命中，却付出数倍 token，覆盖率零回报。
   （精确率 B 1.000 / C 0.9865 的排序**不作结论**：重跑后 A/B 的精确率排序都不稳定。）

> ⚠️ 指标效度提示：结论 1、2 里的"源码级覆盖率都是 5/6""覆盖率零回报"基于**任意挑出的 6 条源码题**，
> 命中主要反映运气与报告篇幅，**不得单独支撑结论**（见 design/evaluation.md 第十四节）。
> 例外：结论 2 中 **token 3.19×** 与 **缓存命中率** 不受影响，继续有效。

3. **"扇出读能不能提高覆盖率"这个问题在本语料规模下不可回答**，需要更大的语料才能测。
   只有当语料大到"单 Agent 的上下文 / 预算成为约束"时，扇出读才可能出现覆盖率优势。
4. **A 与 B 的 token 差异没有稳定结论**：首轮 B 更省（0.83× A），重跑 B 更贵（2.67× A），
   方向相反；而且同一档自身两轮之间就波动 **1.9×（A）/ 1.7×（B）**，与 A/B 之间的差距同量级。
   → **单次运行测不出 A 与 B 的 token 差异**（详见第五节）。

## 四、站得住的三条结论与各自的证据强度

（这三条才是本次可用的产出；其余数字都带噪声，见上文。）

### ① 多 Agent 在"需要共享上下文"的任务上必然更贵 —— 结构性论证

fresh 子 Agent 拿不到父的上下文 ⇒ 每个子 Agent 都必须重建同一份项目理解 ⇒ 重复支付无法避免。
实测三轮方向一致：共享档 **1.76×**、worktree v1 **3.60×**、worktree v2 **3.60×**，
且多 Agent 侧被 120M 熔断封顶，实测值是**下界**。

**证据强度**：结构论证 + 三次运行方向一致 + 熔断下界，三重支撑。
⚠️ 诚实标注：重构侧基线（33.3M）也是 **n=1**，严格说仍带噪声；它比读任务稳，靠的是结构与下界，
不是样本量。

### ② fork 不划算 —— 效应量大，单次成立

同一扇出下 **C = 3.19× B**、覆盖率零回报（都是 5/6）。缓存确实继承上了
（子 Agent 命中率 **0.9537 对 0.9167**，+3.7pp），但抵不过重发量。
这正是"**fork 不是免费的**"的实证：它把"重读成本"换成了"重发成本"，在这个语料上换亏了。

**证据强度**：效应量 3.19× 远大于运行间噪声（≈1.7×）→ 单次即可定论。

### ③ 方法论 —— 本次最大收获

- 小场景里 token 噪声能盖过信号（微基准警告过一次，oncall 重跑正式坐实）；
- **任务描述不得泄露评分标准**（A 档源码级覆盖率因此从 2/6 被抬到 5/6）；
- **天花板是语料规模，不是题难度**；
- 单次对比会产出可被翻转的结论。

以上已提炼为可复用规范：`design/evaluation.md` 第十三节《对照实验规范》。
并附一条功效估算：σ ≈ 0.29 时，20% 的差异要跑 ≈ 42 轮（约 250M token），
所以"加大语料 + 多轮重复"这条路**在成本上不可行**，不应再走。

## 五、机制假说与验稳结果：A vs B 的 token 差异测不出来

### 4.1 机制假说（第一性）

首轮出现过一个反直觉现象：B 多读了 **2.1 倍**的内容（156 次对 67 次），token 却更少
（3,018,936 对 3,616,222）。它若成立，说明：

> **token 的主导项不是"读了多少内容"，而是"一个上下文被重复发送了多少次"。**

而单个上下文的总 token 随轮次是**二次增长**的：每轮都要把到目前的上下文重发一遍，
上下文长度线性增长 × 轮次线性增长 = 二次。于是

- **A**：一份大上下文从 0 长到 S、发 85 轮 → 约 `85 × S / 2`；
- **B**：父上下文小（只读 15 个文件）+ 4 个 Scout 各持约 `S/4` → 二次项被摊薄到几份小上下文上。

这是一个**机制假说**，不是结论。

### 4.2 验稳：没有复现（这次实验最重要的负面结果）

按要求重跑了 A 与 B 各一次：

| 轮次 | A token | B token | B / A | A 文档级 / 源码级 | B 文档级 / 源码级 |
| --- | ---: | ---: | ---: | --- | --- |
| 首轮 | 3,616,222 | 3,018,936 | **0.83×** | 10/12 / 5/6 | 9/12 / 5/6 |
| 重跑 | 1,881,797 | 5,032,857 | **2.67×** | 9/12 / **6/6** | 9/12 / 5/6 |

- **两轮方向相反**，`B ≤ A` 没有复现；
- **同一档自身的轮次间波动更大**：A 1.88M ~ 3.62M（**1.9×**）、B 3.02M ~ 5.03M（**1.7×**）——
  与 A/B 之间的差距同量级；
- 精确率同样不稳（A 0.9455 / 0.9828，B 1.000 / 0.9535），**无法排序**；
- 源码级覆盖率 A 一次 5/6、一次 **6/6**，说明**单 Agent 能把这份语料读满**。

**结论**：本次数据**既不能支持、也不能否定**"扇出读更省 token"；只能说
**在本实验的样本量下，A 与 B 的 token / 精确率差异被运行间噪声淹没**。
机制解释（二次增长、摊薄）作为"为什么有可能发生"仍然成立，但**缺少实测支撑**。

（方法论价值：这与微基准的教训一致——**小场景里 token 噪声能盖过信号**。要测这类差异，
需要多轮重复 + 报告区间，而不是单次对比。）

## 六、"上下文边界"假说：两侧证据强度不同

原设想是用两个任务双向验证"按上下文边界拆分"：

| 任务 | 上下文能否切成互不重叠的几份 | 多 Agent 的 token |
| --- | --- | ---: |
| 重构任务（写代码） | ❌ 每个 Worker 都必须重建同一份项目上下文 | **3.6× 更贵**（多次运行方向一致） |
| 读任务（oncall 汇总） | ✅ 4 个 Scout 读互不重叠的分区 | **未获稳定证据**（0.83× / 2.67×，方向相反） |

**如实标注：这个"双向验证"目前只有一侧站得住。**

- 重构侧：多 Agent 更贵是**多次运行方向一致**的（共享档 1.76×、worktree 档 2.52×~3.60×），
  机制也清楚（每个子 Agent 必须重建同一份上下文）；
- 读任务侧：**本次没有测出稳定差异**，因此不能拿它去印证"可切分就更便宜"。

所以"按上下文边界拆分"目前是**一个机制上合理、但只被单侧实测支持的假说**。
要补上另一侧，需要更大的语料（让"切分"真的省下不可忽略的量）与多轮重复。

## 七、这次实验的两个方法论教训

1. **任务描述泄露了评分标准**：最初把 6 道源码题写进任务后，A 档源码级覆盖率从 2/6 抬到 5/6，
   区分度被自己砍掉。预注册的本意是"评分标准不告诉被试"，不该把清单当任务发下去。
2. **但真正的限制是语料规模，不是题难度**：换更硬的题也没用——搜索空间仍是那 57 个文件，
   单 Agent 照样能扫完，只会再次出现"基线逼近满分"。**天花板是语料规模。**

## 八、后续可做的阳性对照（方向）

要真正测出扇出的价值，任务形态要从"读得深"换成"**产出多**"：例如为 `super_ai` 的 57 个模块
各写一份独立文档（或各写一组测试）。那才是可分解、输出量大、子任务彼此独立的场景——
也就是"context boundary"之外的第二个正确边界：**交付物边界**。
