# 驱逐实验复盘：为什么"驱逐净收益"这一轮是负的

> 记录一次真实的长任务对照实验（E0 vs E1）。负结果比正结果更值钱，本文只写实测数字，不修饰。

## 一、背景：为什么做这个实验

主表 B/C（`problems/main-table-report.md`）证明了两件事：

1. 防火墙对 token 的收益只有 2~3%，不是主杠杆；
2. **驱逐在单 bug 短任务里全程零触发**——默认阈值是 `compaction_threshold // 2 = (100000 - 16000) // 2 = 42000` token，而单个 bug 任务单次请求上下文始终到不了。

于是把问题转成：**在"上下文自然积累"的长任务里，驱逐的净收益是正还是负？**
设计见 `problems/problem29.md`：同一 Session 依次跑 T1 修 bug、T2 补测试、T3 重构，两档对照。

## 二、问题：阈值设太低，驱逐反复触发

E1 沿用"能触发"的想法，把驱逐阈值调到 **20000 token**。结果：

- 整个三阶段任务触发 **51 次**驱逐（T1 就 39 次）；
- 每次驱逐改写历史里的旧工具输出 → 公共前缀被改写 → **DeepSeek 前缀缓存反复失效**；
- 三阶段全部完成（3/3），但累计 token 反而大幅上升。

离线回放 E0 轨迹（无驱逐）确认了触发频率与阈值的关系：

| 驱逐阈值 | 三阶段内触发次数（E0 轨迹离线模拟） |
|---|---|
| 20,000（E1 实际用的） | 26 |
| 24,000 | 19 |
| 28,000 | 15 |
| 32,000 | 9 |
| 38,000 | 6 |
| **40,000** | **2** |
| 41,000 | 2 |
| **42,000（默认值）** | **2** |
| 43,000 | 0 |

E0 三阶段的上下文峰值（`estimate_model_request_tokens`，含长任务固定工具集与系统提示词）：

| 阶段 | 峰值 estimated_tokens |
|---|---|
| T1 | 27,841 |
| T2 | 33,383 |
| T3 | 42,717 |
| 全局 | **42,717（T3 末条消息）** |

也就是说：20k 阈值远低于 42.7k 的峰值，任务中后段一路在阈值上方反复穿越，才导致 51 次触发。

### 3.3 go/no-go

判据（`problems/problem29.md`）：E1 累计 token ≤ E0 的 85% 且三阶段全过 = 净收益为正。

- 实际：1,862,158 ÷ 1,134,610 = **164%** ≫ 85%
- **判定：净收益为负。**
- 按缓存命中约 1/10 计价的成本代理：E0 ≈ 178k，E1 ≈ 642k，**约 3.6 倍**。

## 四、结论与根因

**结论：净收益为负。** 省下的"重发旧工具输出"远不足以抵消前缀缓存失效的损失。

**根因不是"驱逐机制注定亏"，而是两个设计参数问题：**

1. **阈值太低（20k）**：远低于该任务 42.7k 的自然峰值，导致反复穿越、反复触发；
2. **每次只降到"刚好低于阈值"（渐进驱逐）**：`_maybe_evict` 从最旧的完整工具输出开始逐条降级，一旦估算回到阈值以内就停手。这保证了"前缀只在边界断一次"，但阈值被压得很低时，上下文很快又长回阈值上方，于是再次断前缀——**51 次触发 = 51 次缓存断裂**。

佐证：E1 的 `cache_hit_rate` 从 93.7% 掉到 72.8%（−20.9 pt），未命中 token 从 7.2 万涨到 50.7 万（7 倍）。缓存失效是成本上升的直接来源，而不是 artifact 取回——两档 `artifact://` 取回次数都是 0。

同时注意：两档压缩次数都是 0，所以"驱逐替代压缩"这条假设本轮**没有被检验**（E0 的上下文峰值本来就没到 84k 压缩线）。

## 五、对照 oh-my-pi

| 维度 | oh-my-pi 的 shake | 我们的实现 | 差距 |
|---|---|---|---|
| 触发时机 | **接近窗口极限才触发** | 固定取压缩阈值的一半（默认 42k，E1 用 20k） | 触发点太低，容易反复穿越 |
| 收益门槛 | **`minSavings: 4000`**（省不到 4000 token 不动手） | 无门槛，够阈值就驱逐 | 小额度驱逐也照做，白白断缓存 |
| 最近内容保护 | **保护最近 16000 token** | 只保护最近 10 条工具输出（`KEEP_RECENT_TOOL_OUTPUTS = 10`） | 保护口径是"条数"而非"token 预算"，长输出下保护不足 |

结论：三条差距都指向同一个方向——**要么不动，要么一次动到位**；我们的实现是"动得很频繁、每次动一点点"。

## 六、后续方向

1. **阈值调高**：离线扫描显示 40000~42000 可把三阶段触发压到 2 次（20000 是 26 次）。默认值 42000 本身已经接近合理，20k 是有害的；
2. **一次降到位、留缓冲**：触发后不要停在阈值边缘，而是一次多降（例如降到阈值的 60~70%），避免"刚降完又马上触发"；
3. **加 `minSavings` 门槛**：估算要省下的 token 低于门槛（参考 4000）就不驱逐，避免为微小收益打断缓存；
4. **保留"驱逐替代压缩"的独立验证**：本任务峰值 42.7k，离 84k 压缩线太远；要在更长的任务（或更低压缩阈值）里才能观察两者关系。
