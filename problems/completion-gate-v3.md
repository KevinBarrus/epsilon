## 一、门确实逼出了"真读"，但没逼出"我们要的那些事实"

修复接线后的这一跑，模型最终产出的报告**深度是真的**（离线复核，0 成本）：

| 诊断项 | 值 |
| --- | --- |
| 反引号标识符候选 | **285 个，其中 282 个真实存在**（编造仅 3 个） |
| 类别分布 | constant 61 / type 98 / function 123 |
| 真实路径 | 53/53 存在（attempt 1 时是 27/109，大量编造成 `1.1`、`mcp.rs`、`protocol.rs` 等） |
| 5 类问题 | 仅 `protocol` 节缺「失败模式」一段 |

也就是说：**模板确实逼它去真读代码并引用真实符号**（282 个真实标识符不可能靠编），
**但那 9 条隐藏清单事实，它基本没命中（只 4 条）**。

→ 这一条比覆盖率数字更重要：
**「回答了哪几类问题」≠「找到了我们测量的事实」。**
模板能约束**形状**（有职责/交互/结构/参数/失败模式，且都引了真实代码），
但**约束不到"具体是哪些常量、哪些阈值、哪些失败码"**——而这些正是清单在测的东西。

## 二、这条负面结果指向的更根本问题（本步最有价值的产出）

**覆盖度本身能不能被自动检查？**

- 能脚本化的只有**通用结构**：某节存在、引了 N 个真实标识符、引用的是真实路径、没有编造；
- 要脚本化**"有没有答到那 9 条事实"**，就必须在 criteria 里**点名那 9 条**——而 criteria 会随拒绝反馈回注给模型，
  **点名即泄露**，测量仪器当场失效。

结论：**在"不泄露"的前提下，覆盖度无法进门的 criteria。**
它只能继续当"模型看不见的测量仪器"。
这是**完成门这条路线的边界**——知道边界在哪，比多一个漂亮数字值钱。

（除非接受另一种代价：把清单公开、让它从"测量仪器"变成"任务书"。
那样覆盖率当然会上去，但测的就不再是"自主阅读的深度"，而是"照单执行"。这是另一个产品选择，不是同一个实验。）

## 三、顺带暴露的三个实现问题（已修）

1. **UNMET 解析漏掉最自然的格式**（真 bug，影响所有跑）：
   验证器实际写的是 `VERDICT: not_met UNMET:` 换行后跟多条 `- 条目`。
   原实现只在**含 marker 的同一行**里找条目，导致 `unmet` 被解析成空清单
   （拒绝消息退化成"验证器未给出结构化未满足项"）。
   已重写为状态机（三种格式：同行内联 / marker 行尾 + 多行条目 / marker 独立成行），
   并补 3 条回归测试。
2. **模板的 5 个问题名没被任何检查声明覆盖** → 被当成"无脚本证据"→ 验证器被指示判 inconclusive
   → **一份 5 项检查全过的报告也无法通过**（第一跑 1,575,393 token、1/9 就是这么来的）。
   已让 `covers` 支持列表，并补"模板每一行 criteria 都必须被覆盖"的测试。
3. **核验上限（200 次）与"报告越厚越不可验证"的张力**（真实现象，未改口径）：
   最终报告的候选标识符是 285 个，超过上限 → `identifiers_per_section` 判 **UNVERIFIED**。
   离线放开上限重算即 **PASS**（0 成本复核）。
   本步**不改上限**——上限是"验证可行性"参数，但事后调它就会变成调判定口径。
   如实记录：**模型越详尽，越容易被"核验不完"挡在门外**，这是模板路线的一个固有摩擦。

## 四、门在这一跑里确实做了事（但只到"形状"为止）

三次声明的演进（同一跑内，来自 `goal.jsonl`）：

| 声明 | 检查结果 | 验证器判定 |
| --- | --- | --- |
| 第 1 次 | 3 节 0/3 标识符、`protocol.rs` 等大量编造路径（27/109 真实） | `not_met` |
| 第 2 次 | 仍是 0/3，路径已收敛 | `not_met` |
| 第 3 次 | 285 个候选、282 真实、路径 53/53；仅 `protocol` 缺「失败模式」；标识符核验超上限 | `not_met`（一条真缺口 + 一条未证实） |

→ 门**拦住了编造**、**逼出了真实引用**，但**没能把"我们关心的 9 条事实"逼出来**。
且这两次拒绝的代价是 4.4M token（基线 0.52M）。
