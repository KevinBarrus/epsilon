# 第十七轮优化方案：带样式的行内历史与尺寸重排

## 目标与边界

- 已完成消息写入终端主屏幕回滚区后，仍保留用户灰色背景、Markdown、代码颜色和工具样式
- 终端尺寸变化后，以短暂刷新重建 Epsilon 自己写入的回滚历史，消除输入框边框残影
- 保持终端原生滚动、缩放、选区复制、输入框、状态栏、审批和 Slash Command 的现有职责
- 不恢复全屏模式，不重新启用鼠标上报，不修改 Agent Loop、Session、工具、上下文和持久化逻辑
- 本轮不加入历史行数上限或分页加载；先保证当前内存会话能正确重排，超长会话性能根据真实测量另行处理

## 统一设计

稳定对话不再在写入终端时降级为纯字符串。`ConversationEntry` 继续保存角色、原始内容和工具样式，作为当前运行期间唯一的展示来源；终端回滚区只是该来源在某个终端宽度下的带 ANSI 样式渲染结果。

```text
ConversationEntry（原始内容、角色、样式）
    ├── 活动条目 → prompt-toolkit 底部视口，可被流式重绘
    └── 已提交条目 → 终端历史渲染器 → 带 ANSI 样式的主屏幕回滚区
                                               ↓
终端尺寸变化 ── 75ms 防抖 ── 清空当前终端缓冲区 ── 从已提交条目重新渲染
```

终端协议无法只删除“Epsilon 写入的行”。本方案在重排时会清空当前终端的可见区和回滚区，再重建本次 Epsilon 会话的展示；因此进入 Epsilon 前留在同一终端中的 shell 输出不再可回滚查看。会话数据不受影响：重排依据是内存中的 `ConversationEntry`，退出后的恢复依据是 Session 持久化，而不是旧终端行。重排完成后，用户仍可通过终端原生滚动查看完整的本次对话。

## 问题一方案：历史用户消息保留灰色背景

### 实施步骤

1. 将 `InlineHistory` 替换为终端历史渲染组件，禁止调用 `to_plain_text()` 后直接 `print()`
2. 终端历史渲染组件接收已提交的 `ConversationEntry`，按角色产生与活动视图一致的格式化片段：
   - 用户消息：上下留白、左右留白和 `conversation-user` 灰色背景
   - 助手消息：Markdown 格式化片段
   - 工具消息：已有 pending、success、error 与 diff 样式
   - Logo：保持现有居中与主题颜色
3. 用户消息按当前终端列宽预换行，每一个可见行补齐到行宽后再应用背景色；这样自动换行后的每一行、上下留白行都处于同一灰色背景内
4. 使用 prompt-toolkit 的样式输出能力把格式化片段写入主屏幕，输出时携带当前 `Style`，不在历史写入链路中丢失颜色信息
5. 已提交条目仍保持“只输出一次”的语义；重排是唯一允许再次输出全部稳定条目的路径

### 分层边界

- `screen.py`：维护条目生命周期，决定何时提交和请求重排
- 新增终端历史渲染模块：只负责“条目 → 当前宽度下的 ANSI 终端行”和写入
- `theme.py`：继续是颜色唯一来源
- `ui.py`：继续只产生用户、模型和工具事件，不了解 ANSI、换行或缩放

### 验收

- 新消息、恢复会话、缩放后的历史用户消息均带灰色背景
- 向上滚动时可清楚区分用户消息和模型输出
- 用户消息包含中文、Markdown 和多行文本时，背景仍覆盖完整消息块

## 问题二方案：统一 Markdown 输出并限制流式重绘频率

### 实施步骤

1. 将助手消息 Markdown 渲染统一为同一份格式化结果：活动视图和终端历史均调用同一渲染入口，禁止稳定历史走纯文本降级分支
2. 代码块、表格、标题、列表、引用、行内代码和 Pygments 语法颜色通过 ANSI 样式输出到终端历史，保证流式完成前后的展示语义一致
3. 对 prompt-toolkit 应用设置 `1/60` 秒最小重绘间隔，合并同一帧内的多个流式分片；模型事件仍立即累积内容，只是屏幕最多约每 16ms 重绘一次
4. 为 Markdown 渲染入口增加“流式中”状态：
   - 未闭合代码围栏内只使用基础代码样式，不运行 Pygments 全量高亮
   - 代码围栏闭合或助手回复完成后，再对完整代码块执行一次语法高亮
   - 表格继续随着完整行到达而展示，使用重绘合帧控制频率，不等待整段回复结束
5. 助手条目提交时以最终 Markdown 渲染结果写入历史；因此代码高亮、表格布局和普通 Markdown 都不会在提交后消失
6. 不引入第二套 Markdown 语法或异步解析器，继续复用现有 `markdown.py` 和已安装的 Pygments

### 验收

- 长代码块流式到达时，界面持续更新且输入、Esc 取消不明显卡顿
- 代码块闭合后，关键字、字符串、注释等已有颜色正确展示
- 表格逐行到达时保持可读，不在最终提交后退化为原始 `|` 文本
- 终端回滚区中的 Markdown 样式与活动视图一致

## 问题三方案：修复代码块重复换行

### 实施步骤

1. 调整 `render_markdown()` 的逐行状态机：代码块开始符、代码内容、结束符都由代码块分支独占处理
2. 当解析器处于代码块内时，不再由外层普通行逻辑追加换行；换行仅由 `_render_code_block()` 根据实际代码行生成
3. 代码块开始符和结束符不作为普通文本行再次追加换行
4. 保留模型原始代码中的前导空格、空行和尾部换行；修复只移除渲染器重复制造的空白
5. 覆盖完整围栏、未闭合流式围栏、空代码块、代码块后接正文和连续代码块五种输入

### 验收

- ` ```python` 与第一行代码之间不再出现额外空行
- 未闭合代码块在流式过程中不跳动、不累积空白
- Python、JavaScript 和未知语言代码块的缩进内容保持原样

## 问题四方案：尺寸变化后的终端历史重排

### 实施步骤

1. 新增独立的重排协调组件，只保存以下运行时状态：最近观察到的终端尺寸、最近成功重排的尺寸、等待中的重排任务，以及“流式期间发生过尺寸变化”标记
2. 在每次界面绘制前读取终端行列；首次读取只初始化状态，宽度或高度变化才请求重排
3. 尺寸变化采用尾部 75ms 防抖：连续缩放只在终端停止变化后重排一次，避免缩放过程多次清屏造成明显闪烁
4. 重排执行时：
   - 暂停 prompt-toolkit 活动界面输出
   - 通过终端清屏和清回滚序列清空当前可见区与回滚区；该操作会一并移除本次应用启动前的 shell 输出
   - 按最终终端宽度重新渲染全部已提交条目，并以带样式的终端行重新写入
   - 重置 prompt-toolkit 的渲染缓存，恢复底部活动条目、输入框和状态栏
5. 流式回复、working、spinner 和执行中的工具不属于已提交历史，缩放时由底部活动界面按新尺寸正常重绘
6. 若流式期间发生尺寸变化，在当前回复或工具条目提交后强制进行一次立即重排，确保临时宽度下的输出不会残留为最终历史
7. 重排期间禁止普通历史输出与重排输出交叉写入；待写入的已提交条目统一并入本次重排，避免重复或遗漏
8. 不改变 Ctrl+滚轮、触摸板滚动和鼠标选区的处理权；应用仍不启用鼠标上报

### 失败处理

- 无法读取终端尺寸时跳过本次重排，保留现有输出，不影响会话和模型请求
- 终端写入异常只显示简短状态提示，不清空 `ConversationEntry`；下一次尺寸变化可重试
- 重排任务被新的尺寸变化替代时取消旧任务，仅保留最后一次稳定尺寸的任务

### 验收

- 连续 Ctrl+滚轮缩放时只有短暂刷新，不出现横线累积
- 缩放结束后输入框始终恰好有一条上边框和一条下边框
- 缩放后用户仍可向上滚动查看本次完整对话，且历史样式、换行与当前宽度一致
- 流式回复中缩放、工具执行中缩放、审批界面中缩放后均不丢失输入框、状态栏或历史消息
- Ctrl+D 退出后仍保留最后一次重排后的对话和既有用量、恢复指引
- 已知边界：触发重排后，进入 Epsilon 前的 shell 回滚输出不会保留；本次 Epsilon 对话会被完整重建

## 测试计划

- 历史渲染：用户灰色背景、助手 Markdown、代码颜色、工具成功/失败样式、Logo 与恢复历史顺序
- Markdown：代码块无重复空行、未闭合围栏、闭合后高亮、表格流式行
- 流式性能：大量小分片只触发受限频率的界面重绘，最终内容完整
- 重排协调：首次尺寸观察不重排、连续尺寸变化合并为一次、宽高变化都触发、旧任务被新尺寸替换
- 重排结果：清除后按当前宽度重新输出所有稳定条目，活动条目不进入回滚区，提交后可进入
- 流式交叉：流式期间缩放、回复提交后最终重排、工具执行期间缩放
- 回归：Slash Command、审批、选择器、输入历史、`↑ n more`、状态栏、工具展开、取消、恢复会话、Session 持久化
- 手动终端验证：长用户消息、长 Markdown 回复、代码块、表格、连续放大/缩小、触摸板回滚、Ctrl+D 退出
