# 问题 31：LayerFS 隔离工作区实验

本文档描述问题 30 第二版完成后进行的 LayerFS 隔离工作区实验。实验的目标是验证 LayerFS 能否让多个 Worker 在互不污染的工作区中并行修改代码，并量化它对正确率、总耗时、Token、磁盘占用和运行稳定性的影响。

本实验不预设 LayerFS 一定优于共享工作区。只有实验结果证明收益大于接入和运行成本，才考虑将它加入 Epsilon 的正式运行时。

## 一、实验位置

问题 30 第二版仍按已经确定的方案完成：

- Scout 只读并行；
- Worker 和 Reviewer 在共享工作区中串行执行；
- 所有写操作和命令继续经过用户审批；
- 不依赖 LayerFS。

完成第二版并得到稳定基线后，再开始本实验。这样可以把“多 Agent 本身的变化”和“LayerFS 隔离工作区的变化”分开，避免同时改变两个因素后无法解释结果。

## 二、要回答的问题

实验主要回答以下问题：

1. 多个 Worker 能否从同一个代码快照创建互相隔离的可写工作区？
2. 一个 Worker 的修改、删除、命令产物和失败状态是否会污染其他 Worker？
3. 每个 Worker 的结果能否形成独立、可查询、可追溯的 Branch 和 Commit？
4. Reviewer 能否在多个候选结果中选出通过验证的版本？
5. 胜出结果能否可靠地进入最终临时工作区，而不覆盖无关文件？
6. 并行候选 Worker 是否提高任务正确率或缩短获得正确结果的时间？
7. Workspace 创建、物化、Commit 和清理的成本是否抵消了并行收益？
8. LayerFS 增加的依赖、环境要求和失败模式是否在 Epsilon 可接受范围内？

## 三、第一阶段只做候选方案择优

LayerFS 可以保存多个 Branch 和 Commit，也会在分支头变化时拒绝静默覆盖，但当前公开 CLI / SDK 没有通用的兄弟 Branch 自动合并接口。`HeadMoved` 表示提交条件不再成立，不等于自动完成合并。

因此第一阶段不让多个 Worker 分别实现不同子任务后再自动合并，而是让它们从同一个快照出发，独立尝试完成同一个任务：

```text
同一个基础快照
  ├── Worker A → Branch A → Workspace A → Commit A
  ├── Worker B → Branch B → Workspace B → Commit B
  └── Worker C → Branch C → Workspace C → Commit C
                                      ↓
                         Reviewer 验证并选择候选
                                      ↓
                         在新的临时工作区复现胜出结果
                                      ↓
                              独立测试最终结果
```

这种方式不需要跨分支合并，能够先验证隔离、多候选并行和可追溯历史的价值。如果以后确实需要组合多个 Worker 的修改，再单独设计合并实验。

## 四、实验前置条件

### 4.1 Epsilon 前置条件

开始实验前，问题 30 第二版必须满足：

- Scout、Worker、Reviewer 的角色和工具边界已经实现；
- 单个 Worker 可以在共享工作区完成修改和验证；
- Reviewer 可以独立检查修改；
- 子 Agent 的取消、超时和工具轮次上限有效；
- 父 Agent 能记录各子 Agent 的实际 Token、耗时和最终摘要；
- 全量单元测试通过；
- 已保存至少一个不使用 LayerFS 的长任务运行结果，作为初始基线。

如果第二版本身不稳定，不开始 LayerFS 实验。

### 4.2 LayerFS 版本边界

实验固定使用 LayerFS 仓库根目录下的 v0.1.6 参考实现或另一个明确固定的提交，不使用仍在迁移中的 `core/` 作为工作区运行时。

每次实验记录：

- LayerFS 来源路径；
- 版本或提交标识；
- `layerfs --version` 输出；
- 构建命令和构建结果；
- Epsilon 版本、模型配置和实验配置。

LayerFS v0.1.6 是源码发布，实验机必须具备 Rust 工具链并提前构建 CLI。构建不计入单个任务的运行时间，但必须在实验报告中单独记录。

### 4.3 环境检查

正式对照前先检查：

- 操作系统和 CPU 架构；
- LayerFS CLI 能否正常启动；
- 临时目录和 Store 所在磁盘的剩余空间；
- 是否存在 `/dev/fuse`，当前用户是否有使用权限；
- 工作区是否只能使用 `materialize` 投影；
- 异常退出后是否残留 Workspace、后台 owner、挂载点或临时目录。

当前 WSL2 环境没有可用的 `/dev/fuse`，第一轮默认使用 `--projection materialize`。因此第一轮只能验证逻辑隔离、历史和并行候选，不能直接宣称获得了 FUSE 工作区的低复制成本。

### 4.4 最小可行性验证

在接入 Epsilon 之前，先单独完成以下流程：

1. 从一个小型代码目录初始化 Store 和 LayerStack；
2. 从同一基础 Layer 创建两个 Branch；
3. 创建两个物化 Workspace；
4. 在两个 Workspace 中修改同一个文件为不同内容；
5. 确认两个 Workspace 互不可见；
6. 分别 Commit，并查询两个 Branch 的历史和差异；
7. 在其中一个 Workspace 运行测试；
8. 将选中的候选结果应用到一个新的临时最终工作区；
9. 重新运行测试，确认结果与候选一致；
10. End 所有 Workspace，确认没有残留运行时资源。

任何一步无法稳定完成，就停止正式对照实验，先记录问题，不在 Epsilon 内增加补丁式绕过。

## 五、现实边界

### 5.1 LayerFS 不是安全沙箱

LayerFS 提供文件状态隔离和提交一致性，不限制 Agent 进程访问网络、工作区外路径、CPU 或内存。Worker 的命令仍然使用 Epsilon 现有审批机制，不能因为运行在 LayerFS Workspace 中就自动放行。

### 5.2 不提供强崩溃持久性保证

LayerFS v0.1.6 面向本地开发和评估，不承诺进程崩溃、系统崩溃或断电后的强恢复。实验中的“安全提交”只表示：

- 已发布 Commit 不可变且可查询；
- 条件更新可以防止静默覆盖分支头；
- 不同 Workspace 的未提交修改互相隔离。

它不表示备份、灾难恢复或安全边界。

### 5.3 物化投影可能产生复制成本

Branch fork 和内容寻址对象可以复用存储，但 `materialize` 仍要把可见文件写到普通目录。大仓库的 Workspace 创建时间和临时磁盘占用可能很高，必须实际测量，不能把 LayerFS 的内部去重直接等同于“整个工作区零复制”。

### 5.4 暂不自动合并多个候选

第一阶段只选择一个完整候选，不组合多个 Branch。发生以下情况时不自动处理：

- 两个候选都只完成了一部分任务；
- 希望把不同候选的文件拼接成一个结果；
- 分支头变化并返回 `HeadMoved`；
- 候选之间修改同一路径但语义不同。

这些情况单独计入“无法自动集成”，不能把人工处理后的结果算作自动成功。

### 5.5 Python 接入只能先走 CLI

Epsilon 是 Python 项目，LayerFS 的正式 SDK 是 Rust 接口。第一轮通过固定版本的 CLI 子进程接入，不开发 Python 绑定、不复制 LayerFS 内部实现。

CLI 的部分 JSON 结果仍是文本预览，不是稳定的强类型机器接口。因此实验适配器必须：

- 固定 LayerFS 版本；
- 检查进程退出码；
- 严格校验 Workspace、Branch、Commit 等标识；
- 明确识别 `Created`、`UpToDate`、`Busy`、`HeadMoved` 和失败输出；
- 遇到未知输出直接失败，不能猜测成功。

### 5.6 结果回收不能覆盖真实用户目录

第一轮实验只在评测临时目录运行。胜出候选先回收到新的临时最终工作区并完成独立验证，不直接覆盖用户正在使用的项目目录。

## 六、最小接入设计

Epsilon 只增加一个面向实验的 LayerFS 适配边界，职责包括：

- 初始化实验 Store、LayerStack 和基础 Layer；
- 为每个候选 Worker 创建 Branch 和 Workspace；
- 把 Workspace 路径交给现有 Worker 运行时；
- Commit 成功候选，Discard 失败或取消候选；
- 收集 Branch、Workspace、Commit、耗时和错误信息；
- 在实验结束时清理 Workspace 和后台资源。

适配器不负责：

- 调用模型；
- 决定哪个候选获胜；
- 自动解决分支冲突；
- 绕过工具审批；
- 修改 LayerFS 源码；
- 成为普通单 Agent 路径的强依赖。

当 LayerFS 未安装、版本不匹配或环境检查失败时，实验应明确停止，不静默退回共享工作区后继续记录为 LayerFS 结果。

## 七、对照组

使用相同任务、模型、提示词、工具轮次上限和验证命令运行三个档位：

| 档位 | Worker | 工作区 | 目的 |
|---|---|---|---|
| A：第二版基线 | 单 Worker，串行 | 普通共享目录 | 得到当前正确率和耗时 |
| B：LayerFS 开销 | 单 Worker，串行 | 独立 LayerFS Workspace | 测量隔离本身的成本或收益 |
| C：LayerFS 并行候选 | 2～3 个 Worker，并行 | 每个 Worker 独立 Branch + Workspace | 测量多候选择优的正确率和墙钟时间 |

没有 B 档时，不能判断 C 档的变化来自 LayerFS 工作区还是多个模型调用。

## 八、任务选择

第一轮选择至少五个可重复验证的代码任务，并同时包含：

- 单文件缺陷；
- 跨文件修改；
- 有明确测试命令的任务；
- 容易产生不同修复方案的任务；
- 一个会让多个候选修改同一路径的压力任务。

任务必须有确定性验证，不能根据模型最终回复判断成功。每个档位使用新的临时目录、Session、LayerFS Store 和 Workspace，禁止复用上一次运行留下的修改。

冒烟阶段可以只跑一个小任务，但只能说明流程连通，不能据此报告优化百分比。正式对照至少报告每个任务的原始结果；如果需要给出较稳定的模型效果结论，再对较小任务集重复运行并单独报告波动。

## 九、实验流程

每个任务按以下流程执行：

```text
准备相同基础代码
    ↓
创建新的评测运行目录
    ↓
按 A / B / C 档准备工作区
    ↓
启动 Worker，记录模型和工具事件
    ↓
运行候选自己的验证命令
    ↓
LayerFS 候选执行 Commit
    ↓
Reviewer 检查候选差异和测试结果
    ↓
选择胜出候选，或记录无可用候选
    ↓
在新的临时最终工作区重建胜出结果
    ↓
运行独立验证器
    ↓
End / Discard 并检查资源清理
    ↓
保存 JSONL 原始结果和汇总报告
```

候选自己的“测试通过”不能直接作为最终成功。只有胜出结果在新的临时最终工作区通过独立验证，任务才算成功。

## 十、重点指标

### 10.1 正确性

- 最终任务成功率；
- 候选测试通过率；
- 至少一个候选正确的任务比例；
- Reviewer 选中正确候选的比例；
- 胜出结果回收成功率；
- 无关文件修改率；
- Workspace 相互污染次数；
- 需要人工合并或人工修复的任务比例。

正确率变化使用百分点表达，例如从 40% 到 60% 是增加 20 个百分点，不写成“提升 20%”。

### 10.2 时间

- 端到端总耗时；
- 首个正确候选完成时间；
- 最慢候选完成时间；
- Workspace 创建耗时；
- Worker 实际运行耗时；
- Commit 耗时；
- 胜出结果回收和最终验证耗时；
- End / Discard 清理耗时。

相对耗时变化按以下方式计算：

```text
相对变化 = (基线耗时 - 实验耗时) / 基线耗时
```

结果为正表示更快，为负表示更慢。必须同时展示原始秒数，不能只展示百分比。

### 10.3 Token 与成本

- 父 Agent 实际 Token；
- 每个 Worker 实际 Token；
- Reviewer 实际 Token；
- 全部 Agent Token 总和；
- 成功任务平均总 Token；
- 若配置了真实价格，记录每个任务费用。

并行候选可能降低墙钟时间，但总 Token 通常会上升。报告中必须把“更快”和“更便宜”分开。

### 10.4 工作区与存储

- 基础代码大小；
- LayerFS Store 初始大小和结束大小；
- 每个物化 Workspace 的磁盘占用；
- 创建 Workspace 时实际写入的字节；
- Commit 新增对象数、复用对象数和新增字节；
- 临时目录峰值占用；
- 实验结束后的残留文件和进程数。

如果拿不到某项真实数据，记录为不可用，不用估算值冒充实际值。

### 10.5 稳定性与失败

- Workspace 创建失败数；
- `Busy` 次数；
- `HeadMoved` 次数；
- Commit 失败数；
- Worker 取消和超时数；
- 清理失败数；
- CLI 输出解析失败数；
- LayerFS 基础设施失败导致的任务失败数。

LayerFS 环境失败与 Agent 修改错误必须分开统计，不能混入同一个失败类别。

### 10.6 可追溯性

每个候选至少保存：

- Epsilon 运行标识；
- Worker 标识；
- Branch ID；
- Workspace ID；
- Commit ID 或明确的未提交原因；
- 基础快照标识；
- 修改文件列表；
- 验证命令和结果；
- Reviewer 选择结果。

## 十一、结果解释

实验结果按以下规则解释：

- C 比 A 更快，但 B 比 A 明显更慢：收益主要来自并行，LayerFS 本身有额外成本；
- B 与 A 接近，C 更快且正确率不降：LayerFS 隔离适合继续验证；
- C 正确率提高但 Token 大幅增加：这是用成本换成功率，不是全面优化；
- C 候选正确但 Reviewer 经常选错：瓶颈在候选选择，不在工作区隔离；
- Workspace 创建或回收占据大部分时间：优先解决投影和结果回收，不增加更多 Worker；
- 物化目录占用随 Worker 数近似线性增长：当前环境没有获得预期的低复制收益；
- 经常需要人工合并：候选择优模式不适合这些任务，不能继续宣称自动闭环。

固定任务上的一次结果只能作为工程观察，不代表普遍性能结论。报告必须列出任务、模型、环境、LayerFS 版本和每个档位的原始数据。

## 十二、停止条件

出现以下任一情况时停止扩大实验：

- 两个 Workspace 会互相看到未提交修改；
- 无法可靠识别 Commit 是否成功；
- 胜出结果无法无损回收到最终临时工作区；
- 失败或取消后经常残留 owner、Workspace 或挂载；
- 物化成本使小型任务稳定慢于基线，且没有正确率收益；
- 必须修改 LayerFS 内部存储实现才能完成基本接入；
- LayerFS 基础设施失败多到无法区分 Agent 能力。

停止后保留已经得到的原始结果和失败原因，不通过放宽成功标准继续实验。

## 十三、实现顺序

1. 完成并验收问题 30 第二版；
2. 保存 A 档基线；
3. 固定 LayerFS 版本并构建 CLI；
4. 完成环境检查和最小可行性验证；
5. 实现最小 CLI 适配器及错误解析；
6. 接入单 Worker 的 B 档；
7. 验证 Commit、回收和清理；
8. 接入 2 个并行候选 Worker；
9. 流程稳定后再尝试 3 个 Worker；
10. 运行固定任务集的 A / B / C 对照；
11. 保存 JSONL 原始结果并生成报告；
12. 根据结果决定停止、继续实验或设计正式集成。

## 十四、验收标准

- 问题 30 第二版已经完成且测试通过；
- 固定版本的 LayerFS CLI 可以重复构建和启动；
- 两个候选 Workspace 的修改完全隔离；
- 每个成功候选都有可查询的 Branch 和 Commit；
- 失败候选可以 Discard，且不会污染其他候选；
- Reviewer 能看到候选差异、测试结果和身份信息；
- 胜出结果能进入新的临时最终工作区并通过独立验证；
- A / B / C 三档至少完成一轮固定任务集；
- 正确率、时间、Token、存储和失败指标均有原始记录；
- 报告明确区分观察结果、环境限制和推测；
- 未把 LayerFS 描述成安全沙箱、自动合并器或强持久化系统；
- Epsilon 全量单元测试通过。

## 十五、实验后的决策

实验完成后只做以下三种决策之一：

1. **停止接入**：收益不足或现实边界无法接受，保留报告，不进入正式运行时；
2. **继续实验**：结果有潜力，但 FUSE、结果回收、Reviewer 选择或任务规模仍需单独验证；
3. **正式设计**：正确率或墙钟时间有稳定收益，失败和清理边界可控，再为 LayerFS 工作区编写独立正式设计。

无论结果如何，都不直接从本实验跳到“默认开启 LayerFS”。正式启用必须另行设计配置、安装检查、用户提示、故障处理和向后兼容。
