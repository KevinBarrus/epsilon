# 问题 27：会话、上下文与长任务状态仍未形成完整可靠闭环

## 一、问题背景

在学习“会话隔离与上下文压缩”后，需要重新回答一个比“有没有 Session、有没有摘要”更重要的问题：

> Epsilon 能否保证不同任务不会串线、已经执行的工具不会在历史中消失、压缩后的上下文仍然可信，并且长任务中断后可以从明确的任务状态继续，而不是只靠模型重新阅读聊天记录猜测进度？

本轮按源码检查了 `Session`、`Memory`、`ContextManager`、`AgentLoop`、工具注册与权限、JSONL 持久化和 MCP 接入。结论不是“现有设计全部有问题”。Epsilon 已经正确区分了三类数据：

```text
Session History：用户可恢复的完整会话记录
Runtime Memory：当前进程中的消息列表
Model Context：ContextManager 按预算构造的本次模型输入
```

每次 `run_chat()` 还会为当前会话单独创建 `Session`、`ToolManager`、`PermissionManager` 和 `ContextManager`，因此当前单进程、单交互会话模式下不存在全局 `messages` 导致的直接串线。工具虽然通过闭包绑定工作区，但注册表也只属于当前 `run_chat()`，不会被另一个会话复用。

真正的问题集中在失败边界、并发边界、远程工具信任边界和长任务恢复边界。

## 二、问题一：模型请求失败后，本轮已经完成的工具轨迹可能丢失

`AgentLoop.run()` 会把本轮产生的 assistant 工具调用和 tool 结果暂存在 `new_messages` 中，正常结束后由 `ui.py` 写入 Session。

如果模型已经完成一次工具调用，随后下一次模型请求失败，`AgentLoop` 会直接抛出 `AgentError`。当前异常没有携带此前的 `new_messages`，`ui.py` 的异常分支只追加一条 assistant 错误消息。

可能出现以下不一致：

```text
工具已经修改文件
  ↓
下一次模型请求失败
  ↓
界面显示错误
  ↓
JSONL 中没有刚才的工具调用和执行结果
```

恢复会话后，模型无法解释文件为什么发生变化。这里丢失的不是普通展示文本，而是已经发生的外部副作用证据，属于 correctness 问题。

## 三、问题二：并行工具执行期间取消，可能留下不完整工具链

并行批次中，部分只读工具可能已经完成，另一些仍在运行。当前取消逻辑会取消剩余任务，但 `_execute_tool_batch()` 不会把已经完成的部分结果交还给 `AgentLoop`。

最终可能只保存 assistant 的多个 `tool_calls`，却缺少对应的 `tool` 消息。模型恢复后看到“发起了调用但没有结果”，无法区分：

- 工具没有执行
- 工具执行成功但结果没有保存
- 工具执行到一半被取消
- 工具产生了副作用但系统不知道最终状态

对于当前并行只读工具，这主要会造成重复读取和协议不完整；一旦未来允许远程或有副作用工具并发，该不确定性会直接变成安全风险。

## 四、问题三：工具结果的成功与失败语义在消息层丢失

`ToolResult` 已经包含 `is_error` 和 `error_category`，但 `AgentLoop` 转换为 `Message(role="tool")` 时只保留 `content` 和 `tool_call_id`。

这会造成两个实际问题：

1. 上下文摘要只能看到一段工具文本，不能稳定判断调用成功还是失败
2. `_collect_file_operations()` 只看 assistant 发起了哪个工具，会把失败的写文件调用也记入“已修改文件”

可以把它类比为快递系统只保存了“下过单”，却没有保存“已签收、派送失败还是已取消”。后续统计“哪些包裹已经送达”时，系统只能猜。

## 五、问题四：同一个 Session 缺少跨进程单写者约束

Session 内部的后台队列只能保证当前进程中的消息按顺序写入。若用户在两个终端同时 `resume` 同一个 Session，两个进程会共同追加同一个 JSONL 文件。

当前没有会话级文件锁，因此无法保证跨进程记录顺序，也无法保证压缩记录的 `first_kept_message_index` 对应另一进程看到的消息序列。即使单次 append 通常很快，也不能把“多数时候没碰撞”当成一致性保证。

这属于低并发但高破坏性的边界：正常使用不一定遇到，一旦遇到，恢复和压缩都可能建立在错误顺序上。

## 六、问题五：MCP 的超时、输出和权限信任边界不完整

本地文件工具和命令工具已有输出上限，命令也有超时；stdio MCP 当前仍有三个缺口：

1. `_request()` 读取响应时没有超时，MCP Server 不返回数据就可能一直阻塞 Agent
2. MCP 结果没有经过统一输出限制，远程工具可把超大内容直接送入上下文
3. MCP Server 声明 `readOnlyHint=true` 后会被当作读工具自动放行，但该字段来自外部提供者，不应天然成为本地安全策略

此外，`idempotent` 目前只是定义字段，没有参与“本会话始终允许”的决策。一个不可幂等的写工具若被长期授权，重复调用可能产生重复副作用。

## 七、问题六：Workspace 约束没有覆盖 Shell，不能称为安全隔离

文件工具通过路径规范化和根目录检查限制工作区外访问，但 `run_command` 只是把工作区设为当前目录。用户批准命令后，Shell 仍可通过绝对路径或 `cd ..` 访问工作区外资源。

因此当前准确的安全边界是：

```text
文件工具：工作区路径边界
命令工具：逐次人工审批 + 超时和进程清理
整个 Agent：不是沙箱
```

在本地、前台、用户本人操作的 CLI 场景下，这个边界可以接受；在无人值守、执行不可信仓库或多用户服务场景下则不够。

## 八、问题七：长任务只有“聊天摘要”，没有独立的“任务控制状态”

当前压缩摘要保存 Goal、Progress、Key Decisions、Next Steps、Critical Context。它可以帮助模型在长对话中继续理解语义，但仍然是一段由模型生成的文本，不是 Harness 可以校验和驱动的任务状态。

例如任务运行一天后中断，Session 能恢复“聊过什么”，却不能可靠回答：

- 当前目标是否仍然有效
- 哪一步已经完成并有测试证据
- 下一步唯一动作是什么
- 当前是在等待用户、遇到阻塞，还是仍可自动继续
- 本次恢复应该从哪个检查点继续

LoopX 的关键启发不是引入更多 Agent，而是把长期目标拆成两层：长期目标可以跨越多个进程和会话存在；每次执行仍然只是一个有边界、可验证的小步骤。目标、待办、阻塞门、证据和运行记录属于持久化控制状态，聊天记录只是执行过程之一。

Epsilon 若只增加工具轮次而没有任务状态，长任务会“运行更久”，但不会因此更可恢复。模型仍可能在压缩后忘记验收标准、重复探索或把计划误当成已完成。

## 九、当前可以暂缓的设计

以下设计在 SaaS、多用户或更复杂工具生态中有价值，但不是当前本地 CLI 的优先问题：

- Tenant、User、Request 等多层作用域
- 全局纯工具定义加每次调用传入的 `RuntimeContext`
- 完整 Event Store 和 Artifact Store
- 按日志、测试、Diff 等工具类型分别做语义压缩
- 跨 Session 的向量记忆与自动召回

现在引入这些设计会增加大量结构代码，却不能先解决工具轨迹丢失、并发写入和 MCP 卡死等直接风险。

## 十、本轮问题的本质

当前 Epsilon 已经具备正确的基础分层，但部分状态只在“正常结束”路径上闭环：

> 正常路径能保存，不等于失败路径可恢复；有消息摘要，不等于有长期任务状态；工具在工作区启动，不等于工具被工作区隔离。

后续优化应保留现有 Session、Context 和 Tool Registry 边界，先补齐失败与安全闭环，再以最小方式增加长期任务控制状态，而不是重写整个 Harness。
