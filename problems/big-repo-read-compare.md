# 大语料只读对比实验（codex）：A / B / C

> ⚠️ **标注：本文所有结果为"完成门前"的数据。**
> 完成门（Completion Gate）开启后会改变评测行为（`goal(op=complete)` 需经独立验证），
> 因此本文的 A/B/C 与此后任何结果**不可比**。门后的实验见 `problems/completion-gate.md`。

**单次运行、描述性对照，不作统计推断。** 语料 = codex 仓库的**生产 Rust + docs/ + scripts/ + 顶层 Markdown**
（排除 `tests/`、`*tests.rs` 与生成物噪声），实测 **829,876 行 / 2,145 文件**——是单 Agent 可读上限
（约 22 万行）的 **3.8 倍**。三档同模型 `deepseek-flash`（`thinking=high`）、**同一熔断 40M token / 90 分钟**、
副本内容一致。任务描述只给泛化要求（"为每个核心子系统写实现剖析：机制、关键参数/阈值、数据结构、代码位置"），
**不点名任何子系统、不列举清单**。

评分：**11 个子系统 × 40 条隐藏清单** = 30 条"具名常量/字面值"题 + 10 条**机制类**题
（后者要求命中 ≥2 个标识符，单个 grep 不足以作答）。每条关键词都验证过不出现在全仓 Markdown 里。

## 二、三条结论与证据强度

### ① 扇出读在大语料上把覆盖率从 10% 提到 27.5%（2.75×）——**方向明确，n=1**

- **证据强度**：效应量 2.75× **大于**我们在 oncall 上标定的运行间波动（1.7~1.9×），方向与机制一致
  （A 只读了语料约 3% 就宣告完成；B 用 18 个 Scout 把阅读推到了 7/11 个子系统）；
- **但仍要标注 n=1**：没有重复运行，不能排除"这次 A 恰好停得早、B 恰好跑得久"。

### ② fork（C）在这个任务上**不划算**，甚至更差——**效应量大**

- C 与 B 用**同样 18 个 Scout、同样熔断**，结果：**C 撞满熔断且没有产出 report.md**，B 产出报告且覆盖 27.5%；
- 机制清楚：fork 子 Agent 每个请求都要**重发继承到的父上下文**——C 的子 Agent 花了 **38.3M token**
  （其中 36.4M 命中前缀缓存），B 只有 **35.7M**；缓存命中率 fork 更高（**0.9570 vs 0.9455**），
  但**抵不过重发量**，最终把预算耗在"重发"上、没来得及产出交付物；
- **与 oncall 实验结论一致**（那里 C = 3.19× B）：fork 不是免费的，它把"重读成本"换成"重发成本"。

### ③ 机制题两档都只有 **1/10**——扇出读对"必须跨文件连逻辑"的问题没有优势

- A 命中 `app_request_processors`，B 命中 `core_tool_parallel`，**都是 1/10，且不是同一题**；
- 反而**常量题**从 3/30 提到 10/30——扇出读提升的是"覆盖面"，不是"理解深度"；
- **证据强度**：两档独立得到同一个低值（1/10），方向一致；但因为都是单次运行，
  只能定性为"**本次没有观察到扇出读在机制题上的优势**"。

## 三、必须如实记录的异常

1. **A 是"提前宣告完成"，不是"读完了"**：它只用掉 **9% 的预算（3.6M / 40M）**、221 秒、
   109 次读（约语料的 3%）就 `goal complete`。所以 A 的低覆盖率**不能解释为"预算不够"**，
   而是"模型认为够了"。这削弱了"同等预算下比覆盖率"的严格性——A 根本没花它的预算。
2. **C 撞满熔断且没有交付物**：`stop_reason=budget_limited`、`report.md` 未生成，
   因此 C 的覆盖率**不计分（0/40）**，而不是"A 的覆盖率"。
3. **harness 的一个 bug（已修）**：`result.json` 里三档的 `original_code_unchanged` 都写成 `False`，
   原因是最后校验用了**默认（oncall 口径）的哈希参数**，没带 codex 的语料范围，比的是两个不同口径。
   修法：`run()` 新增 `source_hash_fn`，由调用方传入与 baseline 完全相同的口径。
   **独立复核**：用同一口径重算原仓库哈希 = `aba9b213…`，与三档 `baseline.source_hash` **完全一致**，
   且 `git -C ~/projects/codex status --short` 为空 → **原仓库确实零改动**。
   （三档 `result.json` 里的该字段保留原值不改写，以保留证据。）
4. **工具错误数差异大**：A 9 次、B 90 次、C 88 次——扇出读显著抬高了错误量（主要是子 Agent 的）。
5. **精确率无人守住**：A 0.9161、B 0.8909——B 引用的路径数从 155 涨到 449，幻觉也同比例增加。

## 四、对面试叙事的价值

- **"用途边界"而不是"角色边界"**：同一个 fork 改造，在"需要共享上下文"的写任务上是 3.6× 更贵，
  在读任务上是"重发成本吃掉预算"，**两次都证明 fork 不划算**；而扇出读（fresh）的价值只在
  "覆盖面受限于单 Agent 的阅读量"时才出现——**本次是语料 3.8 倍于可读上限的场景，它出现了（10% → 27.5%）**。
- **"覆盖面 ≠ 理解深度"**：机制题两档都只有 1/10，而常量题 3→10——**并行读买得到广度，买不到深度**。
  这正对应"交付物边界"的启发：要测扇出的真正主场，任务应从"读得深"换成"产出多"。
- **方法论**：A 的"提前宣告完成"是一次典型的 **evaluation artifact**——如果不看 token 用量
  （只用了 9%），很容易把"模型说够了"误读成"单 Agent 读不完"。
