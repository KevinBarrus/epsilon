# 第二轮优化方案

## 总体目标

本轮先补齐 Coding Agent 的三条底线：上下文不会因中文估算失真而越窗、危险工具的审批信息足够明确、模型请求不会无限等待。随后提高长任务与评测的可靠性。每个问题独立实现、独立测试；没有真实收益的生产级能力继续记录为延期项，不引入新依赖或重型基础设施。

## 实施顺序

1. 上下文硬预算：问题 1、2、3、5、4
2. 工具审批与模型超时：问题 15、16、25
3. 工具资源边界：问题 19、20、28
4. 运行时韧性：问题 24、26、27
5. 评测可信度：问题 6、7、8、9、10、11
6. 性能、完整度与文档：问题 12、13、17、18、21、22、23

## 问题 1 方案：修正中文 Token 估算（已完成）

- 保持当前零依赖实现，按 Unicode 字符类别估算：CJK 字符按 1 Token，其余文本按 4 字符 1 Token
- 工具名称、调用 ID、参数 JSON 和协议开销继续纳入同一估算函数
- 将模型返回的上下文超限错误识别为 `context_overflow`，由应用层重新构建压缩上下文后仅重试一次
- 不接入 `tiktoken`，因为目标是 OpenAI-compatible 模型，单一 tokenizer 不能保证准确

验收：含中文长消息时压缩会在服务端拒绝前触发；模拟上下文超限错误时可压缩并重试一次

完成记录：Token 估算已按宽字符 1 Token、其余字符 4 字符 1 Token 保守计算；服务端上下文超限会归类为 `context_overflow`，UI 会强制压缩上下文后仅重试一次，相关测试通过（45 passed）

## 问题 2 方案：在工具循环中执行上下文检查（已完成）

- `AgentLoop` 接收一个由 `ContextManager` 提供的上下文重建回调
- 每轮工具结果追加后调用回调，得到重新压缩后的模型可见上下文和可选压缩记录
- `ui.py` 仍是唯一的 Session 写入方；回调只构建上下文，不直接操作 TUI 或 Session
- 保持工具串行执行，本轮不引入并发调度

验收：多轮工具结果累计超过预算时，下一次模型请求前会压缩，且新增消息按原顺序持久化

完成记录：`AgentLoop` 会在每次模型请求前调用应用层传入的上下文构建回调，并始终保留完整运行时历史；UI 在本轮消息持久化后追加回调生成的压缩记录，相关测试通过（43 passed）

## 问题 3 方案：限制摘要请求输入（已完成）

- 为摘要输入使用独立的摘要预算，默认取模型可用消息预算的一半
- 序列化前先按完整对话单元选择最近的待摘要消息；工具结果复用现有输出截断结果
- 超出摘要预算的更旧内容不再直接送入摘要模型，改由规则化说明标记其已省略
- 摘要失败仍沿用现有 fallback，不新增第二个摘要模型

验收：超长历史触发压缩时，摘要请求本身不超过摘要预算；摘要失败后仍能生成硬预算内上下文

完成记录：摘要输入预算已设为正常模型消息预算的一半；摘要模型请求会在序列化前保留预算内的最近完整历史并标记省略内容，预算不足时直接进入既有 fallback，相关测试通过（44 passed）

## 问题 4 方案：处理压缩记录写入失败（已完成）

- `ui.py` 检查 `Session.add_compaction()` 的返回值
- 写入失败时在状态栏显示持久化降级，并在本次运行内保留已生成的压缩结果
- 下一轮使用该运行时压缩结果，避免同一进程内重复摘要；进程重启后允许重新摘要
- 不为压缩记录单独建立 pending 文件，消息日志仍是恢复正确性的唯一依据

验收：模拟压缩记录写入失败时，当前会话不会重复请求摘要，状态栏会提示降级

完成记录：Session 已将未落盘的压缩记录保留为仅当前进程有效的临时状态，后续请求会复用该记录；UI 检查压缩记录写入结果并显示持久化降级提示，相关测试通过（59 passed）

## 问题 5 方案：保证 fallback 工具链有效（已完成）

- 在 `_split_oversized_latest_turn` 的最终兜底前校验工具调用链
- 无法保留完整链时，整体移除该调用链，不单独保留 `tool` 消息
- `_fit_messages_to_budget` 裁剪时以对话单元或完整工具链为最小单位；无法安全裁剪则返回明确的上下文错误

验收：所有 fallback 输出中，每条 `tool` 消息都存在对应 assistant tool call，且完整请求不超预算

完成记录：超大最新轮次无法保留完整工具链时会全部进入摘要，不再留下单独 tool 结果；硬裁剪删除工具结果时会同步移除对应 assistant tool call，相关测试通过（36 passed）

## 问题 6 方案：在报告中隔离回归与能力指标（已完成）

- HTML 报告按“核心链路回归”和“真实任务评测”分区展示结果与汇总指标
- 回归区明确标注为固定脚本验证，不使用“模型能力”措辞
- 保留现有离线场景，不把它们改造成不稳定的模型测试

验收：读者能直接区分固定脚本通过率和真实模型任务结果

完成记录：HTML 报告已按核心链路回归、真实任务评测和在线专项分区；每个分区独立计算汇总指标、展示结果与失败断言，固定脚本区明确不衡量模型能力，相关测试通过（7 passed）

## 问题 7 方案：扩展真实任务评测（已完成）

- 将在线任务扩展为三个确定性文件任务：单文件修改、多文件修改、工具失败后的修复
- 每个任务验证文件最终内容、关键工具调用顺序和无关文件未被修改
- 最终回复只做关键词完整性检查，不接入 LLM-as-a-judge，避免评测引入第二个不稳定模型

验收：在线评测能区分未读取就修改、修改错误文件、工具失败后未恢复三类失败

完成记录：在线主套件现按每次重复执行单文件修改、多文件修改和工具失败恢复三条真实任务；各任务独立工作区，验证目标文件、无关文件、先读后改工具顺序、失败后恢复、最终回复关键词及 Session 持久化，相关测试通过（16 passed）

## 问题 8 方案：修正小样本统计表达（已完成）

- 报告显示样本数，并将少于 20 次的 P50/P95 标为“观察值”
- baseline 比较仍使用耗时指标，但报告不将小样本 P95 表述为稳定性能结论
- 不加入置信区间和显著性检验

验收：6 次运行的报告明确显示样本量和观察性标签

完成记录：报告在各评测分区展示样本数；样本少于 20 时，总耗时和请求耗时的 P50/P95 均标记为“观察值”，并明确不代表稳定性能结论，baseline 计算未改动，相关测试通过（12 passed）

## 问题 9 方案：降低 baseline 噪声误报（已完成）

- 性能门禁仅在样本数不少于 20 时启用 P95 比较
- 小样本只比较任务成功率和模型请求数；压缩次数增加改为报告提示，不直接失败
- 保留 25% 相对阈值，不引入统计依赖

验收：小样本网络波动不会导致 baseline 失败，稳定样本的明显性能回归仍会失败

完成记录：baseline 在当前和历史结果均不少于 20 个样本时才以 P95 延迟作为硬门禁；小样本仍比较任务成功率和平均模型请求数，压缩次数增加仅作为报告观察项，不影响门禁结果，相关测试通过（19 passed）

## 问题 10 方案：展示全部失败断言（已完成）

- 每个失败场景在报告中列出全部失败断言，而非仅第一条
- 保持当前转义和错误诊断展示逻辑

验收：构造两个断言失败时，报告能同时展示两个失败原因

完成记录：报告按“结果 + 断言”逐条渲染失败行，同一场景的所有失败断言及原因都会展示，现有 HTML 转义和分区逻辑保持不变，相关测试通过（12 passed）

## 问题 11 方案：明确估算 Token 的性质（已完成）

- 将报告字段重命名为“估算上下文 Token”，并在说明中标注其不是服务端 usage
- `actual_tokens` 无数据时继续显示为空，不用估算值替代
- 复用问题 1 的 CJK 估算函数

验收：报告不把估算 Token 表述为实际消耗，中文场景估算不再系统性按四分之一低估

完成记录：报告将每次运行的 Token 分为“估算上下文 Token”和“服务端实际 Token”，前者明确标注为本地估算、后者无数据时留空；多轮记忆离线场景已复用核心 CJK Token 估算函数，相关测试通过（15 passed）

## 问题 12 方案：延后运行期 Memory 优化（已完成）

- 当前完整历史是 Session 恢复和压缩的事实来源，暂不改变其全量驻留模型
- 在 `todo` 记录长会话达到性能阈值后再引入按需加载或不可变消息视图

验收：本轮不改生产代码；文档明确这是规模性风险而非当前正确性缺陷

完成记录：未改动生产代码；已在 `todo/session/memory-performance.md` 记录完整历史模型的边界、基于剖析的触发条件、不可变消息视图与按需加载的后续方向，明确这是长会话规模风险而非当前正确性缺陷

## 问题 13 方案：按需读取会话标题（已完成）

- 不建立 sidecar 索引，避免索引与日志的一致性问题

验收：列出会话不再为标题全量反序列化每个 JSONL 文件

完成记录：`list_sessions()` 现在二进制逐行读取到首条有效 user 消息即停止，不再调用完整历史加载；首条消息前的尾部半行仍会忽略、非尾部损坏仍返回明确错误，更新时间继续使用文件元数据，相关测试通过（31 passed）

验收：本轮不新增向量库、检索或跨会话自动记忆

## 问题 15 方案：在审批中展示工具参数（已完成）

## 问题 16 方案：收紧命令工具的会话授权（已完成）

- `run_command` 不提供“本次对话始终允许”选项，只允许单次确认或拒绝
- 其它写工具保持现有按工具名的会话授权语义
- `PermissionManager` 根据工具权限/能力选择允许的审批选项，TUI 不硬编码命令特例

验收：同一会话中每次 `run_command` 都需要明确确认，写文件工具的会话授权不受影响

完成记录：PermissionManager 会向审批层明确传递会话授权是否可用；命令权限工具只展示单次确认与拒绝，即使外部回调错误返回会话授权也会降级为单次授权，相关测试通过（52 passed）

## 问题 17 方案：将 MCP 配置接入启动入口（已完成）

- `main.py` 解析配置，`run_chat` 启动时注册该 Provider；未配置时保持纯本地工具行为
- 只支持一个 stdio Provider，不实现多 Provider 配置解析界面

验收：配置一个可用 stdio MCP Server 后，其工具会出现在模型工具定义并可实际调用

完成记录：新增单个 stdio MCP 的 `.env` 配置解析；启动层以工作区为 cwd 创建 Provider，应用层发现并注册远程工具，TUI 退出或注册失败时关闭子进程，未配置时仍只注册本地工具，相关测试通过

## 问题 18 方案：修正工具设计文档（已完成）

验收：设计文档与 `output_limits.py` 的实际行为一致

## 问题 19 方案：限制文件读取和搜索范围（已完成）

- `read_file` 在读取前以文件大小拒绝超限文件，避免先全量读入
- `search_files` 改用 `os.walk`，剪枝 `.git`、`.epsilon`、`node_modules`、`.venv` 等目录
- 搜索跳过超过单文件上限和含 NUL 字节的文件，并在达到结果输出预算后立即停止
- 不解析 `.gitignore`，避免将搜索工具变成版本控制规则实现

验收：搜索大仓库不会遍历常见缓存目录；大文件和二进制文件不会读入内存

完成记录：读取工具会在读入前拒绝超过 1 MB 的文件；搜索工具改用不跟随链接的 `os.walk`，剪枝常见运行目录并跳过二进制、超大文件，达到既有输出预算后立即停止，相关测试通过（16 passed）

验收：模型不能静默获得命令会话授权；文档不将当前命令工具表述为沙箱

完成记录：问题 15、16 已保证命令完整可见且每次单次确认；工具设计与待办已明确当前命令工具不具备 OS 级文件、网络或资源隔离，未引入脆弱的命令黑名单，相关权限测试通过（52 passed）

## 问题 21 方案：避免流式全量重建对话区（已完成）

- 对话条目保存自己的 `FormattedTextControl`，`append_to_entry` 仅更新目标条目并 invalidate
- 新增条目或恢复历史时才重建布局
- 保持现有自然堆叠、滚动和自动跟随逻辑不变

验收：连续追加流式文本时不会重建全部对话窗口

完成记录：每条对话消息在创建时保存自己的 `FormattedTextControl`；流式追加和工具结果替换只更新目标控件并刷新界面，新增条目仍负责同步布局，现有滚动和自然堆叠逻辑保持不变，相关测试通过（31 passed）

## 问题 22 方案：只增加输入历史（已完成）

- 为输入 `TextArea` 接入 prompt-toolkit 内存历史，支持上下方向键召回本次运行的输入
- Markdown 和代码高亮继续延期，避免改变稳定的纯文本渲染层

验收：发送过的输入可通过上方向键召回

完成记录：输入框已接入 prompt-toolkit 的 `InMemoryHistory`；每次有效发送会保留原始输入文本，本次进程内可通过默认上下方向键召回，审批状态的方向键行为保持不变，未加入持久化、Markdown 或代码高亮，相关测试通过（27 passed）

## 问题 23 方案：批量恢复历史视图（已完成）

- `ChatScreen` 提供批量追加历史条目的方法，恢复时只同步一次对话区布局
- `ui.py` 使用该方法恢复 Session，正常流式路径不变

验收：恢复大量历史时只触发一次布局同步

完成记录：`ChatScreen.add_history_entries()` 会一次创建恢复条目、同步一次布局并滚动到底部；`ui.py` 恢复 Session 时改用该接口，正常新增和流式路径保持原行为，相关测试通过（41 passed）

## 问题 24 方案：增加有限退避重试（已完成）

- 对 `rate_limit`、网络和超时重试采用固定次数的指数退避与小幅随机抖动
- OpenAI 异常包含 `Retry-After` 时优先使用该值，否则使用本地退避
- 保持收到任何流式事件后不重试，避免重复展示和重复工具调用

验收：连续网络失败的重试间隔递增；服务端给出 Retry-After 时按其等待

完成记录：网络、超时和限流错误最多重试两次；无服务端建议时采用 0.5 秒起步、带小幅抖动的指数退避，限流响应的秒数或日期型 `Retry-After` 会被优先使用，相关测试通过（22 passed）

## 问题 25 方案：为模型请求设置超时（已完成）

- 在 `OpenAICompatibleClient` 创建客户端时设置可配置的请求超时
- 超时统一转换为现有 `timeout` 错误类别，进入问题 24 的重试策略
- 不在本轮增加总 Turn 超时，避免中断已经安全运行的长工具任务

验收：模拟模型请求挂起时，Agent 在配置时间后返回可解释的超时错误

## 第二轮总体验收标准

- 中文长上下文、工具循环和摘要请求都不会绕过模型请求预算
- fallback 不会向模型发送孤立的工具结果
- 命令与写工具的审批信息可审查，命令不会因一次确认而获得会话级放行
- 模型网络请求有超时与有限退避，不会无限阻塞
- 文件工具不会无界读取常见大目录、二进制或超大文件
- 在线真实任务与离线回归在报告中清楚分开，指标不夸大小样本结论
