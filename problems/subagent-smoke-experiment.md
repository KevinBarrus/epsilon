# Scout 多独立调查点冒烟评测

## 一、评测目的

旧任务让主 Agent 回答同一套运行时架构问题。即使打开 Scout，真机结果仍为 `scout_calls=0`，没有走到委派链路。

本轮把输入改为四个相互独立的调查点：

1. `config.py` 的配置加载流程；
2. `tools/permissions.py` 的权限判断；
3. `context.py` 的 token 估算；
4. `session_store.py` 的 JSONL 读写。

提示词明确说明四项可并行委派。目标是观察主模型是否会调用多个 Scout，并记录任务完成情况、父 Agent token、全部 Agent token、耗时和 Scout 调用次数。

## 二、运行配置

- 模型：`deepseek-v4-pro`
- 思考强度：`high`
- 工作区：当前 Epsilon 仓库
- 父 Agent 最大工具轮次：30
- 对照方式：同一任务依次运行 off、on 两档
- 原始结果：`evaluation-results/subagent-smoke-independent.jsonl`（按仓库规则忽略，不提交）
- 执行时间：2026-09-23

两档均为只读调查，没有修改工作区。off 档不向模型暴露 `spawn_agent`；on 档暴露该工具并注入 Scout 使用说明。

## 三、结果

| 指标 | off | on | 对比 |
| --- | ---: | ---: | ---: |
| 任务完成 | 是 | 是 | 两档均完成 |
| Scout 调用次数 | 0 | **4** | 多 Scout 委派链路实际触发 |
| 父 Agent actual tokens | 339,813 | **244,748** | **减少 95,065（28.0%）** |
| Scout actual tokens | 0 | 缺失 | 至少一个 Scout 请求缺少服务端 usage |
| 全部 Agent actual tokens | 339,813 | 缺失 | 无法比较 |
| 总耗时 | 161.4 秒 | **2,525.2 秒（42.1 分钟）** | on 为 off 的 **15.6 倍** |
| 父模型请求数 | 11 | 12 | on 多 1 次 |
| 注入父上下文的 Scout 结果 | 0 字符 | 7,155 字符 | 4 个 Scout 摘要合计 |

## 四、结论

本轮达到了最基本的验证目标：把任务改成多个独立调查点后，主模型在 on 档发起了 4 次 `spawn_agent`，不再像旧任务一样全部由主模型自行读取。两档最终回答也都覆盖了四个指定模块。

不过，当前结果只保存 Scout 调用总数，没有保存这 4 次调用所属的工具批次。`spawn_agent` 的工具定义允许同一批次并行执行，但本轮数据不能区分“一次生成 4 个调用”和“分多轮逐次调用”，因此不能据此确认主模型实际采用了并行调度。

父 Agent 的 actual tokens 从 339,813 降至 244,748，单次观测下降 28.0%。这说明 Scout 隔离了部分调查过程，减少了进入父上下文的探索开销。

但本轮不能得出“Scout 降低了总 token”的结论。on 档至少一个 Scout 模型请求没有返回完整 usage，评测器因此按既有规则把 `scout_actual_tokens` 和 `all_agent_actual_tokens` 记为缺失。缺失值没有按 0 处理，也没有用上下文估算值冒充服务端实际用量。

耗时结果明显不利：on 档为 42.1 分钟，是 off 档的 15.6 倍。当前结果只记录总耗时和调用次数，没有保留每个 Scout 的完成状态与分段耗时，因此不能仅凭这一次运行确定慢在模型服务、Scout 超时、重试还是调度等待。可以确认的是，在本次配置和请求条件下，Scout 没有带来墙钟时间收益。

## 五、判断

- **委派有效性：通过。** on 档发起了 4 个独立 Scout，真实走通委派链路。
- **并行性：无法判断。** 结果未保存工具批次分组。
- **父上下文收益：本次为正。** 父 Agent token 下降 28.0%。
- **全部 Agent token 收益：无法判断。** 服务端 usage 不完整。
- **耗时收益：本次为负。** on 档耗时约为 off 档的 15.6 倍。

因此，当前证据支持“Scout 能隔离父 Agent 的调查上下文”，但不支持“Scout 能降低整体成本或缩短耗时”。这是一次单样本冒烟结果，不代表稳定性能。
