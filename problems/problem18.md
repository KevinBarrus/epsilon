# 问题 18：长回复流式输出中途停滞、结束后补齐

## 问题一：活动回复随每个分片全量重算

当前助手回复在流式期间始终作为一个未提交的活动条目存在。每收到一个正文分片，界面都会把该分片追加到整条回复后，再重新解析截至当前的全部 Markdown、重置文本控件缓存并请求重绘。

回复变长后，单次更新需要处理的内容持续增长。模型分片到达速度超过界面处理速度时，分片会在网络或客户端缓冲区累积，界面表现为：开始正常输出，输出到中途停住，随后在模型结束时快速补齐剩余文本。

这不是模型推理、网络等待或 Markdown 最终高亮的问题。即使流式代码高亮已经关闭，普通长正文仍会因为整条活动消息的重复布局而落后。

## 问题二：活动视图没有把稳定内容移出重绘路径

项目已有 `InlineHistory`，但只在整条助手回复完成后才写入终端历史。流式期间，已经不可能再变化的前半段文本仍与末尾未完成文本一起留在 prompt-toolkit 活动视图中，持续参与布局和重绘。

这使长回复的工作量随已生成文本累积，而不是仅与当前未完成尾部有关。

## 问题三：现有渲染容器不适合承载不断增长的大文本

`FormattedTextControl` 适用于较小的静态控件。每次内容更新后，框架需要重新拆分全部格式化片段、计算可见行和自动换行高度。当前把整条持续增长的 Markdown 回复放入这个控件，会使终端重绘成为流式链路的阻塞点。

## 期望行为

- 无论正文长度，模型回复持续、平滑地出现，不在中途停住后一次性补齐
- 已稳定的输出不再反复参与活动区的 Markdown 解析和布局
- 未完成行、代码块和表格仍能在活动区正确显示
- 回复结束后仍使用当前完整 Markdown 渲染、高亮、终端历史和持久化流程
