# 第十四轮优化方案：TUI 交互与运行状态展示

## 总体原则

本轮只修复用户可直接感知且影响日常使用的 TUI 问题，优先复用当前 `CommandPicker`、`ConversationView`、`TextArea`、工具结果折叠和状态栏实现，不重写稳定的对话布局。

核心边界如下：

- `CommandPicker` 只负责 slash command 的选择与可见窗口
- `ConversationView` 只负责对话内容滚动和跟随底部
- `screen.py` 只负责把输入、选择器、对话区和状态栏组装起来
- `ui.py` 只负责把 AgentLoop 事件转换为对话条目和运行状态
- 工具原始参数、原始结果和持久化消息不受 TUI 省略影响
- 状态栏保留现有静态信息，动态 working 信息统一放入对话区
- 终端无法控制的能力（例如光标闪烁和字体缩放）只实现可靠请求，并提供明确降级说明

## 实施顺序

1. 修复 slash command 选择器滚动
2. 替换 ASCII Logo，并调整启动页居中和行间距
3. 修复对话历史键盘滚动与输入框定位
4. 固定输入框隐藏行提示和 Codex 式方向键行为
5. 统一 working/thinking/tool 活动展示
6. 完善工具调用与结果的折叠展示
7. 核对终端缩放协议与光标闪烁边界
8. 编写回归测试并进行真实终端验收

## 问题一方案：让 slash command 列表跟随选中项滚动

### 方案

保留现有 `CommandPicker` 的固定可见行数和 `vertical_scroll` 机制，只修正选择状态与窗口滚动之间的同步关系：

1. 选择项索引由 `move()` 统一修改
2. 每次索引变化后调用一个唯一的 `_follow_cursor()` 方法
3. `_follow_cursor()` 保证：
   - 当前索引不小于窗口起点
   - 当前索引小于窗口起点加可见行数
   - 窗口起点不小于 0
   - 窗口起点不超过 `len(items) - visible_rows`
4. 到达首尾时只钳制索引，不循环
5. 更新候选列表时，如果当前候选内容没有变化，保留当前索引和滚动位置；如果候选被删除，则将索引钳制到有效范围

不新增第二套滚动状态，也不让 prompt-toolkit 的默认补全导航和自定义选择器同时修改 cursor。

### 验收

- 候选数大于可见行数时，连续按 ↓，选中项始终可见
- 连续按 ↑ 可反向滚动
- 到首项/末项后继续按键不会越界或跳回另一端
- 输入继续过滤候选时，选择器不会无故跳到错误的滚动位置

## 问题二、三方案：ASCII Logo 与启动页布局

### 方案

1. 将当前 Unicode 方块字替换为普通 ASCII 字符组成的固定 Logo
2. Logo 内容保留 `ε EPSILON` 的品牌含义，但不依赖 Unicode 方块宽度、全角字符或图片资源
3. `LogoProvider` 继续作为 Logo 内容的唯一来源，渲染层不直接硬编码 Logo 行
4. 启动页渲染时分别计算 Logo 和前置信息的可见宽度，按终端宽度计算每组内容的居中缩进
5. Logo、欢迎语、模型和操作提示作为启动页整体排列，在逻辑组之间增加空行；不把空行加入状态栏
6. 终端宽度不足时使用安全的最小缩进，不产生负数切片或越界
7. 只有 Logo、没有会话消息时保持顶部展示；产生真实会话消息后才按对话区策略跟随底部

### 分层边界

- `logo.py`：只提供 ASCII 文本
- `screen.py`：只计算布局和居中
- `conversation_view.py`：只决定滚动位置
- `status.py` / `_render_info_line()`：不做任何改动

### 验收

- 常见终端字体中 Logo 可读，不出现方块乱码
- Logo 和前置信息视觉上居中
- Logo 与前置信息之间有清晰间距
- 启动页变化不影响工作目录、上下文、余额、费用、模型和复制状态栏
- 首次进入界面时 Logo 顶部完整可见

## 问题四方案：终端缩放采用能力边界清晰的处理

### 方案

优先让终端处理 Ctrl+滚轮缩放，不在应用内维护字体大小状态：

1. 检查自定义输出层启用的鼠标协议
2. 普通滚轮协议继续交给 TUI，用于对话滚动
3. 不启用会拦截终端 Ctrl+滚轮的协议扩展；若终端仍将事件发送给应用，再由应用忽略 Ctrl+滚轮
4. 不继续依赖应用发送 OSC 50 改变字体大小作为唯一方案，因为不同终端支持不一致
5. 在 README 或手动验收说明中注明：Windows Terminal/WSL 是否缩放由终端配置决定，应用只能避免拦截

### 验收

- 普通滚轮仍能滚动对话
- Ctrl+滚轮不会破坏对话滚动和输入
- 在支持该能力的 WSL 终端中，字体可以由终端缩放
- 在不支持的终端中，应用保持稳定，不显示虚假的缩放成功提示

## 问题五、九方案：对话滚动、输入框定位与隐藏行提示

### 方案

采用“方向键属于输入框，PageUp/PageDown 和鼠标属于对话区”的方案，参考 Codex 的 `ChatComposerHistory.should_handle_navigation()` 思路。

### 方向键规则

1. 选择器或审批界面打开时，↑/↓只选择当前选项
2. 输入框为空时，↑/↓使用已有 `InMemoryHistory` 恢复历史输入
3. 输入框有内容时，↑/↓交给 `TextArea`，只移动多行文本光标
4. 光标已在第一行继续按 ↑，内容和光标位置不再变化
5. 光标已在最后一行继续按 ↓，内容和光标位置不再变化
6. 输入框被对话滚动移出视口后，发生输入编辑或历史恢复时调用统一的 `ensure_input_visible()`，将 `ConversationView` 定位到底部
7. 不把 ↑/↓全局绑定为历史对话滚动，避免破坏多行编辑

### 对话区滚动

- 鼠标滚轮调用现有 `ConversationView.scroll_by()`
- PageUp/PageDown 按当前视口高度滚动
- 滚动到最底部后恢复自动跟随
- 模型输出期间如果用户主动离开底部，保留用户位置；用户回到底部后才恢复自动跟随

### 隐藏行提示

- 继续使用输入框顶部的 `↑ n more` 提示
- `n` 根据当前光标所在可见区域和输入框实际行数实时计算
- 文本变化、光标移动、窗口缩放和历史恢复后都触发重新计算
- 提示只占用输入框上边界区域，不修改状态栏高度
- 输入框最大行数继续由现有 UI 配置控制

### 验收

- PageUp/PageDown 和鼠标能够查看历史消息
- 滚动后输入框可通过输入编辑操作重新定位到底部
- 空输入按 ↑ 能恢复上一条已发送内容
- 多行输入按 ↑/↓只移动光标，不切换历史
- 超过输入框高度时准确显示 `↑ n more`
- 现有 Enter、Ctrl+J、Esc、Ctrl+D 行为不变

## 问题七方案：统一对话区运行状态展示

### 方案

新增轻量的对话区活动条目或活动状态，不把动态状态塞回静态状态栏：

1. AgentLoop 或事件适配层提供模型请求开始、工具开始、工具完成、重试和模型请求结束所需的最小事件信息
2. `ui.py` 将这些事件转换为对话区中的临时活动条目
3. `screen.py` 只负责渲染活动条目、spinner 和耗时文本
4. 活动条目在状态变化时原地更新，完成后转换为稳定的历史条目，避免每个计时 tick 都追加一条消息
5. 保留状态栏已有静态信息，不让 working 文本覆盖上下文、余额、费用或模型信息

### thinking-toggle 行为

- 思考展示开启：显示模型提供的 reasoning 内容；不额外显示重复的 `working for` 文本
- 思考展示关闭：显示 `working for Xs`，工具开始后显示工具名和执行耗时，完成后保留最终耗时
- reasoning 内容是否可见由独立的显示策略决定，AgentLoop 不包含 TUI 判断
- 没有 reasoning 输出时仍显示 working，避免用户等待期间无反馈

### 工具状态文本

统一生成以下类型的简短文本：

- `Working for 3s...`
- `read_files · 1.2s`
- `run_command · running`
- `run_command · completed in 2.4s`
- `run_command · failed`

具体颜色和 spinner 样式集中在主题配置，业务逻辑不直接写 ANSI 颜色。

### 验收

- 模型无文本输出时对话区仍有 working 状态
- 工具执行时能看到工具名和运行状态
- 工具完成、失败、取消均有明确结果
- thinking-toggle 开启时不重复展示冗余 working
- 状态栏原有信息完全保留
- 完成后对话历史不被高频 spinner 更新污染

## 问题八方案：工具调用与结果的展示折叠

### 方案

复用当前工具结果条目和 `ctrl+o` 展开机制，统一限制展示层长度：

1. 工具调用参数先生成单行摘要，超出字符阈值时显示省略标记
2. 工具结果按行数和字符数进行展示层折叠，默认只显示前若干行
3. 折叠提示包含隐藏行数和展开快捷键，例如 `... (28 earlier lines, ctrl+o to expand)`
4. 最近一次工具结果由 `ctrl+o` 展开或收起；没有工具结果时快捷键不产生副作用
5. 工具失败显示错误摘要和失败状态，不能只显示空结果
6. 原始结果仍完整进入 AgentLoop 后续上下文和 Session 持久化；展示摘要不得回写为模型工具结果
7. 工具调用和结果顺序保持与 AgentLoop 事件顺序一致

### 展示与数据分离

```text
ToolExecutionEvent 原始结果
        ├── AgentLoop / ContextManager：使用完整结果
        ├── SessionPersistence：保存完整结果
        └── TUI formatter：生成折叠摘要
```

### 验收

- 大命令、大参数不会占满对话区
- 用户能看出工具确实开始、完成或失败
- `ctrl+o` 可以展开和收起最近结果
- 展示折叠不改变模型收到的工具结果
- 工具调用和结果在恢复 Session 后仍然存在

## 问题六方案：光标闪烁的最小可靠处理

### 方案

- 保留 prompt-toolkit 的 `BLINKING_BEAM` 请求
- 不增加应用层定时器模拟闪烁
- 不在每次输出时反复发送光标控制序列
- 在手动验收文档中说明：光标是否闪烁由终端设置决定；如果终端关闭闪烁，应用不能可靠强制开启
- 若当前终端明确支持而仍不闪烁，只检查输出层是否覆盖了光标形状，不引入新的渲染线程

### 验收

- 代码请求的光标形状正确
- 光标不会因模型输出或 spinner 重绘而消失
- 不增加持续定时重绘
- 在终端设置允许时可观察到闪烁；不支持时功能正常降级

## 测试计划

### 单元测试

- `CommandPicker`：超过可见行数时上下移动自动调整滚动窗口
- Logo：ASCII 内容无 Unicode 方块字；启动页居中和窄终端边界
- `ConversationView`：PageUp/PageDown、滚到底部恢复跟随、输入框定位到底部
- 输入框：空输入历史恢复、多行光标边界、`↑ n more` 计算
- 运行状态：thinking-toggle 两种展示策略、工具开始/完成/失败状态
- 工具展示：参数摘要、结果折叠、展开收起、错误结果
- 状态栏：动态活动条目出现时，静态状态字段仍完整存在

### 手动验收

在真实终端中验证：

1. 输入 `/`，连续按 ↓ 超过列表高度，确认列表随选中项滚动
2. 新建会话确认 ASCII Logo 和前置信息完整居中
3. 发送多轮消息后用鼠标、PageUp/PageDown查看历史
4. 输入多行内容，验证 ↑/↓编辑、历史恢复和 `↑ n more`
5. 分别开启和关闭 `/thinking-toggle`，验证 working、reasoning 和工具状态
6. 执行大输出工具，验证折叠、展开和结果状态
7. 在 WSL/Windows Terminal 中验证普通滚轮与 Ctrl+滚轮行为
8. 检查光标闪烁，并区分应用能力与终端设置

## 验收标准

- slash command 选中项始终可见并能正常滚动
- ASCII Logo 稳定显示，Logo 与前置信息居中且间距清晰
- 键盘和鼠标都能查看历史对话，且不破坏输入框方向键语义
- 输入框历史恢复、多行编辑和 `↑ n more` 均正常
- thinking-toggle 能在 reasoning 模式和 working 模式之间切换
- 模型、工具开始、工具完成、工具失败和取消状态在对话区可见
- 大工具参数和结果默认省略，可展开查看，且不影响模型上下文和持久化
- 状态栏原有工作目录、上下文、余额、费用、模型和复制信息保持不变
- 缩放和光标闪烁按终端能力正确降级，不引入高频重绘
- `uv run pytest` 全部通过，并完成真实终端手动验收

## 明确不做

- 不使用图片 Logo 或外部网络艺术字生成服务
- 不把所有方向键全局改成对话滚动
- 不用应用层定时器强行模拟光标闪烁
- 不在 TUI 层截断模型上下文或持久化原始工具结果
- 不修改现有状态栏字段和布局职责
- 不为终端不支持的缩放能力增加复杂兼容层
