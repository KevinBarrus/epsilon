# 第二十轮优化方案：可选回合预算与安全同批工具并行

## 目标与边界

- 正常交互不因固定回合数无故中断，用户仍可随时 Esc 取消
- 同一模型响应中的独立只读工具并行执行，写入与命令保持安全顺序
- 工具结果写回模型上下文的顺序保持与模型调用顺序一致
- 评测结果能区分轮次触顶、模型网络失败、工具失败与补丁错误
- 不引入任务规划器、后台子 Agent、全局任务时限或新的并发框架

## 统一设计

```text
模型返回一批工具调用
  ↓
按调用顺序预检：查找 → 参数校验 → 权限审批
  ├── 任一工具要求串行 → 整批串行执行
  └── 全部工具允许并行 → 并发执行只读工具
                                  ↓
                    完成即发出 TUI 工具结果事件
                                  ↓
                    按原调用顺序写入 tool Message
                                  ↓
                         请求下一轮模型
```

## 问题一方案：把工具回合上限改为显式可选预算

### 实施步骤

1. 将 `Settings.max_tool_rounds`、`run_chat()` 与 `AgentLoop` 的类型改为 `int | None`
2. 用户配置未设置该字段时使用 `None`：交互会话持续运行，直到模型自然完成、用户 Esc 取消或发生不可恢复错误
3. 用户在 `settings.json` 填写正整数时才启用硬上限；0、负数与非整数仍拒绝
4. `AgentLoop` 使用明确的循环计数，在达到可选上限时保持现有 `stop_reason="tool_limit"` 和完整消息持久化行为
5. 真实 SWE-bench 命令继续要求/传入 `--max-tool-rounds`，评测始终有成本边界，不能因取消交互上限而无限运行

### 代价与控制

- 交互模式的成本边界由用户取消和模型自然结束承担；这是为了消除“阅读大项目被 10 回合打断”的固定限制
- 需要限制成本时，用户显式配置正整数，不增加第二套命令或隐式模型判断

## 问题二方案：使用“顺序预检、按批并行、顺序持久化”调度

### 工具声明

1. 在 `ToolDefinition` 增加 `execution_mode`，取值仅为 `parallel` 或 `sequential`
2. `read_file`、`list_files`、`search_files` 标为 `parallel`
3. `write_file`、`edit_file`、`run_command` 标为 `sequential`
4. MCP 工具默认 `sequential`；只有 Provider 明确提供且本地映射校验为只读并行能力时才标记 `parallel`
5. 同一批只要有一个 `sequential` 工具，整批按原顺序串行，避免读写竞态与命令副作用

### 执行步骤

1. 将 `ToolManager.execute()` 拆为两个最小阶段：`prepare()` 负责查找、参数校验和用户审批，`execute_prepared()` 只调用已批准的 handler
2. AgentLoop 按模型调用顺序完成全部 `prepare()`；校验或拒绝产生即时错误结果，不启动 handler
3. 若本批可执行工具全部为 `parallel`，用 `asyncio` 并发运行 handler；否则按原顺序运行
4. 并发任务每完成一个，就发送对应 `ToolExecutionEvent`，TUI 可立即更新该工具状态
5. 等整批结束后，严格按模型原始工具调用顺序创建 `tool` 消息、追加 `context` 与 `new_messages`，保证协议、持久化和恢复顺序稳定
6. 取消时取消并等待所有尚未结束的子任务，保留已经完成的结果；不让后台工具在用户退出后继续写文件

### 边界

- 不根据 `permission="read"` 自动推断并行性；并行性是工具实现对共享状态的明确承诺
- 不在 UI 层协调并发；UI 只消费按完成时间到达的工具事件
- 不改变工具输出截断、审批文案或 MCP 连接生命周期

## 问题三方案：记录可比较的运行轨迹

1. 为 `AgentRunResult` 增加实际工具回合数，为每批工具调用记录执行模式、调用数和批次耗时
2. SWE-bench `EvaluationResult.events` 写入 `stop_reason`、工具批次统计与总并行批次数
3. HTML 报告按任务展示：模型请求数、工具回合数、工具调用数、并行批次数、工具批次总耗时、停止原因与失败类别
4. 对同一小组任务分别运行“串行基线”和“安全并行”各一次，比较通过率、P50/P95 工具批次耗时和网络失败率；不把单次结果夸大为因果结论

## 测试计划

- 未配置上限时，超过 10 个工具回合仍可自然结束
- 配置上限时，仍返回 `tool_limit`、完整工具链与正确回合数
- 两个延迟只读工具在同批中同时启动，完成事件可按完成顺序到达，写回 Message 仍按调用顺序
- 任一写工具、命令或未分类 MCP 工具出现时，整批严格串行
- 审批拒绝、参数错误、单个工具异常和取消不会让其它任务泄漏或破坏消息顺序
- SWE-bench 结果与报告包含停止原因及批次统计

## 验收标准

- 默认交互会话不会因固定 10 回合停止；显式预算仍可可靠截断
- 多个独立只读工具的墙钟批次耗时接近最长单项耗时，而非各项耗时之和
- 写工具、命令、审批与 MCP 默认不发生并发副作用
- 并行批次的 UI 状态、模型上下文、Session 恢复均保持完整且顺序正确
- 真实评测可以明确说明任务是否触顶，以及并行优化的延迟变化

## 执行顺序

1. 先补运行轨迹字段与测试，建立可比较基线
2. 实现可选工具回合预算，保留评测显式上限
3. 实现工具执行模式和顺序预检
4. 实现 AgentLoop 批量调度、取消收尾与事件顺序
5. 跑单元测试、串行/并行微基准和一组真实 SWE-bench 对照
