# 第二十五轮优化方案：保证 SWE-bench 补丁卫生与裁判结果可解释

## 目标

- 让评测运行产生的临时构建文件不进入 Agent 代码补丁
- 保留基线中原本存在的项目文件，避免“过滤过头”
- 查清 11905 的 Harness 日志与报告字段为何不一致
- 以修复后的有效样本重新获得可解释的结果

## 唯一方案

在评测补丁生成链路中维护“基线文件清单”，只排除**基线不存在且属于明确运行产物**的路径；清理阶段与 diff 阶段使用同一套判断，形成双重保护。

```text
任务基线工作区的文件清单
  ↓
Agent 在容器内运行命令并修改工作区
  ↓
识别新增且属于明确运行产物的路径
  ↓
清理这些路径，并在生成 diff 时再次排除
  ↓
仅把真实源码变化交给官方 Harness
```

不使用简单的“忽略所有 `*.egg-info`、所有 `build/`”规则：项目可能真的跟踪这类路径。基线已有文件永远不因运行产物规则被删除或排除。

## 代码改动顺序

### 问题一：在补丁生成前清理新增运行产物

1. 在准备任务基线工作区后记录相对路径集合
2. 扩展现有运行产物清理逻辑，识别新增的以下目录或文件：
   - `__pycache__/`
   - `*.pyc`、`*.pyo`
   - `.pytest_cache/`
   - 新增的 `*.egg-info/`
   - `build/`、`dist/`、`htmlcov/`
   - `.coverage`、`*.so`
3. 仅删除“不在基线清单中”的匹配路径
4. 保持 Agent 源码修改、基线已有文件和非运行产物的新文件不变
5. 为基线已有的同名目录、新增 `egg-info`、新增 `pyc` 分别增加单元测试

### 问题二：在生成 diff 时再次排除运行产物

1. 将与问题一相同的“新增运行产物”判断传入 diff 生成路径
2. 即使清理阶段因个别文件权限、并发写入或遗漏而未删除，diff 也不得包含这些路径
3. 不通过字符串替换后处理 patch 文本；应在收集候选变更文件时过滤，避免生成不完整或格式损坏的补丁
4. 单元测试构造源码修改与运行产物混合的工作区，断言补丁只包含源码修改

### 问题三：核对并修正 11905 的结果归类

1. 读取 11905 的 `test_output.txt`、`run_instance.log` 和 Harness `report.json`
2. 确认“补丁已应用、测试已运行、报告仍为 `patch_successfully_applied=false`”是 Harness 原始输出还是 Epsilon 读取/映射错误
3. 若是 Epsilon 解析或字段映射错误，在评测结果解析的单一入口修复，并增加该报告形态的单元测试
4. 若是 Harness 自身原始报告不一致，保留原始字段，并在 Epsilon 结果中新增明确的诊断说明，不伪造为已通过或未通过测试
5. 将 11905 的最终归类写入评测记录，作为后续结果解释依据

核对结论：11905 的 Git 补丁已成功应用，测试命令也已执行。官方 Harness 的
`patch_successfully_applied` 只有在它能从测试日志解析出状态表时才会置为真，因此它在
这次测试异常、日志无法解析时保持为假，不能按字面解释为“Git 补丁未应用”。Epsilon 保持
官方 `resolved=false` 的失败结论，并在评测结果中写入这条诊断，不把它误归类为环境错误。

### 问题四：最小回归验证

按顺序执行：

1. 单独重跑 13321，确认补丁不再含 `Django.egg-info/*`，且可进入官方 Harness
2. 单独重跑 11019，确认模型服务可用时能完成完整链路；若仍超时，只标为模型服务样本，不改写为 Agent 失败
3. 不立即重新跑全部五个任务；先用这两个具有明确诊断价值的样本验证修复，避免浪费模型调用

## 验收标准

- 新增 `__pycache__`、`.pyc`、`.pytest_cache`、`*.egg-info` 不会出现在评测补丁
- 基线已有的同名文件不会被清理或从补丁中无故排除
- 13321 的官方 Harness 不再因 `Django.egg-info/*` 同名文件冲突而中断
- 11905 的结果能解释“补丁是否应用、测试是否执行、最终为何未通过”
- 11019 重跑结果能明确区分模型超时与官方裁判未通过
- 完整测试集通过
