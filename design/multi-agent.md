# 多 Agent（SubAgent）设计与实测结论

> 定位：本文记录"要不要拆多 Agent、按什么拆、代价是多少"的完整决策链。
> 配套证据：`problems/multi-agent-arms.md`（四臂对照）、`problems/oncall-read-compare.md`（fork vs fresh）、
> `todo/subagent-context-fork.md`（上下文边界改造）。

## 一、设计目标

两个目标，且只有这两个：

1. **把噪音移出主上下文**：读代码会产生大量文件内容与搜索结果，交给只读 Scout 去读，
   父 Agent 只收一份有界的结论；
2. **把可并行的写工作并行掉**：多个 Worker 在隔离工作区里改不同文件，父 Agent 合并。

**不追求**：更少的 token、更高的墙钟效率（下面第一节就证明这两点做不到）。

## 二、设计原则：拆分边界是**上下文边界**，不是角色边界

最常见的错误是"按角色拆"——"你是读代码的 Agent、你是写代码的 Agent、你是审查的 Agent"。
我们的结论是：**按角色拆得不到好处，按"上下文边界"拆才有**。

| 子 Agent | 默认上下文模式 | 理由 |
| --- | --- | --- |
| **Scout**（只读侦察） | **Fresh**（空上下文） | 它的任务是"读一批文件、回一份结论"，**父 Agent 的上下文对它没有价值**；Fresh 让它只装该读的那部分，结论回传时也天然有界 |
| **Worker**（写代码） | **Fork**（继承父快照，默认截断到最后 4 个 user 回合） | 它要改代码，**必须知道父 Agent 已经决定过什么**；Fork 让缓存前缀可复用，且不必重新交代任务 |
| **Reviewer**（独立审查） | **Fresh** | 独立审查的价值来自**视角独立**；继承父上下文会让它继承父 Agent 的错误假设 |

判别规则（一句话）：

> **子 Agent 需要"知道父 Agent 的决定"，就 Fork；只需要"完成一个自包含的活"，就 Fresh。**

配套机制：

- `fork_history()` 会**先去掉尾部"尚未产生结果"的 assistant 工具调用消息**，避免把半个回合继承下去；
- `fork_last_n` 只保留最后 n 个 user 回合（`DEFAULT_FORK_TURNS = 4`），不足则退化为全量；
- Fork 的提示词**放宽但不放水**（`FORK_CONTEXT_NOTICE`）："继承上下文里读过的文件可以直接引用，
  不必重读；**但不得引用继承里从未出现过的内容**"；
- **配置优先于模型选择**（`resolve_mode`：显式配置 > 模型传参 > 角色默认），避免模型自由发挥破坏路由。

## 三、结构化回传（不共享可变消息列表）

子 Agent **不**与父 Agent 共享一份可变消息列表，而是回一份**有固定小标题**的文本：

| 角色 | 必须包含的小标题 |
| --- | --- |
| Worker | `## CHANGED` / `## EVIDENCE` / `## BLOCKED` |
| Reviewer | `## Passed` / `## Findings` / `## Evidence` |

缺失的小标题会被补空（保证父 Agent 永远拿得到完整结构）。
好处：父 Agent 的上下文增长**可预测**，且不会因子 Agent 的输出格式随机而污染主上下文。

## 四、实测：四臂对照（token + 墙钟双列）

同一任务（把副本 `src/core` 的 75 个 Python 模块重构成等价的 TypeScript）、同 goal、同模型
`deepseek-flash`（`thinking=high`）、同安全熔断口径。**每档只跑一次，是描述性对照，不作统计结论。**

| 档 | token | 墙钟 | 墙钟/单 Agent | token/单 Agent | 完成度 | tsc |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| **单 Agent**（有 goal） | 33,317,726 | 47:24 | 1.00× | 1.00× | **75/75** | 通过 |
| 多 Agent 共享工作区 | 58,546,994 | 1:56:13 | 2.45× | **1.76×** | 45/75 | 独立复验通过 |
| worktree 并行（v1 干净） | 120,010,128 | 2:34:33 | **3.26×** | **3.60×** | 49/75 | 通过（harness） |
| worktree 并行（v2，带 Loop Guard） | 120,077,810 | **2:14:06** | **2.83×** | **3.60×** | 73/75 | **不通过** |

> 出处：`problems/multi-agent-arms.md`（含每档失效模式与单 Worker 失控数据）

### 3 条可靠结论（不依赖任何"覆盖率"型指标）

1. **多 Agent 的 token 代价稳健更高**：共享档 **1.76×**、worktree 档 **3.60×**。
   原因是文本通信带来的**重读成本**——子 Agent 拿不到父 Agent 的上下文，必须自己再读一遍。
   **这个成本改不掉**：加并发、加隔离都不影响它。
2. **worktree 隔离 + 并行机制本身可用**：干净重跑 merge 冲突 **0**、实际并发峰值 **4**。
   修掉"混合批次整批串行化"后，Worker 确实真并发了。
3. **"并行能不能把墙钟压回来"：在失控未复现的情况下仍然是否定的**。
   v2 把最大单 Worker 从 56.2% / 97 分钟压到 11.3% / 24.8 分钟，墙钟从 3.26× 改善到 **2.83×**，
   但 token 仍是 **3.60×**，且 tsc 不通过。墙钟由"总工作量 × 重读成本"决定，并行只能重叠，压不过重读带来的额外总量。

## 六、fork vs fresh：fork 不是免费的

同一扇出任务下的两档对照（`problems/oncall-read-compare.md`）：

| 档 | token | 相对 | 子 Agent 缓存命中 |
| --- | ---: | ---: | ---: |
| B `fanout_fresh` | 3,018,936 | — | 0.9167 |
| C `map_then_fork` | **9,638,365** | **3.19× B** | **0.9537**（+3.7 pt） |

**机制生效了**（fork 的缓存命中率确实更高），但**远不足以抵消重发量**：

> **fork 不是免费的，它把"重读成本"换成了"重发成本"**——每个请求都要重发继承来的前缀。

这也解释了为什么必须"**fork_last_n 截断 + 缓存继承**"配对使用：只 fork 不截断，重发成本会失控。

## 七、边界：什么时候不该用多 Agent

1. **需要共享上下文时**——重读成本 ≥ 省下的时间，直接单 Agent；
2. **输出是一个整体产物时**（一份报告、一个设计、一段连续推理）——拆开再合并的通信损耗会吃掉收益；
3. **语料小于单 Agent 的读取能力时**——没有"读不完"的问题，扇出就没有存在理由（见第五节推论）；
4. **任务本身可串行且无噪音时**——没有要隔离的噪音，也没有可并行的活。
5. **不要用"角色"当拆分依据**——按第二节的上下文边界判别规则来。

## 八、仍然诚实的缺口

- 四臂对照**每档只跑一次**，是描述性结论；按 `design/evaluation.md` 第十三节的功效分析，
  要做出统计结论的样本量在本次规模下不可行；
- v2 档**tsc 不通过**（`core/ui.ts(536,9): error TS2353`），按口径只能判 incomplete；
- Reviewer 角色**模型仍未主动使用**——设计存在但未被真实调用，属待验证能力；
- 隔离工作区（LayerFS）实验尚未落地（`problems/problem31`）。
