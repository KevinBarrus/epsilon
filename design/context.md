# 上下文管理方案

## 一、设计目标

上下文管理参考 Pi 的核心策略，同时保持 epsilon 的实现简洁：

```text
SessionStore：保存完整 JSONL 历史
        ↓
Session / Memory：保存完整运行时消息
        ↓
ContextManager：生成模型请求上下文
        ↓
ModelClient：请求模型
```

核心原则：

- 持久化历史和模型上下文分离
- 历史只追加，不因为压缩而删除
- 上下文超限时，使用模型生成摘要
- 模型看到“摘要 + 最近原始消息”
- 工具调用链不能从工具结果中间切断
- 压缩失败时保留原有历史，并向上层返回明确错误
- TUI 不参与上下文裁剪

## 二、上下文预算

第一版不接入 Tokenizer，使用字符数估算 Token 数：

```text
estimated_tokens = ceil(message_characters / 4)
```

配置两个预算：

- `context_window`：模型上下文窗口大小
- `reserve_tokens`：为模型新回复预留的 Token 数

当满足以下条件时触发压缩：

```text
estimated_context_tokens > context_window - reserve_tokens
```

压缩后优先保留最近的原始消息，目标大小由 `keep_recent_tokens` 控制

## 三、第一版：最小可用压缩链路

### 目标

完成 Pi 压缩机制的主流程，让早期对话和工具调用的重要信息通过摘要继续进入模型上下文

### 功能范围

1. 新增独立的上下文管理模块

   - 从 `Session / Memory` 读取完整消息
   - 返回新的模型上下文列表
   - 不修改原始消息列表

2. 增加消息 Token 估算

   - 用户消息、模型消息、工具结果统一估算
   - 工具调用名称和参数计入估算
   - 估算逻辑保持纯函数，便于测试

3. 增加压缩记录

   JSONL 中新增压缩记录，至少包含：

   - `type: "compaction"`
   - 摘要内容
   - `first_kept_message_index`
   - 压缩前的估算 Token 数

   压缩记录只改变模型上下文的构建方式，不删除原始消息

4. 增加模型摘要请求

   - 将被压缩的旧消息序列化为普通文本
   - 明确要求模型只生成结构化摘要，不继续回答原问题
   - 摘要至少包含目标、进展、关键决策、下一步和重要事实
   - 工具结果在摘要请求中允许使用较短版本，避免摘要请求本身过大

5. 构建模型上下文

   未压缩时：

   ```text
   system messages + 完整原始消息
   ```

   压缩后：

   ```text
   system messages + compaction summary + first_kept_message_id 之后的原始消息
   ```

8. 增加摘要失败兜底

   摘要请求失败时按以下顺序处理：

   ```text
   第一次摘要请求
       ↓失败
   短暂重试一次
       ↓仍然失败
   使用当前模型请求一次简化摘要
       ↓仍然失败
   执行确定性的规则裁剪
   ```

   规则裁剪必须：

   - 保留所有 `system` 消息
   - 从最新消息向前保留到 `keep_recent_tokens`
   - 不在 `tool` 消息中间切断
   - 保留完整的 assistant tool call 与对应 tool result
   - 在上下文中加入“早期历史因摘要失败而省略”的明确提示
   - 不写入永久 compaction 摘要记录

   规则裁剪只作为故障兜底。下次恢复 Session 时仍从完整历史重新尝试摘要，避免一次摘要失败导致早期历史永久无法被模型使用

9. 保证工具消息结构有效

   - 不在 `tool` 消息内部切断
   - 如果边界落在工具调用链中，向前移动到有效边界
   - 保留的原始部分必须包含完整的 assistant tool call 与对应 tool result
   - 被压缩部分的工具信息由摘要承接

10. 接入 AgentLoop 请求前流程

   ```text
   Session.get_messages()
       ↓
   ContextManager.build()
       ↓
   必要时生成并保存 compaction
       ↓
   AgentLoop.run(context_messages)
   ```

### 第一版明确不做

- 不修改或删除 JSONL 中的原始消息
- 不做向量检索、自动摘要链路以外的长期记忆
- 不做复杂 Tokenizer
- 不做单轮超大对话的前缀摘要
- 不做文件读写操作累计追踪
- 不做分支会话摘要

第一版需要实现摘要失败重试和规则裁剪兜底，但不实现备用模型配置。当前项目只有一个模型客户端，因此失败后使用同一客户端进行一次简化摘要请求

## 四、第二版：补齐 Pi 的关键细节

第一版已经完成压缩状态恢复、摘要失败兜底和压缩结果预算校验，第二版只处理三个第一版明确推迟的问题

### 4.1 单轮超大消息处理

#### 问题

第一版按完整对话轮次裁剪。当最新一轮本身超过 `keep_recent_tokens` 时，整体保留会导致压缩后仍然超预算，整体删除又会丢失最新需求

#### 唯一方案

只拆分最新的超大对话轮次：

```text
超大对话轮次
├── 前缀消息 → 生成前缀摘要
└── 后缀消息 → 保留原始消息
```

最终模型上下文依次包含：

```text
已有历史摘要
当前轮前缀摘要
当前轮后缀原文
```

实现规则：

- 以完整消息为最小拆分单位，不截断单条消息文本
- 以工具调用链边界为约束，不拆开 `assistant tool_call` 与对应 `tool result`
- 从最新消息向前保留，优先保证用户最新需求的后缀原文
- 前缀摘要失败时使用第一版规则裁剪兜底
- 原始 JSONL 消息不修改，只新增压缩记录

### 4.2 摘要迭代更新

#### 问题

第一版连续压缩时只摘要本次被隐藏的旧消息，长期运行后早期任务目标和关键决策可能在多次摘要中逐渐丢失

#### 唯一方案

每次压缩都将已有摘要和本次新增的旧消息一起交给模型：

```text
已有累计摘要 + 本次新增旧消息
              ↓
          新累计摘要
```

实现规则：

- 只保留最新一条累计摘要作为模型上下文摘要
- JSONL 保留原始消息和每次压缩记录
- 新摘要必须继续覆盖任务目标、进展、关键决策、后续步骤和关键上下文
- 压缩边界继续指向原始消息序号，不修改 `Message` 模型
- `Session.restore()` 使用最新压缩记录恢复累计摘要

### 4.3 文件操作累计信息

#### 问题

工具调用和工具结果可能在压缩后不再出现在模型上下文中，Agent 可能忘记哪些文件已经读取或修改

#### 唯一方案

从已持久化的工具调用中提取文件路径，并在累计摘要中维护两个固定区块：

```text
<read-files>
...
</read-files>

<modified-files>
...
</modified-files>
```

实现规则：

- 读取类工具的路径写入 `read-files`
- 修改类工具的路径写入 `modified-files`
- 多次压缩时合并已有列表并去重
- 文件列表随累计摘要更新，不额外引入数据库或向量检索
- 工具来源由工具定义提供的类别判断，不在上下文模块中硬编码工具名称

### 4.4 第二版明确不做

- 向量检索
- 复杂 Tokenizer
- 多模型摘要路由
- 分支会话摘要
- 删除或修改原始 JSONL 消息
- 自动追踪除文件路径外的复杂工程状态

### 4.5 第二版代码改动顺序

1. 增加单轮超大消息检测测试
2. 实现前缀摘要和后缀原文保留
3. 增加超大轮次和工具调用链测试
4. 实现已有摘要与新增旧消息合并的累计摘要
5. 增加连续多次压缩的信息保留测试
6. 提取并维护读取文件、修改文件列表
7. 增加文件列表恢复测试
8. 运行完整测试集并进行真实多轮对话验证

## 六、第一版完成情况

第一版已经完成预算估算、规则裁剪、模型摘要、失败重试、提示词外置、预算配置、压缩记录持久化、恢复流程和压缩后预算校验。完整测试集通过 145 个测试

## 七、当前实现取舍

- 设计中的 `first_kept_message_id` 当前实现为 `first_kept_message_index`
- 原因是现有 `Message` 没有消息 ID，增加 ID 会侵入消息模型和全部持久化测试
- 消息序号只在当前线性 Session 中使用，不支持分支会话
- 如果未来实现分支、编辑历史或并发写入，再将边界升级为稳定消息 ID
- 规则裁剪不写入永久 compaction 记录，避免摘要失败导致历史事实永久丢失

## 八、第一版验收标准

- Session 历史和 JSONL 原始消息不会因压缩被删除
- 未超出预算时，模型收到完整消息副本
- 超出预算时，模型收到摘要和最近原始消息
- 摘要请求失败时，不产生损坏的压缩记录
- 摘要请求全部失败时，仍能通过规则裁剪生成可发送的上下文
- 规则裁剪不会写入永久 compaction 摘要记录
- 规则裁剪后的上下文包含明确的历史缺失提示
- 保留的工具调用链结构有效
- Session.restore 后仍能根据 compaction 记录构建相同的模型上下文
- TUI 展示逻辑不负责也不感知上下文裁剪细节
- 第一版测试覆盖预算判断、裁剪边界、摘要接入和恢复流程

## 九、第二版执行前提

第二版在第一版验收通过后执行。每完成一个小步骤先补充测试并验证，再进入下一步，不提前实现下一项能力

## 十、第二版验收标准

- 单轮消息超过 `keep_recent_tokens` 时，不会因为整体保留导致压缩后上下文继续超预算
- 超大轮次的前缀被摘要，后缀原文被保留
- 最新保留部分仍包含完整的用户需求和有效工具调用链
- 前缀摘要失败时可以回退到第一版规则裁剪
- 连续多次压缩后，累计摘要仍保留最早任务目标和关键决策
- 新摘要由已有摘要和本次新增旧消息共同生成
- `Session.restore()` 后可以恢复最新累计摘要和正确的原始消息边界
- 摘要中包含 `<read-files>` 和 `<modified-files>` 区块
- 文件路径在多次压缩中正确合并并去重
- 文件列表不会因为会话恢复而丢失
- 原始 JSONL 消息不会被修改或删除
- 上下文模块不硬编码具体工具来源和工具名称
- 所有新增逻辑都有单元测试，完整测试集通过
- 至少完成一次包含超大消息、多次压缩和文件工具调用的真实多轮验证

## 十一、第三版：陈旧输出驱逐与 Artifact Store

前三节（预算 → 压缩 → 摘要迭代）解决的是"上下文太长怎么办"。
本节记录的是**另一条更激进的路**：不摘要、直接把陈旧的工具输出从上下文里搬走。
它的结论是**负面的**，但负面结论本身是可讲的设计资产。

### 11.1 设计是什么

三个机制配对使用，围绕"工具输出"这一上下文膨胀的主因：

| 机制 | 位置 | 做什么 |
| --- | --- | --- |
| **工具输出防火墙**（Firewall） | `src/core/artifacts.py`（`FIREWALL_THRESHOLD_CHARS = 8_000`） | 单条工具输出超过阈值时，**原文落盘**，上下文里只留**有界占位符** |
| **陈旧输出驱逐**（Eviction） | `src/core/context.py`（`eviction_enabled` / `eviction_threshold_tokens`） | 估算上下文超过驱逐阈值时，把**最旧的完整工具输出**批量降级成占位符 |
| **Artifact Store** | `src/core/artifacts.py`（`ArtifactStore` → `<workspace>/.epsilon/artifacts/<session>/`） | 按会话保存原文，纯文本落盘，模型需要时用**普通 `read_file` 读 `artifact://<id>`** 按行范围取回 |

关键取舍：**不发明新工具、不发明新协议**。
取回走已有的 `read_file`，URI 只是 `artifact://` 前缀；**JSONL 会话原文永不改写**——
被驱逐的只是"模型可见上下文"，历史事实一条都没删。这一点与第二节的"压缩不等于删除历史"是同一条原则。

驱逐默认**关闭**（`eviction_enabled: bool = False`），阈值缺省取压缩阈值的一半。

### 11.2 阈值是怎么定的：先踩坑，再离线定上限

**第一轮真机（E1：开启驱逐，阈值 20k）vs（E0：关闭驱逐）**，长任务三阶段、同一模型同一熔断口径：

| 指标 | E0（关闭） | E1（开启，20k） |
| --- | ---: | ---: |
| 累计 token | 1,134,610 | **1,862,158（+64.1%）** |
| 缓存命中率 | **93.7%** | **72.8%（−20.9 pt）** |
| 驱逐触发次数 | 0 | **51 次**（T1 就 39 次） |
| 未命中 token | 7.2 万 | 50.7 万（7 倍） |
| 三阶段通过 | 3/3 | 3/3 |

**净收益为负**（go/no-go 判据要求 ≤85%，实测 164%）。
根因有两条（`problems/eviction-experiment.md`）：

1. **阈值定得太低**：20k 远低于真实峰值，任务中后段一路在阈值上方反复穿越；
2. **每次只降到"刚好低于阈值"（渐进驱逐）**：一旦估算回到阈值以内就停手，上下文很快又长回阈值上方 →
   **51 次触发 = 51 次缓存前缀断裂**，缓存失效才是成本上升的直接来源
   （两档 `artifact://` 取回次数都是 0，**不是**取回开销导致的）。

**第二步：离线回放定上限**（`/tmp/epsilon-probes/replay_e0.py`，读 E0 归档、0 成本）：

| 阶段 | 实测上下文峰值 |
| --- | ---: |
| T1 | 27,841 |
| T2 | 33,383 |
| T3 | **42,717** |
| 全局 | **42,717** |

阈值扫描：20k → 26 次触发、32k → 9 次、38k → 6 次、**40k–42k → 2 次**、43k → 0 次。

结论：**上界定在"真实峰值之上"（≈43k），而不是拍脑袋**。
低于真实峰值的阈值必然反复触发，而每次触发都是一次缓存断裂。

### 11.3 什么时候不该开

- **语料/任务没到上下文上限时，不该开**——此时驱逐只会白付缓存断裂的成本（本次就是这种情况）；
- 默认关闭；只有"单 Agent 读不完"的超长任务才有开启的理由；
- 即便开启，阈值也必须先量出真实峰值——**不许凭感觉设阈值**。

### 11.4 为什么把负面结论写成文档（可讲的点）

1. **"加了优化反而更贵"是可验证的**：token +64%、缓存 −20.9 pt 都是硬指标，不靠叙事；
2. **能定位到机制**：不是"驱逐没用"，而是"**阈值低于真实峰值 + 渐进驱逐**"这个具体组合有害；
3. **能给出判据**：go/no-go 阈值（≤85%）是**跑之前**定的，不是事后凑的；
4. **离线回放把结论从"感觉"变成"上界"**：0 成本复算，任何人都能重跑。

> ⚠️ 本节引用的 token / 缓存命中率 / 触发次数 / 峰值均为硬指标，不受指标效度限制；
> 但若引用"覆盖率"类结论，须按 `problems/metric-validity-correction.md` 降级处理。

### 11.5 边界

- 驱逐只作用于**工具输出**（上下文膨胀的主因），不驱逐用户消息与 assistant 的推理；
- Artifact Store 只存工具输出**原文**，不做检索、不做摘要、不做索引；
- 仍然**不发明新工具**：取回只走 `read_file`；
- 不做跨会话共享 artifact（按 session 分目录）；
- 这套机制的定位是"**超长任务的兜底**"，不是默认路径。
