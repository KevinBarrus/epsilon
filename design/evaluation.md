# 评测方案

## 一、目标与定位

当前评测从“验证模块能否连通”升级为“衡量 Coding Agent 在真实代码仓库中的任务完成能力”。评测必须同时回答两个问题：

1. Agent 是否能在真实项目中理解 Issue、使用工具、修改代码并通过测试
2. 上下文压缩后，Agent 是否仍能保持任务连续性和修改正确性

整体分为三层：

```text
离线契约评测
        ↓
真实仓库任务评测
        ↓
真实上下文压缩对照评测
```

真实任务采用 SWE-bench 的任务构造方式，但本项目只报告自定义评测集结果，不宣称官方 SWE-bench 成绩。任务来源优先使用 SWE-bench Lite，少量使用完整 SWE-bench 任务

## 二、评测原则

- 评测代码位于顶层 `evaluation/`，不侵入生产 AgentLoop
- 每个任务在独立临时工作区中执行
- 保存完整模型事件、工具调用、文件变更和测试结果
- 任务成功必须由测试、文件状态和变更范围等确定性条件判断
- 真实模型评测必须显式确认，避免意外产生费用
- 原始结果保存为 JSONL，静态报告保存为 HTML
- 评测结果必须区分 Agent 失败、模型失败、工具失败、环境失败和评测器失败
- 单个 Agent 运行必须设置超时上限（如 30 分钟），超时按 Agent 失败记录并单独标注，防止个别实例拖垮整批评测

## 三、任务来源与准入标准

### 1. 任务格式

每个真实任务由以下内容组成：

```text
repository
base_commit
issue_description
test_command
expected_changed_files
forbidden_changed_files
hidden_validation
```

任务使用 Issue 对应的修复前提交作为初始状态。正确修复提交、原始补丁和隐藏测试内容不能提供给 Agent

### 2. 任务筛选

首轮任务全部限制为 Python + pytest 项目，并满足：

- 任务来自 SWE-bench Lite 或完整 SWE-bench
- 修复前提交可以成功检出
- 依赖安装可重复执行
- 测试启动和执行时间控制在 2 分钟以内
- 原项目测试能明确判断修复是否成功
- 工作区不依赖人工交互
- 不需要复杂数据库、浏览器或外部服务

预检失败的任务不能混入 Agent 成功率，必须单独记录为环境不可用

### 3. 任务组成

首轮目标为 10 个任务：

- 8～9 个经过本地预检的 SWE-bench Lite 任务
- 1～2 个来自完整 SWE-bench 的任务
- 任务类型覆盖单模块缺陷、跨文件缺陷、测试驱动修复和工具失败恢复

任务报告中必须记录来源标签：`swebench-lite`、`swebench-full`，不能把两类任务来源隐藏在总指标中

### 4. 抽样与扩展路径

从首轮 10 个扩展到有统计意义的样本时，按以下策略推进：

- **按 repo 分组执行**：同一仓库的多个实例共享 clone 缓存与镜像，优先跑完整一组（如 django 系列 10～15 个）再换下一个仓库，降低网络与准备成本
- **分层抽样**：扩展到 20～30 个时，按仓库覆盖 SWE-bench Lite 的主要语言与难度（单模块 / 跨文件），避免集中在单一仓库
- **失败重跑**：环境失败（`environment`）修复后可直接重跑；Agent 失败默认不重跑，需要稳定性结论时对同任务多次运行（pass@k），重跑结果单独标注

## 四、评测分组与运行次数

### 1. 普通真实任务组

普通组用于衡量 Agent 的基础仓库级修复能力：

- Lite 任务每个运行 3 次
- 完整 SWE-bench 任务每个运行 1 次
- 每次使用新的临时工作区和新的 Session
- 使用相同模型、提示词、工具配置和超时配置

预计普通组运行 25～29 次

### 2. 真实上下文压缩组

从 Lite 任务中选择 3 个任务额外运行低上下文预算版本。除上下文预算外，其余配置保持一致

每次压缩专项必须满足：

- 预先设置较小但可运行的上下文预算
- 运行过程中至少触发一次真实压缩
- 记录压缩前后上下文估算 Token
- 保存摘要请求、压缩记录和后续工具轨迹
- 使用原项目测试重新验证最终修改

如果没有触发压缩，该次运行只能标记为“未触发压缩”，不能作为压缩成功样本

压缩专项单独统计，不与普通任务成功率混合

**同任务对照**：压缩专项与普通组选择同一批任务，对比同一任务在普通 / 低预算下的 `passed`、`compactions`、`estimated_tokens` 与 `actual_tokens`，量化压缩模块对解决率与 Token 成本的影响（压缩不是“只要触发就算好”，必须同时证明压缩后任务仍能完成）

## 五、统一执行流程

```text
准备 base_commit 工作区
        ↓
启动独立 Session
        ↓
向 Agent 提供 Issue 描述
        ↓
Agent 阅读代码、调用工具、修改文件、运行测试
        ↓
保存模型和工具事件轨迹
        ↓
运行独立测试与隐藏验证
        ↓
检查文件变更范围和 Session 恢复结果
        ↓
生成 EvaluationResult 和 HTML 报告
```

评测器不得读取正确修复提交来帮助 Agent，只能在任务结束后使用它或隐藏测试进行验证

## 六、确定性验收

每个任务至少包含以下断言：

- 原项目测试或隐藏测试通过
- 目标缺陷已修复
- 允许修改的文件范围正确
- 禁止修改的文件未被修改
- 工具调用参数合法
- 工具失败后是否继续完成任务
- Session 是否可以恢复
- 持久化是否发生降级
- 压缩专项是否真的生成压缩记录
- 压缩后最终代码测试是否仍然通过

任务的 `passed` 只能由确定性断言计算，不能由模型最终回复中的关键词决定

## 七、统一轨迹与结果

每次运行保存一条 JSONL 结果，并记录：

```json
{
  "run_id": "uuid",
  "task_id": "repo-issue-id",
  "source": "swebench-lite",
  "evaluation_group": "normal",
  "base_commit": "commit",
  "passed": true,
  "duration_ms": 4210.4,
  "model_requests": 3,
  "tool_calls": 5,
  "tool_failures": 1,
  "compactions": 0,
  "estimated_tokens": 1200,
  "actual_tokens": 2400,
  "persistence_degraded": false,
  "changed_files": ["src/example.py"],
  "assertions": [],
  "events": []
}
```

事件轨迹至少包含用户消息、模型文本、工具调用、工具结果、上下文压缩、Session Flush 和最终测试结果

## 八、指标

### 1. 正确性指标

- 任务成功率：通过任务数 / 有效任务运行数
- 测试通过率：测试通过运行数 / 有效任务运行数
- 无关修改率：未修改禁止文件的运行数 / 有效任务运行数
- 工具失败恢复率：工具失败后最终完成运行数 / 发生工具失败的运行数
- 持久化成功率：未发生降级的运行数 / 有效任务运行数

### 2. 压缩指标

- 压缩触发率：实际生成压缩记录的运行数 / 压缩专项运行数
- 压缩后任务成功率：压缩后测试通过运行数 / 触发压缩运行数
- 摘要请求失败率
- 摘要失败后的兜底成功率
- 压缩前后 Token 数和压缩比例

### 3. 性能与资源指标

- 端到端耗时平均值、P50、P95
- 单次模型请求耗时平均值、P50、P95
- 平均模型请求次数和工具调用次数
- 输入 Token、输出 Token、总 Token
- 单任务费用：只有配置了真实价格后才计算

服务端没有返回实际 Token 时必须记录为 `null`，不能用估算值冒充实际 usage。样本量小于 20 时，P50/P95 只作为观察值，不作为稳定性能结论

所有指标分别按以下维度展示：

- 全部有效任务
- `swebench-lite`
- `swebench-full`
- `normal`
- `compaction`

## 九、失败分类

每次失败必须归入一种主要类别：

- `agent`: Agent 未完成任务或修改错误
- `model`: 模型请求失败、返回格式错误或无法继续
- `tool`: 工具执行失败且未恢复
- `environment`: 依赖、网络、测试命令或仓库环境不可用
- `evaluation`: 评测器、断言或结果保存错误

环境失败不计入 Agent 成功率，但必须单独展示，避免通过删除困难任务制造虚高结果

## 十、Baseline 与报告

Baseline 至少保存：

- 任务集版本
- 任务来源和任务 ID
- base commit
- 模型名和模型版本
- 提示词版本
- 工具定义版本
- 上下文预算配置
- 运行次数
- 成功率、测试通过率、Token 和延迟指标

回归比较必须区分：

- 新增失败
- 历史已知失败
- 任务缺失
- 重复运行
- 环境失败
- 评测器失败

HTML 报告至少展示任务来源、运行分组、样本数、通过数、失败分类、测试结果、工具轨迹摘要、压缩记录、Token、耗时和 baseline 差异

## 十一、实现顺序

1. 扩展评测结果模型，增加任务来源、任务分组、base commit 和变更文件字段
2. 增加 SWE-bench 任务描述与本地任务适配器
3. 实现任务预检：仓库检出、依赖安装、测试启动和超时检查
4. 实现独立临时工作区和任务清理流程
5. 接入统一确定性验收：测试、文件变更和工具轨迹
6. 实现 Lite 任务普通组运行
7. 实现完整 SWE-bench 任务运行
8. 实现低上下文预算压缩专项
9. 更新指标、JSONL 存储、baseline 和 HTML 报告
10. 先运行小规模试验，确认任务和断言可靠后再运行完整批次
11. 保存原始结果、报告和运行配置，保证结果可复现

## 十二、长任务评测（扩展方向）

SWE-bench 单实例是单 bug 修复，测不出“连续长时间任务”能力。作为扩展方向，在基准线稳定后增加：

- **连续多实例会话**：在同一个 Session 内连续修复同一仓库的 3～5 个实例，跨多轮自然触发压缩，验证压缩后的任务连续性
- **压缩记忆验证**：压缩前后对关键事实（文件路径、改动内容、上下文约束）的保持程度，通过压缩后提问或后续任务完成度衡量
- **自定义长任务场景**：加功能 → 修 bug → 重构的连续开发任务，配合单实例超时与 Session 恢复验证“可中断、可恢复”

长任务评测单独统计，不与单实例基准线混合

## 十二、验收标准

- 至少 8 个 SWE-bench Lite 任务通过本地预检
- 至少 1 个完整 SWE-bench 任务完成独立运行
- 普通组按约定完成 3 次或 1 次重复运行
- 3 个任务完成低上下文预算专项
- 压缩专项至少真实触发一次上下文压缩
- 所有任务都有独立测试或隐藏验证结果
- Agent、模型、工具、环境和评测器失败可以区分
- 普通组与压缩组指标独立展示
- 结果 JSONL 可以重新读取，HTML 报告可以重新生成
- 全量测试通过
- 报告明确标注这是自定义 SWE-bench 风格评测，不冒充官方 SWE-bench 成绩
