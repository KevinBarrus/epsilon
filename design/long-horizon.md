# 长程控制：空转纠偏（Loop Guard）与完成门（Completion Gate）

> 定位：长任务里 Agent 有两种**方向相反**的失效——**做太多**（陷进局部循环烧光预算）
> 和**做太少**（自己说"完成了"其实没做完）。本文记录这两侧的机制、代价与边界。
> 配套证据：`todo/loop-guard.md`、`todo/loop-guard-v2.md`、`problems/multi-agent-arms.md`、
> `problems/completion-gate.md`、`problems/completion-gate-v3.md`。

## 一、设计动机：两个相反方向的失效

| 失效方向 | 症状（真实观测） | 机制 |
| --- | --- | --- |
| **做太多**（空转） | 一个 Worker 空转 **97 分 09 秒**、发出 **1,360 次**模型请求、烧掉 **53%~56%** 的预算后报错，父 Agent 一直在等它 | **Loop Guard**：检测 → 注入纠偏 |
| **做太少**（假完成） | Agent 读了 9% 的预算就宣告"够了"，报告里 109 个路径只有 27 个真实存在 | **完成门**：独立验证 → 拒绝 → 把未满足项回注 |

两条线共用一条原则：**不设硬上限**。轮次上限会掐死正常的长任务，
而这两种失效都不是"时长问题"，是**行为问题**——到点死掉 ≠ 走出来。

## 二、Loop Guard：只注入纠偏，不设轮次上限

### 2.1 两个检测

| 检测 | 语义 | 阈值 |
| --- | --- | --- |
| **A：重复调用** | 跨轮出现**签名相同**的工具调用（工具名 + 规范化参数摘要 `action_digest`） | `thresholds = (3, 5, 8)`，其后每 4 轮 |
| **B：无新事实** | 连续 N 轮**没有任何新事实**（新签名 / 成功的写或委派 / 新的命令输出指纹） | `no_progress_rounds`，默认 **8** |

v1 → v2 两个关键修正：

1. **进展的定义改了**：`run_command` **不再默认算进展**——只有产生**新签名或新输出指纹**才算。
   v1 把"跑了命令"当进展，于是"反复跑同一个失败的测试"不算空转（漏报）；
2. **"没写文件"不再报警**：v1 把"没写文件"当无进展，误报了正常的**长探索**
   （288 轮的合法探索被连续告警）。v2 只看"读取集合是否还在增长"。

### 2.2 提醒节制（不节制就会洪泛）

- **每轮最多注入一条提醒**（硬上限）；多条候选时按优先级挑一条：
  **`进展不变 > 错误族 > 重复调用 > abab`**；
- 阈值分级沿用 v1：`repeated_call` 用 3/5/8（首次 mild，其后 detailed）；
- `exempt_tools` 可豁免指定工具；
- **只读角色豁免检测 B**（`READ_ONLY_ROLES = {"scout"}`）——Scout 的任务就是反复读，不是空转；
- 每条提醒都带**"防持久化"那一句**：明确告诉模型"这是本轮临时提醒，不是用户偏好，
  **不要写进 Memory / Skills 或任何持久文件**"。

### 2.3 实测（这是最值得讲的数字）

| 指标 | 值 | 出处 |
| --- | ---: | --- |
| live 全轮注入次数 | **3 次**（父 0 / Scout 1 / Worker 2） | `problems/multi-agent-arms.md` |
| 同一批归档按 **v1 口径**反事实 | **≈304 次** | 同上 |
| 离线回放 vs 真机 | **逐项对得上**（22 个 run，最长 288 轮） | `evaluation/replay_loop_guard.py` |
| 那个 288 轮 / 13.6M token 的大 Worker | 最长"无新事实"连续只有 **3 轮** | `problems/multi-agent-arms.md` |
| 失控复现情况 | v2 重跑**未复现**失控（最大单 Worker 11.3% / 24.8 分钟） | 同上 |

**304 → 3 的含义**：v1 的口径会把所有合法探索都当成空转（洪泛 304 次），
而**正确的语义一次都没漏报**——288 轮的合法探索零误报，同时真失控的模式被抓住。

**离线回放工具**是这套机制可验证的关键：`evaluation/replay_loop_guard.py` 读归档的
`child_events.jsonl`，**按 `run_id` 分组**逐轮喂给 guard，输出每个 run 的首个触发轮次、
各信号触发次数与注入次数。**live 与 replay 共用同一份 `observe_facts()` 实现**，
因此"回放对得上"不是巧合，而是同一个函数跑两遍。

### 2.4 借鉴来源

| 参考项目 | 借鉴了什么 |
| --- | --- |
| **oh-my-pi** | `ToolCallLoopGuard`：跨轮检测**完全相同的工具调用**，达阈值注入**隐藏纠偏消息**；可配 threshold / exemptTools；模型换调用即重置 |
| **deepseek-harness (dsh)** | 同类"检测 + 纠偏"的工程做法 |
| **MiniMax Code** | `runaway-guard`：在"检测 + 纠偏"上做得更细 |

**我们加的**：无新事实语义（v2）、每轮最多一条 + 优先级、只读角色豁免、防持久化提示、离线回放工具。

### 2.5 为什么"给 Worker 加上限"是错答案

1. **生产环境不能用轮次/时间上限**——正常长任务会被一起掐死；
2. **上限治不了根因**——空转是行为问题（陷进局部循环），**到点死掉不等于走出来**。

## 三、完成门：独立验证后才允许宣告完成

### 3.1 机制

- **三值判定**：`met` / `not_met` / `inconclusive`（解析不出来一律 `inconclusive`，**绝不放行**）；
- **三条拒绝原因**：`not_met`（证据说没做完）、`inconclusive`（**证据不足**）、
  `verifier_error`（**验证器自己坏了**：预算耗尽 / 超时 / 连接报错）。
  **故障与证据不足必须分开记**——把验证器故障记成"证据不足"，等于把实现缺陷归咎于模型；
- **拒绝与回注**：拒绝时把**未满足项**回注给模型，让它继续推进原目标（上限 `max_rejections = 2`）；
- **超限放行写 `unverified`**，**不写 `complete`**——"停下来交给人"，而不是假装完成；
- **终态**：`GoalStatus = Literal["active", "complete", "unverified", "budget_limited"]`。

### 3.2 验证是"判定一份有界证据"，不是"再探索一遍"

**这是 v2 的核心设计**（验证成本 2~3M → **约 4k token**）：

宿主先装配一份**有硬上限的证据简报**（整包 **≤ 14,000 字符**），验证器**只判定它**：

| 小节 | 上限 |
| --- | ---: |
| 目标 objective | 4,000 |
| 验收标准 criteria | 4,000 |
| 完成声称 claim | 2,000 |
| 改动的文件（来自**动作记录**） | 4,000（≤100 条） |
| 跑过的命令与退出码（来自动作记录） | 4,000（≤100 条） |
| 脚本化检查结果 | 4,000 |
| 近期对话尾巴 | 4,000（≤5 条） |

超限按优先级裁剪（先裁尾巴 → 命令 → 改动）。**改动与命令来自动作记录，不重新读代码。**

验证器默认 **evaluator 模式：单次模型调用、不给任何工具**；可选 subagent 模式带
`BoundedReadGuard`（≤3 文件 × ≤200 行）。

### 3.3 脚本化检查器（能出 pass/fail 的才算验收标准）

| 检查器 | 判定 |
| --- | --- |
| `path_exists` / `files_changed` | 交付物/改动是否到位 |
| `sections_cover` | 结构化小节是否齐全 |
| `paths_per_section` / `mentioned_paths_exist` | 引用的路径真实存在（**防编造**） |
| `command_passed` | 命令退出码 |
| `identifiers_per_section` | 每节引用**在代码里真实存在**的标识符（常量/类型/函数各≥1，跨节不重复计数，核验次数有上限，超限判 **UNVERIFIED** 而不是静默通过） |
| `question_types_per_section` | 每节覆盖 5 类问题，且**该段引用了代码级证据** |

无脚本证据的条目在简报里**明确标注**，验证器对它们一律判 `inconclusive`。

### 3.4 成本与效果

| 指标 | 值 | 出处 |
| --- | ---: | --- |
| 验证成本 | v1 真机 2~3M → v2 **约 4k/次** | `problems/completion-gate.md` |
| smoke | 第一次声明 `not_met`（脚本检查 FAIL）→ 回注补齐 → 第二次 `met`，**9,778 token** | 同上 |
| **能拦编造** | 报告 109 个路径只有 **27** 个真实 → 拒绝；修正后 **282/285** 个标识符真实、路径 **53/53** | `problems/completion-gate-v3.md` |
| 中等语料覆盖率（⚠️ 已降级指标） | 门前 3/9（518k token）→ 门后 4/9（4.91M，9.5×） | 同上 |

> ⚠️ 上表最后一行引用的"覆盖率"是**已降级指标**（见 `problems/metric-validity-correction.md`），
> **不得单独支撑结论**。其余各行是硬指标。

## 四、边界（这一节最重要）

### 4.1 覆盖度进不了 criteria

v3 实验的目标是"让 criteria 驱动覆盖度"，做法是**子系统问题模板**：不列"要哪些事实"，
只规定"每个子系统必须回答哪 5 类问题"（职责/交互/关键数据结构/关键参数/失败模式）。
结果：**报告里 285 个标识符候选有 282 个真实存在、路径 53/53、编造清零，覆盖率仍然只有 4/9。**

结论（这是整条路线的边界）：

> **「回答了哪几类问题」≠「找到了我们测量的事实」。**
> 要脚本化"有没有答到那 N 条事实"，就必须在 criteria 里**点名那 N 条**——
> 而 criteria 会随拒绝反馈**回注给模型**，**点名即泄露**，测量仪器当场失效。
>
> 因此在"不泄露"的前提下，**覆盖度无法进门的 criteria**，它只能继续当
> "**模型看不见的测量仪器**"。这是结构性的，不是实现没做好。

替代方案（能进 criteria 的只有"形状"）：结构完整性、无编造、命令退出码、
标识符存在性——**全部与"考哪几个"无关**。

### 4.2 其它边界

- 完成门**不证明"内容是对的"**，只证明"声称与证据一致"；
- `unverified` 是**诚实的终态**，不是失败——但要人在环；
- Loop Guard **不设上限**，因此它**不保证**预算不被烧光，只保证"空转会被打断"；
- 门与 guard 的判据都**必须在跑之前写死**（本次 go/no-go 与 v3 判据都是先写死再跑）。

## 五、成本对照（为什么 v2 的重写值得）

| 版本 | 验证器形态 | 单次验证成本 | 结果 |
| --- | --- | ---: | --- |
| v1 | fresh 只读 Scout（**用主循环共享总账判预算**） | 2~3M 且**每次都判不出** | 全部 `inconclusive` |
| v2 | 判定**有界证据简报**（≤14,000 字符，单次调用、无工具） | **约 4k** | 判得出、能拒绝、能促成修正 |

**v1 失败的真因**（必须讲准）：不是"验证器会探索仓库"，而是**验证器客户端的预算账本口径错误**——
它用的是**主循环共享总账**，主循环早已超限，于是**每次验证调用在发请求之前就被判超预算**。
属**实现缺陷**，与"验证器是否会探索"无关。
（教训：**"参考项目这么做" ≠ "我们因为它没这么做才失败"**。）

## 六、验收标准

- 未注册/Loop Guard 关闭时行为与引入前一致；
- 空转检测：合法长探索**零误报**；重复调用与无新事实**不漏报**；
- 每轮最多注入一条；只读角色豁免；提醒不写入任何持久文件；
- 完成门：解析不出来一律 `inconclusive`（绝不放行）；故障记 `verifier_error`；
- 超限放行写 `unverified`，**不写 `complete`**；
- 证据包整包 ≤14,000 字符，且验证器**拿不到任何工具**；
- **防绕过**：配置了验证器时，同步的"自然结束"路径绝不能把自己标成完成；
- 离线回放与真机逐项一致。
