# 编程语言选型

## 结论

epsilon 第一阶段使用 Python 3.11+ 开发。

如果后续经过实际测量，确认某个独立模块成为明确的性能瓶颈，再考虑使用 Rust 重写该模块。Rust 不是第一阶段的默认实现语言，而是面向经过验证的性能瓶颈的补充方案。

## 选择 Python 的原因

epsilon 当前最重要的目标是做出一个自己能够完全理解、解释和持续迭代的 Coding Agent。Python 在开发速度、代码可读性和 Agent 生态之间提供了较好的平衡。

- LLM、OpenAI-compatible API、MCP、Git、文件处理和评测工具都有成熟支持。
- Agent Loop、上下文管理、工具协议和记忆模块可以用较少的代码表达。
- 适合快速验证架构，而不需要先投入大量精力处理底层语言复杂度。
- Python 的主要性能瓶颈通常来自模型请求和外部工具，而不是本地 CPU 计算。
- 便于编写集成测试、评测脚本和实验代码，能够快速验证设计是否有效。

## 为什么不一开始使用 Rust

Rust 适合高性能、强安全和并发密集型基础设施，但当前阶段的主要风险不是执行速度，而是架构理解不足和过度设计。

如果一开始使用 Rust，可能把大量精力放在所有权、生命周期、异步类型和 crate 拆分上，反而延缓 Agent 核心流程的验证。对于当前项目，这种复杂度收益并不明确。

## Rust 的引入原则

未来只有在满足以下条件时，才考虑将某个模块改用 Rust：

1. 已经通过 profiling 或基准测试确认该模块是实际瓶颈。
2. 瓶颈来自本地计算、并发调度、文件处理或其他适合系统语言优化的工作，而不是模型 API 延迟。
3. 模块职责和输入输出协议已经稳定，可以独立替换。
4. 引入 Rust 后带来的构建、调试和部署成本低于性能收益。

优先考虑独立重写的候选模块包括大规模文件搜索、复杂 Token/文本处理、并发任务执行器或高频状态索引。Agent Loop、上下文策略和业务编排仍优先保留在 Python 中，以保持设计清晰和迭代速度。

## 配套技术选型

- 包管理：`uv`
- 异步运行时：标准库 `asyncio`
- 类型检查：`pyright` 或 `mypy`
- 格式化与静态检查：`ruff`
- 测试：`pytest`
- CLI：优先使用 `argparse` 或轻量 CLI 库
- 数据模型：优先使用标准库 `dataclasses`，确有必要时再引入 `pydantic`

第一阶段尽量少依赖大型 Agent 框架。模型客户端、Agent Loop、工具协议、上下文对象和基本持久化由项目自己实现，使关键设计可以被完整理解和解释。

## 预期收益

这套选型将语言复杂度控制在合理范围内，同时保留未来优化空间：

```text
Python 快速验证架构
        ↓
实际运行与 profiling
        ↓
只优化已确认的瓶颈
        ↓
必要时以 Rust 替换独立模块
```
