# 指令：完成门 v2 —— 验证器改为「判定有界证据」（含接口决定）

> 本文已折入执行方 5 个接口点的拍板结果，**可直接实现，不必再确认**。
> 调研依据见 `ref/agent-completion-gate.md`（本地，不入库）。

> **⚠️ 根因已更正（见 `todo/completion-gate-v3.md`，勿再引用本文旧说法）**
>
> 本文初稿曾写"根因（有代码铁证）：验证器探索仓库"——**这个判断是错的**。
> 真因是**验证器客户端的预算账本口径错误**：它传的是主循环的**共享总账**，
> 主循环早已超限，于是**每次验证调用在发请求之前就被判超预算**
> （v1 的 Scout 连一次请求都没发出去）。属**实现缺陷**，与"验证器是否会探索"**无关**。
>
> **v2 的 bounded evidence 是基于 minimax-code 的独立设计改进**（验证成本 几 M → 约 4k/次），
> 与 v1 的失败**没有因果关系**，**不可归因**。
>
> **教训**：**"参考项目这么做" ≠ "我们因为它没这么做才失败"**——
> 不要把"优秀设计"当成"我们失败的原因"，更**不要在未验证时写成"铁证"**。

## 一、四个改动

| # | 改动 | 效果 |
|---|---|---|
| ① | **有界证据包**（整包 ≤14,000 字符） | 验证成本 2~3M → **约 4k token** |
| ② | **脚本化检查器** | 验收标准变成**能出 pass/fail 的检查** |
| ③ | **独立终态 `unverified`** | 超限放行**不再写 `complete`** |
| ④ | **先解耦**：在验证可行的中等语料上测门 | 不先碰 codex 全量 |

## 二、改动 ①：有界证据包

新增 `src/core/completion_evidence.py`：`assemble_evidence_brief(...) -> str`

### 2.1 证据项与硬上限（照抄 minimax-code 口径）

| 证据项 | 来源 | 上限 |
|---|---|---|
| objective | `Goal.objective` | 4,000 字符 |
| acceptance_criteria | `Goal.acceptance_criteria` | 4,000 字符 |
| **完成声称** | 最后一条 assistant 文本 + `goal(op=complete)` 调用摘要 | 2,000 字符 |
| **改动文件清单** | 见 2.2 | ≤100 条 / 4,000 字符 |
| **命令 + 退出码** | 见 2.2 | ≤100 条 / 4,000 字符 |
| **脚本化检查结果** | 见改动 ② | 4,000 字符 |
| 近期对话尾巴 | 见 2.3 | ≤5 条 / 4,000 字符 |
| **整包** | — | **≤ 14,000 字符**（超了按优先级裁剪） |

### 2.2 改动/命令的来源（**接口决定 1**）

- 从 **`GoalPolicy.observe_tool_results(tool_calls, results)`** 提取，**不改签名**；
- **成功的和失败的动作都要记**，但**在证据包里分开呈现**：
  - **`成功改动`**：成功执行的 write/edit 类调用的路径；
  - **`失败尝试`**：失败的写/编辑/命令（是"尝试过"的证据，**不是**"改成了"的证据）；
  - **`命令与退出码`**：命令类调用 + 其 `is_error` / 退出码。
- **上限 100 条 / 4,000 字符**，超了按"最近的优先"裁剪。

### 2.3 近期对话尾巴的来源（**接口决定 2**）

- **复用 `AgentLoop` 在工具执行期已写入的 ContextVar 快照**（零签名改动）——`goal` 工具的处理器正好在该窗口内运行；
- **但该 ContextVar 目前叫 `PARENT_CONTEXT`（为 fork 起的）** → 请**重命名为中性名**（如 `CURRENT_MESSAGES`），**或在定义处注释写明双重用途**，避免以后重构 fork 时把它删掉、导致门的证据静默缺失；
- **快照不存在时**（测试/异常路径）→ 尾巴**留空**，并在证据包里**显式标注"无近期对话"**，不要静默省略。

### 2.4 验证器调用方式（**必须改**）

- **默认 `evaluator` 模式：单次模型调用，不给任何工具**——它**只能**依据证据包判定；
- `completion_gate.verifier_token_budget` 默认 **3,000,000 → 100,000**；
- `completion_gate.verifier_timeout_seconds` 默认 **300 → 60**；
- 提示词要点：
  > "你**只能**根据下面的证据判定，**不得**打开工作区或索要更多资料。
  > 证据不足的条目一律判 `inconclusive`。只输出 `VERDICT:` 与 `UNMET:`。"

## 三、改动 ②：脚本化检查器（**接口决定 3**）

### 3.1 分工

- **检查器**放在 `completion_evidence.py`：**有界纯函数**，签名 `(spec, workspace) -> CheckResult`；
- **`Goal` 增加 `acceptance_checks: list[dict]`**（结构化，与散文 `acceptance_criteria` 并列，**随 goal 持久化**）；
- **harness 注入**：`GoalPolicy(..., checks=..., workspace=...)`——**policy 本身不知道工作区**，由 harness 给。

### 3.2 内置检查器（全部必须有界）

| 检查器 | 作用 |
|---|---|
| `path_exists` | 被引用的路径必须真实存在（防幻觉） |
| `sections_cover` | 交付物必须包含指定章节（如"每个核心子系统一节"） |
| `paths_per_section` | 每个章节必须给出 ≥N 个真实存在的代码路径 |
| `files_changed` | 指定文件确实被成功改动过 |
| `command_passed` | 跑一条命令并看退出码（见 3.3 的门槛） |

### 3.3 `command_passed` 的三条门槛（**新加**）

1. **默认禁用**，需在 `acceptance_checks` 里**显式开启**；
2. **必须走既有的命令执行器与权限/审批路径**，**不得绕过审批**；
3. **必须带超时**。

### 3.4 两条纪律

1. **`acceptance_checks` 在设置时就校验**：未知 checker、参数缺失 → **直接报错**，**不许静默忽略**（静默忽略 = 门悄悄放水）；
2. **无法脚本化的条目**在证据包里明确标注"**无脚本证据**"，验证器对这类条目**一律 `inconclusive`**——
   **不许假装检查过了**。

### 3.5 ⚠️ 与隐藏清单严格分离

**门的反馈会回注给模型**（"你缺 X"）→ 所以：

- **评测用的 criteria 必须泛化**，**绝不能是那 40 条隐藏清单**；
- 40 条清单继续当"**模型看不见的测量仪器**"，与门的 criteria **严格分开**；
- 加一条验收测试：**断言门的反馈文本里不含任何清单条目的关键词**。

## 四、改动 ③：独立终态 `unverified`（**接口决定 4**）

数据已显形：门后 B 只做 17.1M、覆盖率 5/40（门前 38.0M、11/40）
→ **"拒绝 N 次后放行"给了模型一条合法的提前退出通道。**

- `GoalStatus` 增加 **`unverified`**；超过 `max_rejections` 后写 `unverified`，**不再写 `complete`**；
- **渲染**：统一显示为"**未通过验证（停下来交给人）**"（`/goal status`、`goal_final_status`、`completion_verdict`）；
- **语义**：**凡判断"完成没完成"的地方必须把它当未完成**（`status != complete`），**不能当成 complete 的变体**；
- **必须终态**：`unverified` 后**不再自动续跑**（否则"超限 → 未验证 → 又续跑"= 新的死循环）。

## 五、改动 ④：`subagent` 模式（**接口决定 5**，可选、保持最小）

- 默认仍是 `evaluator`；`subagent` 模式**只为确需抽查时**提供；
- **包一层 `read_file`，只作用于验证器子 Agent**，**不影响正常 Agent 的读工具**：
  第 4 个文件直接拒绝；单文件**只返回前 200 行**；
- **工具集只给 `read_file` / `search_files` / `list_files`**，**不给 shell、不给任何写工具**；
- 不要为它做复杂抽象。

## 六、执行顺序（**不许跳步**）

```
1. 改动 ①②③④（0 模型成本）→ 先写测试 → 全量测试通过
2. 极小 smoke（<100k token）：门能基于「证据包 + 脚本检查」做出判定（met 与 not_met 各一次）
3. 在「验证可行」的中等语料上测门：
   语料 = codex 的 protocol + config + mcp 三个子系统子集
   —— 跑之前先报预估，经确认再跑
4. codex 全量：暂缓，等第 3 步有正面结果再说
```

**第 3 步要回答的问题**：
> **当验证真的能判定时，门能不能把覆盖率从 X% 推到接近 100%？代价是多少 token？**

## 七、测试（先测后写）

1. **证据包有界**：超长 objective/criteria/大量改动 → 整包 **≤14,000 字符**，且按优先级裁剪；
2. **成功/失败分开**：伪造事件流，断言"成功改动"与"失败尝试"**分开呈现**，且各自 ≤100 条；
3. **对话尾巴**：有快照时取最后 5 条；**无快照时留空并标注**"无近期对话"；
4. **检查器**：5 个检查器各有正反用例；**`command_passed` 未显式开启时必须被拒**；越界（无超时配置）被拒；
5. **`acceptance_checks` 校验**：未知 checker / 参数缺失 → **报错**，不是静默忽略；
6. **无脚本证据的条目** → 验证器判 `inconclusive`（不得 `met`）；
7. **evaluator 模式不给工具**：断言验证器收到的工具集为空；
8. **`subagent` 模式硬上限**：第 4 个文件被拒、单文件 ≤200 行；
9. **`unverified` 语义**：超限后状态是 `unverified`（**不是** `complete`），且 **`status != complete`**、**不再自动续跑**；
10. **泄漏检查**：门反馈文本不含隐藏清单关键词；
11. **无回归**：`completion_gate.enabled=false` 行为与现在一致；v1 的**防绕过测试仍通过**；
12. 全量测试通过（当前 867 项，以实际值为准）。

## 八、验收

1. 上条 12 项全过；
2. **smoke**：门基于证据包 + 脚本检查**真的做出判定**（`met` / `not_met` 各一次），成本 **<100k token**；
3. 全量测试通过；门 v1 的防绕过测试不回归。

## 九、边界

- **验证器默认不打开工作区**（evaluator 模式）；
- **证据包必须有硬上限**（无上限 = 回到 v1 的错误）；
- **不设执行轮次上限**（上限只加在拒绝次数上）；
- **"无法验证"一律算未通过**（fail-closed），但**必须便宜地失败**（几 k token，不是几 M）；
- **评测 criteria 与隐藏清单严格分离**；
- **`acceptance_checks` 由用户/调用方提供，不得由模型自己生成**（否则等于自证）。

## 附：不要做的事

- ❌ **不要在改动 ①②③④ 完成前跑 codex 全量**——只是把 60~120M 花在同一个无效判定上（已验证一次）；
- ❌ **不要靠"抬高验证器预算"解决**——预算再高也追不上"验证器读整个仓库"的成本曲线；
- ❌ **不要把散文标准交给会探索的验证器**（这是设计原则，**不是** v1 的实际失败原因——v1 的真因是预算账本口径错了）；
- ❌ **不要为让门"看起来有效"而调整判定口径**——**判不出来就如实写判不出来**。
