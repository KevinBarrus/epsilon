# 指令：大语料只读对比实验（codex）——先容量探测，再跑 A/B/C

## 零、为什么换语料（前情，必须理解）

oncall 实验失败的原因不是多 Agent 不行，是**语料太小**：

- oncall 约 **20,000 行** → A 档（单 Agent）**176 秒 / 3.6M token 就读满了** 5/6 源码题；
- 换算：约 **180 token / 行代码**（含上下文重复发送的放大）；
- 单 Agent 实际可用预算 ~40M → **大约能覆盖 20 万行**。

**结论：要让"单 Agent 读不完"成为结构性约束，语料需要 40 万行以上。**
只有到那时，"扇出读提高覆盖率"才会是**量级大的结构性效应**（例如 40% vs 80%），而不是上次那种被噪声盖住的十几 % 差异。

## 一、语料与范围

- **语料**：`~/projects/codex`（**约 452,000 行**代码；去掉测试约 178k 核心）
- **范围**：整仓，排除 `.git`、`target`、`node_modules`、单文件 > 2MB
- **保留**：Rust 源码、测试、脚本、文档（**文档保留，但清单必须是源码级**，见第四节）
- **副本机制**：复制到临时目录，Agent 只改副本；`result.json` 记 `original_code_unchanged`

## 二、Phase 0：先出清单（不跑模型）

1. 按**子系统**划分 codex（例如 `core` / `exec` / `tui` / `app-server` / `mcp` / `sandbox` / `protocol` …），
   每个子系统出 **2~3 条源码级问题**，合计 **20~30 条**；
2. **每条都要逐项验证：答案不在 `README.md` / `docs/` 里**（写在代码里才合格）
   ——上一次就是栽在这里：清单内容能在 README 里找到，任务一泄露就直接把基线抬满；
3. 输出结构：`{子系统: [问题...]}`，评分时按"子系统命中数 / 总条目数"算**源码级覆盖率**。

## 三、Phase 1：容量探测（**只跑 A，先做**）

**目标**：确认单 Agent 在新语料上**读不完**。这一步决定后面三轮值不值得跑。

- **做法**：跑 A 档（单 Agent），熔断 **40M token / 90 分钟**；
- **判定**：
  - ❌ **饱和**（没撞熔断、且覆盖了清单大部分）→ **语料还是不够大** → **停下汇报**，换更大的语料
    （`oh-my-pi` 456k / `minimax-code` 377k / `layerfs` 338k）；
  - ✅ **撞熔断，或明显漏掉大量子系统** → 语料够大 → **进入 Phase 2**；
- **产物**：`evaluation-results/big-repo-read-probe-codex-<date>/`（含 `report.md` + `result.json`）；
- **费用**：预计 **5~20M token**，**开跑前先报预估、经确认再跑**。

**注意**：Phase 1 的 A 档结果**直接作为 Phase 2 的 A 基线**，不必重跑（同一任务、同一范围）。

## 四、Phase 2：正式三档

| 档 | 内容 |
|---|---|
| **A** | 单 Agent 串行读（复用 Phase 1 结果） |
| **B** | **fresh** 只读子 Agent 扇出（各读不相关子系统） |
| **C** | **父先做项目测绘 → fork 子 Agent 继承项目图后深读** |

**两条铁律**（都是上次的教训）：

1. **清单内容绝不写进任务描述**。任务只写**泛化要求**，例如：
   > "为每个核心子系统写一段**实现剖析**：说清机制、关键参数/阈值、数据结构与**代码位置**。
   > 无法确定时写'未能确定'，**不许编造**。"
   ——**不列举**具体问题；
2. **清单必须分散在整个代码库**（每个子系统都有条目），覆盖率才反映"读了多少"，
   而不是"题目划没划重点"。

## 五、功效门槛（**Phase 2 开跑前必须过**）

按 `design/evaluation.md` 第十三节先算功效：

- 本实验要检出的是**结构性效应**：**源码级覆盖率的大幅差异**（例如 40% vs 80%）；
- 预期若只是**十几 %** 的差异 → **不要跑**（噪声级差异需要几十轮，成本不可行，上次已经证明）；
- 算出来需要跑很多轮 → 说明效应不够大 → 先想办法把语料/范围调到"明显读不完"。

## 六、指标

**主**：**源码级覆盖率**（按子系统命中）；
**副**：文档级覆盖率、token、精确率、读调用次数、缓存命中率；
**记录但不作主指标**：墙钟。

## 七、验收

1. Phase 0 清单产出，且**逐项验证过"不在文档里"**（附验证方式）；
2. Phase 1 明确给出"读得完 / 读不完"的判定与证据；
3. Phase 2 三档产出 `report.md` + `result.json`，**固化到 `evaluation-results/`**；
4. 对照表含：源码级覆盖率、token、精确率、读调用次数、缓存命中率；
5. 结论**标注证据强度**（按 `design/evaluation.md` 第十三节）：结构性 / 噪声级；
6. 如实标注单次或多次运行。

## 八、边界

- **不改 codex 仓库**（只改副本）；
- 子 Agent **只读**（Scout），不给写权限；
- 任务描述**除档位说明外三档完全一致**；
- **不设轮次上限**，只用熔断兜底；
- fork 档沿用**放宽后的引用口径**（继承上下文里已读过的可直接引用，不必重读；未出现过的不得引用）。

## 附：成本

- Phase 0（出清单）：**0**（不跑模型）；
- Phase 1（容量探测）：**5~20M**；
- Phase 2（A 复用 + B + C）：预计 **每档 10~30M**。

**逐阶段汇报、每阶段开跑前报预估。**
