# 指令：给 Goal 加「完成门」（Completion Gate）

> 调研见 `ref/agent-completion-gate.md`（五家做法对照）。本文是可执行规格。

## 零、要解决的问题（实测证据）

大语料只读实验（codex，829,876 行）：

| 档 | 源码级覆盖率 | 预算用了 | 终止 |
|---|---:|---:|---|
| A 单 Agent | **10.0%** | **9%** | **`completed` / goal complete** |
| B 扇出 | 27.5% | 95% | **`completed`** |

**A 只读了语料的 3%、答对 4/40 道题，就宣告目标达成。**
我们的 `goal(op=complete)` 把完成决定权**完全交给模型的自我声明**，没有任何外部检查。

**而且**：我们的 goal 提示词**已有防呆措辞**（"绝不把成功重定义为更小子集"），**模型照样提前收手**。
→ **结论：光靠提示词不够，必须有一个能否决完成的机制层"门"。**

## 一、目标设计（对齐 minimax-code，按我们的规模裁剪）

| 层 | 做什么 |
|---|---|
| **① 验收标准** | `Goal` 增加 `acceptance_criteria`：**可检查**的完成条件 |
| **② 独立验证器** | `goal(op=complete)` 时，交一个 **fresh、只读**的子 Agent 判定 |
| **③ 拒绝 + 续跑** | 未通过 → **拒绝完成**，回注"未满足项"，目标保持 active |
| **④ 拒绝上限** | 连拒 N 次后**放行但标注"未通过验证"**（防死锁） |
| **⑤ 防退化 nudge** | "多轮没调工具" / "重复同一总结" 各一条 |

**注意**：上限加在**"拒绝次数"**上，**不加在执行轮次上**——不违背"长任务不掐死"。

## 二、实现要求

### 2.1 `Goal` 增加验收标准

- `src/core/goal.py` 的 `Goal` 增加 `acceptance_criteria: str = ""`（**多行文本，一行一条**）；
- 为空时，**用 `objective` 作为判定依据**（不阻断旧用法）；
- 随 goal 一起持久化。

### 2.2 完成门（核心）

`GoalPolicy.mark_complete()` 现在是个**平凡检查**（`src/core/goal.py:99`）。改造：

- 注入一个**验证器回调**（由 harness 提供，见 2.4）：`async (goal) -> Verdict`；
- `Verdict` 三值：**`met` / `not_met` / `inconclusive`**
  （**暂不做 minimax-code 的第四值 `impossible`**——我们目前没有 paused/blocked 状态，先不加；
  将来加"暂停"状态时再补）；
- `goal(op=complete)` 的处理改为：
  - `met` → 接受完成（`status=complete`，`verified=True`）；
  - `not_met` / `inconclusive` → **拒绝**：返回**未满足项清单**，目标保持 active，**拒绝计数 +1**；
  - **验证器不可用/超时** → **拒绝**（"无法验证 ≠ 已完成"，对齐 minimax-code 的"把不确定当作未达成"），**同样计入拒绝次数**。

### 2.3 拒绝上限（防死锁）

- 配置 `max_rejections`（**默认 2**）；
- 超过上限后：**放行完成**，但 `Goal` 记 `verified=False`，并在最终回复与评测产物里**显式标注"未通过验证"**；
- 这条是"不设轮次上限"原则的配套：**上限加在拒绝次数上，不加在轮次上**。

### 2.4 验证器（复用现有件，不另起一套）

- **必须是 fresh 子 Agent**（独立性），且**只读**——复用现有 Scout 路径；
- **输入**：`objective` + `acceptance_criteria` + 工作区路径；
- **指令要点**（照抄 minimax-code 的精神，中文化）：
  > **把完成当作未证实**，对照**当前实际状态**验证；对**每一条验收项**找出权威证据（文件、命令输出、测试结果、运行时行为）；
  > **不要**用意图、部分进展、对早前工作的记忆、或一个看起来合理的答案当作完成的证据；
  > **不确定或间接的证据一律算未达成**；**审计必须"证明完成"，而不是"没找到明显剩余工作"**；
  > 只输出：`VERDICT: met|not_met|inconclusive` + `UNMET:` 逐条列出未满足项（没有则写"无"）。
- **超时**：`verifier_timeout_seconds`（默认 120s），超时按 `inconclusive` 处理。

### 2.5 防退化 nudge（两条，照抄措辞）

| 触发 | 注入内容 |
|---|---|
| **连续 N 轮一个工具都没调**（默认 3） | "**复述计划、状态或意图不是进展。**用工具检查当前证据，执行下一个具体动作再汇报。" |
| **连续两次给出实质相同的总结** | "不要重复同样的总结或停在同一个点。**选一个实质不同的下一步**并执行。" |

### 2.6 完成审计提示词 + **缓存前缀稳定**

- 把 2.4 的审计要点写进 **goal 的 kickoff 契约**；
- **长契约只在 kickoff 注入一次**，后续续跑只注入**一句短提示**
  （对齐 minimax-code 的注释 *"so canonical history stays cache-prefix stable"*，也与我们已有的 prompt cache 工作一致）。

### 2.7 配置

```
completion_gate: {
  enabled: true,               # 默认开
  max_rejections: 2,
  verifier_timeout_seconds: 120,
  no_tool_nudge_rounds: 3
}
```
解析进 `Settings` 并校验非法值（与 `loop_guard` 同风格）。

### 2.8 可观测

- 新增 `CompletionGateEvent`：`verdict`、`unmet`（清单）、`attempt`（第几次）；
- `AgentRunResult` 加 `completion_gate_rejections`；
- 评测 `result.json` 汇总：拒绝次数、每次的判定、最终是否 `verified`；
- 事件序列化要进 `evaluation/events.py` 的 `event_to_record`（**否则评测里一触发就崩**，这个坑我们踩过）。

## 三、测试（先测后写）

1. **无 criteria** → 用 `objective` 作判定依据；
2. **`met`** → 接受完成，`verified=True`；
3. **`not_met`** → 拒绝，返回未满足项，目标仍 active，拒绝计数 +1；
4. **`inconclusive`** → 同拒绝；
5. **验证器超时/抛错** → 按拒绝处理（fail-closed），计数 +1；
6. **超过 `max_rejections`** → 放行，`verified=False`，且产物里标注"未通过验证"；
7. **防退化 nudge**：连续 3 轮无工具调用 → 注入"复述计划不是进展"；重复总结 → 注入"换一个下一步"；
8. **无回归**：`completion_gate.enabled=false` 时行为与现在完全一致；
9. **可观测**：事件序列化、计数进 result.json；
10. 全量测试通过。

## 四、验收

1. 构造一个"**故意偷懒**"的场景（goal 带 3 条验收标准，模型只做了 1 条就声明完成）→
   **门必须拒绝**，且拒绝原因/未满足项**落盘可查**；
2. 再跑一次让它补齐 → 门通过；
3. 拒绝次数超上限时放行且**明确标注未验证**；
4. 全量测试通过、goal/loop guard 无回归。

## 五、边界

- **不设执行轮次上限**（上限只加在"拒绝次数"上）；
- 验证器**只读**（Scout），**不得修改工作区**；
- **验收标准必须由用户/调用方提供**，**不得由模型自己生成**（否则等于自证）；
- 验证器判定**不得被模型的消息内容影响**（它看状态，不看声称）；
- 全链路 fail-open 只用于"不影响主流程"，**但"无法验证"一律算未通过**。

## 附：与既有机制的关系

| 机制 | 防的是什么 | 方向 |
|---|---|---|
| **Loop Guard**（已实现） | 空转、原地打转 | 防**做太多** |
| **Completion Gate**（本指令） | 提前收手、谎报完成 | 防**做太少** |

两者互补，缺一不可。
