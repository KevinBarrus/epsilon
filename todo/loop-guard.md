# 指令：Agent 空转检测与纠偏（Loop Guard）

> 本文先讲清"要解决什么问题"（面试要点），再给实现方案。方案已与执行方对齐。

## 一、要解决的问题

### 1.1 现象（真实案例）

worktree 并行大任务评测中，出现一个**失控 Worker**：

- `worker-call_01` 连续运行 **97 分 09 秒**、烧掉 **64,028,171 token**（占全局 **53%**），最后报错退出；
- 中途可观察到的症状：**3 个 worktree 的 commit 号连续 30 分钟不变**、**子事件清一色全是 `read_file`**；
- 父 Agent 只发了 23 次模型请求，**Worker 发了 2359 次**。

也就是：一个 Agent 陷入了"**反复调用工具、却没有任何进展**"的局部循环，把整个任务的预算吃光。

### 1.2 为什么"加上限"是错误答案

第一反应往往是"给 Worker 加轮次/时间上限"。**这是错的**，原因两条：

1. **生产环境不能给长任务设上限**。真实用户跑几小时的长任务时，任何"轮次上限"都会把正常任务也掐死；
2. **上限治不了根因**。"空转"是 **行为问题**（陷进局部循环），不是 **时长问题**（跑太久）。给时长封顶，只是让它在到点时死掉，**没有让它走出来**。

### 1.3 正确思路

把"空转"当成一个**信号**：**检测出来 → 注入一条纠偏消息 → 把模型从局部循环里拽出来**。不是掐死任务。

## 二、业界怎么做（调研结论）

| 项目 | 空转处理 | 关键设计 |
|---|---|---|
| **oh-my-pi** | `ToolCallLoopGuard` | 跨轮检测**完全相同的工具调用**（name + 规范化参数）；达阈值注入**隐藏纠偏消息**（含工具名、次数、参数/结果摘要）；可配 threshold、exemptTools；模型换调用即重置 |
| **deepseek-harness** | `repeat-tool-reminder` + `timeout-policy` | **升级式提醒** `thresholds=[3,5,8]`：第 3 次温和提醒，第 5/8 次详细提醒；**只提醒、不否决**（advisory）；参数按**完整规范化串**比较；另有每工具声明 `timeoutMs` |
| **codex** | 无内置重复检测 | 靠 **stop hooks** + **用户中断** |
| **pi** | 无 loop guard | 靠 **用户中断** |
| **ClaudeCode** | 靠**验证检查** | "给 Agent 一个能判 pass/fail 的检查，循环自己就闭合了"（`/goal` 完成条件）+ 用户中断 |

**共同点**：**都不设轮次上限**。用"检测 + 纠偏提醒"把模型拽出来。

## 三、方案：Loop Guard

### 3.1 检测 A（核心）：重复的相同工具调用——按**单个调用签名**

（对齐决定：**不用"整轮 hash"，按单个签名检测**，更通用，能抓"同轮夹了别的调用"的重复读。）

- 为每个**调用签名**（`name` + 规范化参数）维护"连续出现次数"；
- 某签名在某轮**未出现** → 该签名计数归零；
- 出现**任一"有进展"调用**（定义见 3.2）→ **全部签名计数归零**；
- 达到**升级式阈值**（默认 `[3, 5, 8]`）时，注入对应级别的纠偏消息；
- 支持 `exempt_tools`（免检签名）。

### 3.2 检测 B（补充）：长期无进展

有些空转不是"完全相同的调用"，而是"读了一堆不同文件但一直不产出"。补一个：

- **进展定义（对齐修正）**：**任一成功的、`capability` 不是 `file.read` 的工具调用**——即 `file.write`（写/编辑）、`run_command`、`agent.*`（委派）都算进展；只有纯读文件（`read_file`/`list_files`/`search_files`）不算。
  - 这样**父 Agent 的委派不会误报**（`spawn_*` 的 capability 是 `agent.*`，算进展）。
- **连续 N 轮（默认 8）没有任何"进展"调用**，且模型仍在调工具 → 注入"你已连续多轮无产出"提醒；
- **角色开关（对齐）**：默认 **scout 关闭**，其余（parent / worker / reviewer）开启；`no_progress_rounds=0` 关闭检测 B。

### 3.3 纠偏消息（升级式 + 节流）

**温和（第一阈值 3）：**
> 你在用**完全相同的参数**重复调用同一个工具。先仔细分析上一次的结果：如果任务还没完成，请**换一种方法或换参数**，不要重复同样的调用。

**详细（阈值 5、8）：**
> 检测到重复工具调用：
> - 工具：`<name>`
> - 连续次数：`<count>`
> - 参数：`<canonical args 摘要>`
> - 上次结果：`<result 摘要>`
> 不要继续重复；换策略，或明确说明当前阻塞。

**无进展（检测 B）：**
> 你已经连续 `<N>` 轮没有产生任何文件改动、命令执行或委派。重新评估：是卡住了、缺信息，还是该换个方案？如果确实无法推进，请说明阻塞原因。

**节流（对齐决定）**：`3/5/8` 各注入一次；**8 之后每 4 轮注入一次详细版**，直到循环中断。
- 理由：真实失败是"模型无视有限提醒、空转 97 分钟"，所以**不能"8 之后静默"**；但"每轮都塞"会让 context 无限增长，故**每 4 轮节流**。

### 3.4 配置（对齐决定：嵌套对象）

顶层 `loop_guard: { enabled, thresholds, exempt_tools, no_progress_rounds }`（与 `mcp_stdio` 同风格），解析成 `Settings` 的 4 个字段：

- `loop_guard.enabled`（默认 `true`）；
- `loop_guard.thresholds`（默认 `[3, 5, 8]`）；
- `loop_guard.exempt_tools`（默认 `[]`）；
- `loop_guard.no_progress_rounds`（默认 `8`，`0` 关闭检测 B）。

## 四、实现点

1. 新增 `src/core/loop_guard.py`：`ToolCallLoopGuard`（检测 A + B）+ 纠偏消息渲染（中文注释）；
2. 接入 `src/core/agent_loop.py` 的 `run()`：每轮工具结果写回后把该轮喂给 guard；命中则**注入 `role:"system"` 消息到 `context`（不写入 `new_messages`、不持久化）**——与现有 `TurnEndPolicy.follow_up_message()` 的 goal 续跑消息同一模式；
3. **每个 AgentLoop 各持一个 guard**（`_run_subagent` 每次新建 `AgentLoop`，天然隔离）；
4. **新增 `LoopGuardEvent`**（kind A/B、工具名、连续次数、级别）随 `on_event` 抛出；`AgentRunResult` 加 `loop_guard_injections` 计数；评测 `result.json` 汇总父/子各角色触发次数；
5. 配置从 `Settings` 读取（`config.py` 解析 + 校验）；
6. **接线范围（对齐决定）**：`ui.py`、`evaluation/swebench.py`、`evaluation/long_task.py`、`evaluation/big_task_single_goal.py` **四处都接**，统一从 `Settings` 取。

## 五、测试（先测后写）

1. 检测 A：连续 3 轮出现**相同签名** → 第 3 轮注入温和提醒；第 5、8 轮注入详细提醒；
2. 检测 A 重置：中间出现一次**不同调用** → 该签名计数归零；出现**成功写/命令/委派** → 全部归零；
3. 检测 A 免检：`exempt_tools` 命中的签名不计数；
4. 检测 A 节流：第 8 轮之后，**每 4 轮**再注入一次详细版；
5. 检测 B：连续 8 轮无"进展"调用 → 注入无进展提醒；出现任一非只读成功调用后重置；**scout 角色不触发**；
6. 注入的消息**不进 `new_messages`、不落盘**（与原 goal 消息一致）；
7. 现有 goal / 混合批次 / 全量测试无回归。

## 六、验收标准

1. 构造"模型重复同一工具调用"的场景，harness 能**检测并注入纠偏**（`LoopGuardEvent` / 日志佐证），且**不硬停任务**；
2. 纠偏后模型行为改变（换调用 / 继续推进）；
3. 无进展检测**不误伤父 Agent 的委派与只读角色**；
4. `result.json` 能看到父/子各角色的 `loop_guard_injections` 计数；
5. 全量测试通过，原 goal 机制无回归。

## 七、边界（明确不做）

- **不加轮次/时间上限**——检测到循环只"提醒纠偏"，不掐任务；
- 不做"自动改写模型调用"（advisory，只加消息）；
- 不做全局单例 guard（每个 Agent 独立）。

## 八、已知局限（v1，诚实标注）

检测 B 的"进展"判定是 `capability != "file.read"`，因此**任何成功的非读文件调用都算进展**，
包括 `ls`、`git status` 这类平凡命令。后果：一个 Agent 如果"每轮重读同一文件 + 顺带跑一条
平凡命令"，会不断重置计数，**检测 A、B 都抓不到**。

- 这是"防父 Agent 委派被误报"的代价（父 Agent 的 `spawn_*` capability 是 `agent.*`，不是
  `file.read`，所以必须算进展），属 **v1 可接受局限**；
- 本轮真实失控形态是"**清一色 `read_file`**"（2359 次模型请求中没有命令调用），检测 A 在
  阈值 3 时几秒内即可命中，**已被完整覆盖**；
- 收紧方向（**不建议现在做**）：把 `ls`/`git status` 等纯查询命令排除出"进展"，需要维护
  查询命令白名单，漏判会把父 Agent 的委派误报回来——收益不确定、风险确定。
