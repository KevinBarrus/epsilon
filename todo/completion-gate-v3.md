# 指令：完成门 v3 —— criteria 升级为「子系统问题模板」+ 两处修正

> 前置：`todo/completion-gate-v2.md`（已实现）。
> 本指令解决两件事：**先修两个错误**，再把 criteria 从"结构合规"升级为"**能驱动覆盖度**"。

## 零、先修两处（必须，0 模型成本）

### 0.1 更正根因写法的错误（**这是最重要的一条**）

`ref/agent-completion-gate.md` 与 `todo/completion-gate-v2.md` 里写的"**根因（有代码铁证）：验证器探索仓库**"——
**这个判断是错的**。真实原因是**预算账本 bug**：验证器客户端传的是主循环的**共享总账**，
主循环早已超限，于是**每次验证调用在发请求之前就被判超预算**（v1 的 Scout 一次请求都没发出）。

请把两处改成：

> **v1 失败的根因**：验证器客户端的**预算账本口径错误**（用了主循环共享总账）——
> 属**实现缺陷**，与"验证器是否会探索"**无关**。
> **v2 的 bounded evidence 是基于 minimax-code 的独立设计改进**（成本 几 M → 约 4k/次），
> 与 v1 的失败**没有因果关系**，**不可归因**。

> 教训写进文档：**"参考项目这么做" ≠ "我们因为它没这么做才失败"**——
> 不要把"优秀设计"当成"我们失败的原因"，更不要在未验证时写成"铁证"。

### 0.2 更正错误分类：预算类错误必须记成 `verifier_error`

v1 那 4 次拒绝**全部记成 `inconclusive`**——把**验证器故障**记成了"**证据不足**"，
等于**归咎于模型没做完**。我们专门把拒绝原因分三类，就是为了防这种误归因。

**改**：验证器客户端的**预算 / 超时 / 连接类错误 → `verifier_error`**；
只有"验证器正常跑完但证据不足"才是 `inconclusive`。**加回归测试**。

## 一、为什么现在的 criteria 推不动覆盖率

中等语料实测（门后 1,138,011 token / 覆盖率 **4/9 = 44.4%**，门前 3/9）：

门的 criteria 衡量的是**结构合规**（"三小节 + 每节 ≥2 真实路径 + 无编造"），
**不是"读了多少、答对多少"**。所以它能**拦住编造**，但**推不动深度**。

→ 要让门驱动覆盖率，**criteria 必须编码"覆盖度"**。

## 二、criteria 升级：子系统问题模板

### 2.1 核心思路

**criteria 不列"要哪些事实"（那会泄露隐藏清单），而是规定"每个子系统必须回答哪几类问题"。**

对**每一个子系统**，强制回答：

1. **职责**：它负责什么；
2. **交互**：它与哪些子系统交互（须给出真实路径）；
3. **关键数据结构**：核心的类型/表/结构；
4. **关键参数/阈值/常量**：给出**代码位置**；
5. **失败模式与错误处理**：出错时怎么办、错误码/降级路径在哪。

**为什么这招成立**：
- **不泄露**：这是"问答模板"，不说任何具体事实；
- **强制深度**：要答第 3/4/5 类，**必须真去读代码**——正好打我们之前那条"机制题 1/10"；
- **可脚本化**：每类问题都能用结构性检查判 pass/fail。

### 2.2 对应检查器（全部**客观可核、不泄露**）

| 检查器 | 判定 | 是否泄露 |
|---|---|---|
| `sections_cover`（已有） | 每个子系统各一节 | 否 |
| **`identifiers_per_section`（新，关键）** | 每节 ≥N 个**在代码里真实存在**的标识符（常量/结构/函数名）——**用 grep 核验存在性** | 否（**不说哪些**） |
| `paths_per_section`（已有） | 每节 ≥M 个真实存在的代码路径 | 否 |
| `mentioned_paths_exist`（已有） | 无编造路径 | 否 |
| **`question_types_per_section`（新）** | 每节覆盖 5 类问题（按结构关键词判定） | 否 |
| `files_changed` / `command_passed`（已有） | 交付物确实改了 / 命令通过 | 否 |

**`identifiers_per_section` 是这一版的关键**：它逼模型**为每个子系统举出真实存在的常量、结构、函数名**——
而要做到这一点，**只能真去读那部分代码**。

### 2.3 与隐藏清单的分离（不变）

- 门用**模板 + 存在性核验**；40 条清单继续当"**模型看不见的测量仪器**"；
- **继续保留泄漏断言测试**：门反馈文本里不得出现任何清单条目关键词。

## 三、实现要求

1. **新增"模板 → criteria"生成器**：输入**子系统清单**（由 harness 给定，**不得从隐藏清单推导**），
   输出结构化 `acceptance_checks`；
2. **新增两个检查器**：`identifiers_per_section`、`question_types_per_section`；
3. **`identifiers_per_section` 的实现**：从报告里抽取被反引号/代码块包裹的标识符，
   **逐个在语料里核验存在**（用 `search_files` 或等价的有界搜索），统计**每节真实存在的数量**；
   - **必须有界**：一次核验的总搜索次数设上限（例如 ≤200 次），超限按"未验证"处理；
4. **"防刷分"约束**：
   - 同一标识符**跨节不重复计数**；
   - 每节必须包含**不同类别**的标识符（≥1 常量、≥1 结构/类型、≥1 函数），
     避免"随便 grep 一堆常量"刷过去；
5. **`acceptance_checks` 校验**：未知检查器/参数缺失 → **设置时报错**；
6. **文档更正**（第 0.1 节）同步落到 `ref/` 与 `todo/` 两处。

## 四、测试（先测后写）

1. `identifiers_per_section`：正例（引用了真实标识符）通过；反例（编造标识符）判 FAIL；
2. **跨节重复不计数**；**类别不全**（只有常量没有结构/函数）判 FAIL；
3. `question_types_per_section`：5 类缺失任一 → FAIL；
4. **有界性**：核验次数超上限 → 按"未验证"处理，**不得静默通过**；
5. **预算类错误 → `verifier_error`**（第 0.2 节）；
6. **泄漏断言**：门反馈文本不含隐藏清单关键词；
7. **无回归**：v1 防绕过测试、v2 的证据包有界测试全部仍通过；
8. 全量测试通过（当前 884 项，以实际值为准）。
